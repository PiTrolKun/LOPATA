# ЛОПАТА — аудит аппаратной независимости ИИ-сценариев

Дата фиксации: 2026-10-05



## 1. Причина аудита

При синхронизации с репозиторием после выпуска `0.4.0-beta` обнаружилось, что первая музыкальная CUDA-реализация была жёстко привязана к `SM89 / compute capability 8.9`.

После проверки остальных сценариев выяснилось, что похожее историческое предположение присутствует и в других частях ЛОПАТЫ:

> **«GPU = NVIDIA CUDA»**

На основном тестовом ПК с RTX 4090 это долго оставалось незаметным.

---

## 2. Общий продуктовый принцип

Целевая логика ЛОПАТЫ должна быть аппаратно-независимой:

> **если совместимый GPU поддерживается конкретным движком и ресурсов достаточно — использовать лучший доступный GPU backend; CPU/RAM использовать как fallback.**

Пользователь не должен вручную выбирать CUDA, Vulkan, SM86, SM89, SM120 или конкретное поколение GPU.

ЛОПАТА должна:
1. определить доступное железо;
2. определить возможности конкретного runtime;
3. выбрать лучший проверенный backend;
4. оценить доступную память;
5. использовать CPU/RAM только при реальной необходимости.

## 3. Найденные области риска

### 3.1. Музыкальный сценарий YuE2

Текущее состояние анализа `0.4.0-beta`:
- CUDA runtime собран с `CMAKE_CUDA_ARCHITECTURES=89`;
- `GGML_VULKAN=OFF`;
- `MusicCudaSupport` разрешает GPU только при `major == 8 && minor == 9`;
- иначе выбирается CPU AVX2.

Закреплённый `yue2.cpp` поддерживает:
- NVIDIA CUDA;
- AMD/Intel через Vulkan;
- CPU;
- runtime loading нескольких backend.

Upstream CMake предусматривает архитектуры от Turing до Blackwell, включая:
- SM86 — RTX 30;
- SM89 — RTX 40;
- SM120/121 — Blackwell / RTX 50.

**Статус:** эта часть уже передана Codex отдельной текущей задачей и должна быть исправлена первой.

### 3.2. Литературный сценарий

Это наиболее серьёзная найденная зависимость после музыки.

`LiteraryChatRuntime` формирует аргументы запуска с жёстким:

```text
--device CUDA0
```

Подготовка также требует `native.cuda`, а `LiteraryAutomaticBudget` ориентируется на инвентаризацию именно `CUDA0`.

Литературный runtime умеет уменьшать число GPU-слоёв и использовать RAM reserve, но это происходит внутри CUDA/NVIDIA-контура.

**Риск:** пользователь с мощной AMD GPU может не получить полноценного GPU-пути, даже если используемый llama.cpp способен работать через другой backend.

**Приоритет:** критический.

### 3.3. «Желе» — извлечение фактов

`jelly_worker.py` содержит прямую проверку:

```text
if not torch.cuda.is_available():
    raise RuntimeError(...)
```

Модели загружаются через `.to("cuda")`, затем дополнительно проверяется, что фактическое устройство — CUDA.

**Следствие:** GLiNER/NuExtract-проход текущего «Желе» является CUDA-only.

**Приоритет:** критический.

Здесь нельзя автоматически предполагать, что Vulkan добавляется так же просто, как в GGML-runtime. Нужно отдельно исследовать доступные Windows backend для используемых PyTorch-моделей.

### 3.4. Анализ изображений — Alpha / Beta / Gamma

Текущие Omni-профили используют общий backend:

```text
Runtime/Backends/llama.cpp/b9442/win-cuda-12.4-x64
```

`OmniLlamaProtocol` описывает размещение как:

```text
model = "cuda"
projector = "cuda"
```

и запускает модель с полным GPU-offload (`-ngl 99`, `--mmproj-offload`).

**Риск:** AMD/Intel GPU сейчас не получают эквивалентный GPU-путь. RTX 50 также требует отдельной проверки на актуальном backend/runtime.

**Приоритет:** высокий.

### 3.5. Генерация изображений

Текущий простой генератор использует `stable-diffusion.cpp`, но в `image-generation-manifest.json` закреплён только Windows CUDA runtime:

```text
sd-...-bin-win-cuda12-x64.zip
```

Сам закреплённый upstream `stable-diffusion.cpp` поддерживает:
- CUDA;
- Vulkan;
- HIP/ROCm;
- SYCL;
- OpenCL;
- CPU.

У upstream есть Windows-пути для Vulkan и ROCm/HIP.

**Следствие:** Radeon сейчас лишён GPU-ускорения именно текущей поставкой ЛОПАТЫ, а не возможностями upstream.

**Приоритет:** высокий.

### 3.6. Общее ядро Qwen / Песочница / Prompt Assistant / часть финансов

Многие функции используют `LlamaServerRuntimeService`, который работает через:

```text
LlamaBackendPaths.Platform = "win-cuda-12.4-x64"
```

То есть поставляется NVIDIA CUDA-сборка llama.cpp.

Положительная сторона: `LlamaServerRuntimeService` сначала пробует `gpuLayers=99`, а при неудачном старте повторяет с `gpuLayers=0`.

Поэтому на неподходящем GPU программа способна уйти на CPU/RAM, но мощная AMD/Intel GPU может при этом простаивать.

**Приоритет:** средний, но архитектурно важный.

### 3.7. Kimi Medium

`chatllm.cpp v24 / win-x64` в текущей ЛОПАТЕ отдельно зафиксирован и проверен в CPU-профиле.

**Приоритет:** низкий. Отдельная GPU-оптимизация возможна позже, но это не такая же очевидная дыра.

### 3.8. RAG — Giga Embeddings

`giga_embeddings.py` уже имеет:

```text
auto / cpu / cuda
```

При `auto` выбирается CUDA при наличии, иначе CPU.

**Вывод:** без CUDA сценарий не ломается. AMD/Intel GPU всё равно не используются текущим PyTorch CUDA runtime, но CPU fallback штатный.

**Приоритет:** средний/низкий.

### 3.9. Утилита обработки изображений

Здесь ситуация заметно лучше:
- Real-ESRGAN — ncnn Vulkan;
- Real-CUGAN — ncnn Vulkan;
- SwinIR — `auto / cpu / cuda`.

**Вывод:** утилита обработки изображений в целом не имеет такой же архитектурной дыры, как основные сценарии.

## 6. Что нужно проверить Codex

Для каждого runtime/сценария отдельно установить:

1. Какие backend реально поддерживает upstream.
2. Какие backend реально входят в поставку ЛОПАТЫ.
3. Где код жёстко требует NVIDIA/CUDA/CUDA0.
4. Где CPU fallback существует.
5. Где fallback отсутствует.
6. Где можно использовать Vulkan.
7. Где возможен HIP/ROCm.
8. Где возможен DirectML/SYCL/OpenCL или иной Windows backend.
9. Как определяется доступная VRAM.
10. Что происходит при OOM.
11. Возможен ли partial offload GPU+RAM.
12. Какие зависимости и лицензии добавятся.
13. Какой будет размер поставки/обновления.
14. Что можно покрыть автоматическими тестами без физической AMD/Intel карты.
15. Что нельзя объявлять проверенным до реального железа.

## 7. Требование к архитектуре

Не создавать отдельный хаотический селектор устройства внутри каждого сценария, если этого можно избежать.

Нужен общий уровень аппаратных возможностей, условно:

```text
Hardware / Backend Capability Layer

NVIDIA GPU
    CUDA
    доступная VRAM
    compute capability

AMD GPU
    Vulkan
    возможно HIP/ROCm

Intel GPU
    Vulkan / SYCL — только если конкретный runtime поддерживает и проверен

CPU
    AVX2 / обычный x64 fallback
```

Конкретный runtime объявляет свои возможности:

```text
yue2.cpp
    CUDA / Vulkan / CPU

stable-diffusion.cpp
    CUDA / Vulkan / HIP / ... / CPU

llama.cpp
    поддерживаемые собранные backend / CPU

PyTorch workers
    отдельный набор доступных устройств
```

Сценарий должен запрашивать не `CUDA0`, а:

> **лучшее доступное совместимое устройство для данного runtime и текущего объёма работы.**

---

## 8. Важное правило документации

Всегда разделять четыре разных утверждения:

1. **Поддерживается upstream.**
2. **Поддерживается архитектурой ЛОПАТЫ.**
3. **Включено в текущую поставку.**
4. **Проверено на реальном физическом железе.**

Нельзя превращать upstream-поддержку в заявление «ЛОПАТА проверена на Radeon / RTX 50», если такого физического теста не было.

Для AMD и части новых GPU на первом этапе допустима формулировка:

> «поддержка реализована и покрыта автоматическими тестами, реальное железо ещё не проверено».

---

## 9. Текущее реально проверенное железо

На момент фиксации:
- RTX 4090 — основной подтверждённый GPU;
- RTX 4080 SUPER ранее использовалась в пользовательских проверках отдельных контуров;
- AMD GPU — физически не проверена ;
- RTX 30 — физически в текущем аудите не проверена;
- RTX 50 — физически в текущем аудите не проверена.

Отсутствие физического теста не должно автоматически запрещать backend, который штатно поддержан upstream. Нужно честно маркировать статус проверки.

---

## 10. Ключевой вывод

Музыкальный сценарий выявил более старую архитектурную проблему:

> **часть ЛОПАТЫ исторически проектировалась на тестовой NVIDIA-системе и местами фактически приравняла понятие «GPU» к «CUDA0».**

Это не требует немедленно переделывать всю программу одним большим патчем.

Правильный порядок:
1. закончить текущую правку YuE2;
2. после восстановления лимита Codex провести системный аудит;
3. сначала исправить критические CUDA-only места;
4. затем унифицировать выбор аппаратного backend;
5. только после этого продолжать крупное развитие музыкального направления.

Цель:

> **ЛОПАТА должна использовать доступное железо пользователя, а не требовать совпадения его ПК с машиной разработчика.**
При реализации и дальнейше работе отслеживать состояние лимита, при досиижение  1% безопасно уйти на паузу.
