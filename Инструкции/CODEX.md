## 2. Общий контекст проекта

AI_HUB — будущий русскоязычный локальный AI-хаб для Windows 11.

Ключевые ориентиры проекта:

- платформа: Windows 11;
- основной предполагаемый стек: C# / .NET / WPF;
- визуальная философия: Windows-проводник для локального ИИ;
- основное локальное ядро: Qwen3 8B GGUF Q4_K_M;
- пользовательский ввод: голос или файлы;
- навигация: кнопочное дерево решений;
- модель работы: локальные бесплатные модели и автоматически устанавливаемые backends;
- важные модули: AI-хранилище, паспорт ПК, каталог моделей, RAG-память, Backend Manager;
- лицензия проекта: GPL-3.0-or-later;
- пользователь не программист, поэтому решения объяснять просто.

Архитектурная концепция: AI_HUB строится как Codex-подобная рабочая среда для локальных моделей, но шире кодинга. Локальные модели могут быть слабее облачного Codex, поэтому программа не должна надеяться, что модель сама всё угадает. Вокруг модели нужен взрослый рабочий контур: инструменты, инвентарь возможностей, правила доступа, журналы действий, проверка фактов, планирование, откаты, понятные статусы и честное признание, когда данных или возможностей не хватает.

## 10. PowerShell 7 и Windows-ограничения

- Для сложных PowerShell-команд, диагностики, backup и проверок на Windows предпочитать `pwsh` / PowerShell 7.
- `powershell.exe` использовать как fallback или когда этого требует конкретный `.cmd`/`.ps1` сценарий.
- Если поведение кодировки кажется странным, сначала проверять, через какой shell реально идёт запуск.

Учитывать системные ограничения Windows:

- `CreateProcess` command line: максимум `32767` UTF-16 символов.
- `cmd.exe`: максимум `8191` символов командной строки.
- `MAX_PATH`: `260` символов для legacy-путей, если long paths не включены отдельно.

Эти лимиты не гарантируют, что большой патч реально пройдёт: PowerShell quoting, heredoc, tool wrapper и длинные workspace-пути могут уронить команду раньше.

## 11. Big patch safety

### HARD RULE

Не отправлять гигантские patch-body одним куском.

Опасными считать патчи, которые:

- визуально тянут на `600+` строк;
- смешивают несколько файлов;
- содержат длинные встроенные текстовые блоки;
- совмещают архитектуру, UI, миграции и тексты.

Никогда не пытаться отправлять одним куском patch-body на `1400+` строк.

Предпочтительная стратегия:

- один файл за раз;
- один логический блок за раз;
- маленькие патчи;
- после каждого крупного шага — проверка сборки или хотя бы синтаксиса.

Если правка начинает разрастаться:

- остановиться;
- разбить задачу на подпатчи;
- не повторять одну и ту же гигантскую команду.

## 14. AI_HUB: безопасность моделей, backends и инструментов

### HARD RULE

Модели и инструменты не должны получать бесконтрольный доступ к системе.

Правила:

- не удалять пользовательские результаты без явного подтверждения;
- не удалять закреплённые модели;
- не скачивать модели/backends без понятного подтверждения;
- не запускать скачанное без проверки источника и подтверждения;
- не менять системные настройки Windows без подтверждения;
- не выполнять shell/PowerShell-команды без подтверждения;
- не хранить secrets в коде и публичных документах;
- не давать модели прямой бесконтрольный доступ к файлам, интернету, shell или системным настройкам;
- все действия через инструменты должны проходить через permission layer и логирование.

### HARD RULE — зарезервированные голоса инструментов

- `Aleksandr` и `SLT` остаются общими RHVoice-профилями ядра во всех сценариях.
- Только исполнитель «Режима неопределённости» по текущему решению использует RHVoice-профили `Elena` и `BDL`.
- Ни один инструмент другого сценария не должен получать `Aleksandr`, `SLT`, `Elena` или `BDL` без прямой просьбы пользователя.
- Не переносить это ограничение на ядро: оно вправе использовать свои `Aleksandr` и `SLT` во всех текущих и будущих сценариях.

## 15. AI-хранилище и результаты

Учитывать утверждённые продуктовые правила:

- модели можно скачивать и удалять по политике, потому что их можно скачать заново;
- закреплённые модели защищены от автоудаления;
- временные модели могут быть кандидатами на удаление;
- результаты пользователя удалять только вручную или по прямому запросу пользователя;
- дисковые лимиты могут быть мягкими или жёсткими;
- лимит AI-хаба не равен всему свободному месту на диске;
- перед крупным скачиванием показывать прогноз места.

При изменении хранения обязательно учитывать:

- модели;
- временные модели;
- результаты;
- backends;
- кэш;
- индексы документов;
- логи;
- RAG-базу.

## 16. RAG и память

Общая RAG-база — память всей системы, а не только ядра.

Она может хранить:

- знания о пользователе;
- знания о ПК;
- знания о моделях;
- знания о backends;
- историю сессий;
- ошибки и способы лечения;
- результаты интернет-поиска;
- документацию технологий;
- правила работы;
- предпочтения пользователя;
- опыт инструментов;
- прошлые решения.

Каждая запись должна иметь паспорт происхождения:

- кто внёс запись;
- какая модель или инструмент;
- при каких обстоятельствах;
- в какой сессии;
- по какой задаче;
- какие источники;
- уровень доверия;
- тип записи;
- может ли запись влиять на будущие решения.

Модели могут предлагать записи, но не должны молча менять фундаментальные правила.

## 17. Система правил AI_HUB

Правила делятся на три уровня.

### 1. Фундамент

Жёсткие правила внутри кода:

- не удалять результаты без разрешения;
- не удалять закреплённые модели;
- не выполнять опасные команды без подтверждения;
- не обходить жёсткие лимиты;
- не менять системные настройки без подтверждения.

### 2. Кости

Правила конкретных задач и сценариев:

- как искать модели;
- как подбирать модель;
- как вести кодинг-задачу;
- как работать с картинками;
- как строить дерево;
- как вести интернет-поиск.

Их можно развивать вручную или по предложению ядра, но не менять молча.

Для сценариев маршрутизации AI действует отдельный принцип:

> Сценарное ядро строит профиль AI-исполнителя, а не проводит предметное интервью вместо него.

Каждый динамический вопрос должен структурированно менять хотя бы один параметр выбора модели, инструментов, backend, контекста, нагрузки или режима выполнения. Недостающие предметные детали после маршрутизации выясняет рабочая модель.

### 3. RAG-правила

Контекстные правила и выводы из базы знаний.

Приоритет:

```text
Фундамент сильнее Костей.
Кости сильнее RAG.
RAG уточняет, но не перебивает верхние уровни.
```

## 18. Глобальная кнопка “Сохранить результат...”

В программе утверждена глобальная команда:

> Сохранить результат...

Она доступна в любой момент и обращается к той ИИ-модели, инструменту или системе, которая активна прямо сейчас.

Активная ИИ формирует предложение записи, пользователь подтверждает, и запись уходит в RAG с паспортом.

Нельзя сохранять важные правила молча без подтверждения пользователя.

## 19. Интернет-инструменты

Интернет для ядра — это инструмент хаба, а не свободное блуждание модели.

Базовая схема:

```text
модель решает, что нужен поиск
↓
хаб вызывает web/search/open-page инструмент
↓
хаб возвращает извлечённые данные
↓
модель анализирует
```

Правила:

- если интернет не нужен, программа должна жить офлайн;
- web-поиск должен логироваться;
- использованные источники должны сохраняться в интернет-память/RAG;
- скачивание файлов требует подтверждения;
- внешний браузер можно использовать для ручного открытия источника;
- browser automation — отдельный будущий режим, не базовый путь.

### HARD RULE

При повторном баге сначала искать совпадения в:

- `H:\AI_HUB\Документы_проекта\КАТАЛОГ_ПОВТОРЯЕМЫХ_БАГОВ.md`

Искать по:

- `[BUG:...]`
- `[TAG:...]`
- `[FIX:...]`
- `[PROC:REPEATED-BUG-RECOVERY]`

Процедура:

1. Найти похожий баг.
2. Сверить внешний симптом.
3. Проверить, что реально сломано: данные, логика, рендер, transport, storage, права или backend.
4. Проверить, не был ли утрачен старый fix.
5. Если совпадение подтверждается, сначала возвращать канонический fix минимальным патчем.
6. Только если симптомы не совпали, искать новый root cause.
7. После подтверждённого лечения обновить каталог.

## 22. Версионирование и релиз

### HARD RULE

Вести строгую нумерацию версий проекта.

Начальный формат версии:

```text
0.X.Y
```

При создании каждого нового полноценного пользовательского сценария повышать среднюю цифру `X`. Первый полноценный сценарий `Анализ изображений` переводит проект на `0.1.0`; после такого повышения счёт небольших исправлений и улучшений этого сценарного этапа начинается с `Y = 0`.

При последующих кодовых правках повышать `Y`, если проект уже вошёл в фазу версионируемых сборок.

Номер версии нельзя менять молча или задним числом без записи причины.

Перед релизом или публичной сборкой фиксировать:

- номер версии;
- тип релиза;
- состав изменений;
- проверенные артефакты;
- hash релизного артефакта, когда появится установщик или сборка.

При изменениях зависимостей, backends, моделей, установщика, схемы хранения или формата данных обновлять `REESTR.md` и релизные заметки.

Перед релизом явно определить тип:

1. `app-only patch` — меняется только приложение.
2. `backend/tooling update` — меняется backend, инструмент, модельный каталог или установщик backend-а.
3. `full release` — меняется несколько частей.
4. `experimental build` — сборка для проверки идеи, не считается стабильным релизом.

Не публиковать release/update-feed, если соответствующий артефакт реально не собран и не проверен.

### HARD RULE — один источник версии

По возможности держать одну истину о версии программы.

Новые элементы, которые показывают или используют версию, должны читать её из основного источника версии проекта, а не хранить отдельную ручную копию.

Это относится к:

- UI;
- окну About;
- статусным строкам;
- установщику;
- updater/update-feed;
- release notes;
- диагностике;
- логам;
- будущим модулям и backend-интеграциям.

Если по технической причине нужна временная копия версии, нужно явно описать причину, способ синхронизации и место проверки.

## 23. Установщик

Пока конкретный установочный контур не выбран, не фиксировать MSI/NSIS/WiX/MSIX как окончательное решение.

При появлении установщика:

- собрать отдельную инструкцию;
- не смешивать dev-сборку и public-release;
- для dev/test-сборок допустима установка в `%LOCALAPPDATA%\Programs`, чтобы не требовать права администратора;
- перед публичным релизом обязательно отдельно пересмотреть режим установки: вариант `для всех пользователей`, путь `C:\Program Files\AI HUB`, необходимость прав администратора, uninstall-поведение и миграцию настроек;
- фиксировать путь артефакта;
- фиксировать hash;
- фиксировать rollback;
- не запускать установщик без явного разрешения пользователя;
- не собирать тестовый установщик автоматически после каждого ТЗ.

Сборку установщика выполнять только по прямой команде пользователя. Исключение: тест установленной версии критичен для задачи, например проверяется сам установщик, uninstall, ярлыки, путь установки, перенос настроек или ошибка проявляется только в установленной сборке.

Если установщик не собирался, в истории и финальном ответе явно фиксировать: обычные проверки прошли, установщик не пересобирался по правилу.

### HARD RULE — публикация установщика только по отдельной явной команде

Сборка установщика и публикация в GitHub Releases — отдельные действия. Публиковать установщик и соответствующий update-feed только по явной команде пользователя на публикацию. Команда может сразу разрешать сборку и публикацию; повторное подтверждение тогда не требуется.

Успешная сборка, тестирование, приёмка или закрытие ТЗ, а также обязательный commit/push исходников при архивировании ТЗ сами по себе не разрешают публикацию установщика. Исключение, разрешающее необходимую тестовую сборку, не разрешает её публикацию. Пользователь может собирать установщики для проверки до исправления багов.

Внутренняя версия остаётся `-dev`. Публичный тестовый установщик выпускается с суффиксом `-beta`, без дополнительных цифр после beta; dev-установщики не публикуются. Публиковать только выбранный и проверенный артефакт, без известных явных багов, через отдельный `Инструменты/publish-installer.ps1`. Обычная сборка, включая `-PublicBeta`, ничего не публикует; `-Publish` применяется только при наличии указанной команды пользователя.

Установщики хранятся как вложения GitHub Releases. Политика хранения: первый установщик текущей линии major.minor и два последних (2–3 уникальных установщика). Очистку выполнять отдельным явным действием по руководству, а не побочным эффектом сборки или commit/push. Порядок проверки, публикации, продолжения черновика и очистки: [Обновления и публикация](../Документы_проекта/ОБНОВЛЕНИЯ.md).
