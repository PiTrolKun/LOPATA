# RAG, диалоги и единая папка проекта — 2026-09-11

Версия 0.1.89-dev. Реализация передана на пользовательскую проверку; ТЗ не закрыто. Установщик не пересобирался, публикации нет.

## Что изменено

- Проектные тексты, оригиналы, физический Qdrant, подготовка индекса, поисковые кэши, диалоги и диагностика находятся внутри проекта.
- `storage.json` версии 2 фиксирует организацию папок. `project.json` и индекс глав сохраняют прежнюю версию 1 и идентификаторы.
- `chapters` — рукопись; `Materials` — копии оригиналов; `Rag/Source` — оригинал; `Rag/Work` — версии завершённых частей; `Rag/Qdrant` — физическая база; `Rag/Queries` — векторы запросов; `Rag/Staging` — подготовка; `Dialogs/Writer` и `Dialogs/Advisor` — переписки; `Diagnostics`, `Exports`, `Jelly` — журналы, экспорт и резерв будущей памяти.
- Общими остаются веса, исполняемые компоненты, лицензии, настройки и реестр адресов. Старые проектные чаты, которые прежняя версия не сохраняла, восстановить нельзя.
- Во время индексации блокируются действия и отправка; можно набирать сообщения. После ошибки возвращаются действия и кнопка повтора. Escape и F12 не обходят блокировку; закрыть приложение можно.
- Завершённая часть индексируется после перехода к следующему файлу. Текущий файл остаётся предварительным и поступает обеим ролям свежим снимком. Обычное автосохранение не запускает индексацию.
- До трёх попыток при сбое embedding-worker. Отмена и постоянные ошибки диска не повторяются. Записанные строки имеют идентификатор исходных данных; оборванный хвост восстанавливается, повреждение середины не скрывается.
- Qdrant запускается для операции и освобождается после неё. Запросы Giga выполняются на CPU, индексация — auto GPU/CPU; временный embedding-процесс завершается. Веса Runeweaver и последовательность двух ролей сохранены.
- Полная переписка лежит на диске. Writer не получает старые ответы автоматически; Advisor получает беседу в пределах бюджета. Незавершённые ответы помечаются, неотправленный ввод восстанавливается; очистка одной роли не затрагивает другую.
- Первоисточник и собственная история имеют разные метки и операции чтения. Найденные фрагменты сверяются с текстом и актуальной версией. Поиск возвращает короткие выдержки с адресами полного чтения; модель не получает произвольный доступ к файловой системе.

## Реальные ответы Runeweaver: успехи и ограничения

- `models-01`: Advisor увидел сначала синий конверт, затем ручную замену на зелёный ключ. Writer продолжил именно новую версию; художественная формулировка не оценивалась как безошибочная.
- Первоначальный буквальный поиск полного вопроса дал пустую выдачу; затем top-5 семантических совпадений застревал на сцене визита к графине. В `retrieval-02` три повторения подтвердили проблему. Добавлен семантический вариант многословного запроса, выбор разных разделов из top-16.
- После расширения `retrieval-03`: Advisor 3/3 назвал тройку, семёрку и туза.
- Первоначально большой объём выдержек не помещался в бюджет Writer. В `writer-01` нужные материалы вытеснялись. Теперь выдержки до 900 символов с точными адресами и возможностью дочитать; старые реплики Advisor освобождают место раньше актуальных источников.
- Финальная компактная выдача: `retrieval-04` — 2/3 правильных ответа Advisor; в одном ответе модель отрицала названия карт. `writer-03` — 2/3 правильных, в третьем смешал выигрышного туза с дамой из финала. В `writer-02` такая же смысловая ошибка. Проверка исходящего запроса `writer-02` подтвердила: цитата с тройкой, семёркой и тузом реально передана, `omittedSourceBlocks=0`.
- Это известная граница качества текущей модели при сопоставлении нескольких событий, а не обещание, что RAG устраняет ошибки. Нельзя считать отсутствие подходящего ответа доказательством отсутствия факта в книге. Новый проход с вопросом пользователя и чтением указанного раздела остаётся полезным.

Не подстраивались роли, параметры повторов или модель под конкретную книгу; названия карт не зашиты в программу. Новые веса/компоненты не скачивались.

## Ресурсы короткого запроса

Один контроль CPU и один CUDA при уже загруженной Runeweaver (`resources-01`). ПК: i9-13900KF, 128 ГБ RAM, RTX 4090 24 ГБ. Это наблюдения конкретного запуска, не универсальный benchmark.

| Giga query | Полный запуск worker | Пик рабочего набора RAM процесса | Пик выделений PyTorch на GPU |
|---|---:|---:|---:|
| CPU, до 4 потоков | 4,338 с | 2,76 GiB | 0 |
| CUDA | 4,534 с | 1,46 GiB | 0,91 GiB |

Private Bytes были 4,75/4,12 GiB соответственно: это выделенное адресное пространство/commit, его нельзя прибавлять к рабочему набору как ещё одну физическую RAM. PyTorch-счётчик не включает все выделения драйвера. Выбран CPU для коротких поисковых запросов: в этом контроле GPU не сократил полное время и занимает видеопамять рядом с основной моделью. Повторный идентичный запрос использует проектный векторный кэш; процесс Giga постоянно не висит.

## Повтор проверки

`dotnet run --project Тесты/LiteraryMemory/Probe.csproj -- fixture <новая-папка>` — отдельные контрольные проекты; никогда не удаляет переданный пользовательский проект.

Режимы `models`, `retrieval`, `writer-rag`, `resources` требуют третьим аргументом путь проекта; `migrate` действительно выполняет миграцию. `wpf` проверяет интерфейс без генерации. Выходная папка должна быть новой. Детали нельзя интерпретировать по одному коду завершения: для генерации читать case-*.json и фактические запросы.

Подготовка оригинала до подтверждения проекта резервирует выбранную папку; после прерывания она может остаться с `.creation`, чтобы её содержимое не потерялось. Это данные внутри выбранной материнской папки. Для продолжения нужно использовать те же адрес и имя. Экспорт по явному выбору пользователя за пределы проекта остаётся самостоятельной внешней копией.
