# Подготовка раздельного сохранения вокала и инструментала

Дата: 21.10.2026. Исходники: 0.5.106-dev.
Связь: [ТЗ трёх музыкальных этапов](../../ТЗ/Архив/2026-10-21_Музыка_раздельное_сохранение_каверы_MIDI.md).
Статус: исследованы код/документация/метаданные; физическое разделение не запускалось.

## 1. Вывод для реализации

Одна галочка реализуема как общий этап обработки PCM после любого подходящего
генератора. Для основной пары не нужны два разных разделителя. Из уже используемой
Studio можно взять готовую основу HT-Demucs/ONNX; это не ещё один генератор песен.
В ЛОПАТЕ пока нет подключённого worker/модели/состояния для этого этапа.
Главные интеграционные задачи — сохранность PCM, восстановление комплекта файлов
и синхронное воспроизведение двух ролей. Нужна штатная управляемая доставка
недостающих компонентов. Уточнённый контракт пользователя: отдельная папка на
песню/вариант с голосом, музыкой и TXT (текст, параметры, измеренные тайминги);
одна карточка; ПКМ по воспроизведению — «Голос / Музыка / Вместе».
Механика по умолчанию выключена; перед последующей генерацией с включённым
разделением нужен вопрос, оставить ли его включённым (не при продолжении задания).
Текущий режим плеера виден на самой кнопке: 🎤 голос / 🎼 музыка / 🔊 вместе;
по умолчанию вместе. Новые значки/меню только у двухслойного результата;
для обычных файлов плеер остаётся прежним независимо от галочки генерации.
Копирование во всех режимах двухслойной песни переносит всю её папку.
Третьего постоянного полного микса этот режим не требует. Общая часть метаданных
одинакова у всех файлов, индивидуальная роль явно обозначена.

## 2. Что подтверждено в нашем коде

| Место | Наблюдение | Последствие |
|---|---|---|
| `Services/MusicGenerationRunner.cs` | Синтез создаёт проверенный WAV и AudioHash; затем `MusicOutputPublisher`; после Completed временный AudioFile удаляется | Разделение нельзя вставлять после очистки и незаметно питать MP3; нужно отдельное состояние/контракт очистки |
| `Services/MusicGenerationJobs.cs` | Есть Plan/Audio/Result hashes, AdditionalPath/Hash, Completed и KaraokeReadiness; полей разделения нет | Не переиспользовать Completed или AdditionalPath для другой роли; добавить необязательный блок с миграцией false |
| `Models/MusicProject.cs` | Snapshot хранит output, wishes, expert, LoRA и отправленный job | Новый флаг фиксируется в проекте/задании, старые записи не включают его автоматически |
| `Controls/MusicOutputControl.cs` | Есть форматы, битрейт, «+» и адаптивная раскладка | Галочка рядом с битрейтом, второй формат остаётся отдельной настройкой |
| `Services/MusicOutputSettings.cs` | Output preferences сохраняются между запусками | Проектный флаг разделения не должен случайно стать глобальным default из-за размещения в том же UI |
| `Controls/MusicGenerationSession.cs` | Обычный запуск снимает текущие настройки, RepeatAsync восстанавливает прежние и ABC, recovery использует job | Флаг/receipt участвуют в том же снимке; повтор разделения не запускает новый музыкальный синтез |
| `Services/MusicAudioEncoder.cs` | Кодирование с тегами/обложкой и проверкой, несколько форматов | Использовать для двух ролей, без отдельного кодировщика и без lossy-цепочки |
| `Services/MusicSongMetadata.cs` | Фактические generator/runtime/seed/LoRA/engine set уже записываются | Дополнить ролью и разделителем, не потеряв исходную музыкальную модель |
| `Controls/MusicTracksControl.cs` | Одна карточка на вариант и выбор дополнительного формата | Комплект остаётся одной песней, роли не создают дополнительные карточки |
| `Controls/MusicPlayerControl.cs` | Play вызывает RequestPlayback; Select открывает track.Path, Save копирует этот же файл | Добавить ПКМ-выбор трёх режимов и значок на самой кнопке; хранить ссылку на комплект, копировать всю папку независимо от прослушивания |
| `Services/MusicAudioPlayer.cs` | IMusicAudioPlayer.Open принимает один путь; работает один WPF MediaPlayer, с временным PCM при декодировании | «Вместе» требует общей шкалы. Минимальный кандидат — временный PCM суммы дорожек через FFmpeg и прежний один плеер; это не третий постоянный результат |
| `Models/MusicTimedLyrics.cs` | AudioPayloadHash и Clock.SourcePayloadHash связывают тайминги с конкретным аудио | TXT ссылается на источник измерений; нельзя копировать идентичность полной записи в дорожки без корректного контракта привязки |
| `Services/MusicStudioLease.cs` | Наш lease запускает/проверяет engine и service; dispose завершает принадлежащие процессы | Для ACE нельзя слепо переиспользовать lease, требующий YuE2. Разделение должно работать без его весов |
| `Services/MusicStudioOutput.cs` | Studio float после нормализации переводится через FLAC в прежний PCM16/48 kHz | Не заявлять, что текущий промежуточный WAV — неизменённый float-мастер модели; использовать фактический общий PCM |
| `Services/MusicLyricsWorkerProcess.cs`, `MusicLyricsDevicePolicy.cs` | Есть owned process, вывод, отмена, offline launch и аппаратный CPU retry | Полезный образец жизненного цикла, не повод менять рабочий ASR runtime ради разделителя |

Пути выше относительно `Исходники/AIHub`. Atlas outline использован для навигации;
индекс C# имеет partial coverage без call relationships, выводы проверены прямым
чтением файлов. Существующий gate таймингов не отменять ради новой постобработки.
Восстановление таймингов/метаданных (`MusicLyricsTimingStore`,
`MusicLyricsTimingMetadata`) нужно согласовать со всем комплектом и TXT.
Отсутствующий результат измерений явно отмечается, не заполняется оценкой модели.

Для проигрывания суммы проверить задержки декодирования, общий gain без клиппинга,
сохранение позиции/паузы при смене режима и отмену подготовки старого источника.
Два независимо стартующих MediaPlayer без синхронизации не подходят. Временный
кэш должен проверяться по хешам актуальных дорожек и очищаться; вычисление
совместного звука не требует повторного запуска разделителя.

## 3. Готовая основа закреплённой Studio

В engine set 002 используется Studio source
`c3e214f3a65f3f56c18e107127ebd2ebad5150ad`.
Его [separation.rs](https://github.com/timoncool/YuE2-Studio/blob/c3e214f3a65f3f56c18e107127ebd2ebad5150ad/crates/music-server/src/separation.rs)
содержит готовое ONNX-разделение перекрывающимися окнами, прогресс и отмену
между окнами. Граф: 44,1 kHz stereo, 343 980 samples, overlap 0,25; выходные
роли drums/bass/other/vocals/guitar/piano. Число сохраняемых ролей не убирает
вычисление остальных. Это не гарантия качества конкретной песни.

[Headless API](https://github.com/timoncool/YuE2-Studio/blob/c3e214f3a65f3f56c18e107127ebd2ebad5150ad/crates/music-server/src/lib.rs)
содержит `/v1/separation/status`, `/v1/separation/settings`,
`/v1/library/import`, `/v1/library/songs/{id}/stems` и чтение дорожки.
Это возможный путь переиспользования. Однако штатный путь связан с внутренней
библиотекой/настройками/загрузчиком Studio; его writer сохраняет отдельные PCM16
дорожки. Наша задача требует управляемых файлов, суммирования accompaniment до
clipping и готовности без чужого генератора. Поэтому готовность API нельзя
приравнять к готовности адаптера ЛОПАТЫ.

Проверенный рецепт `Инструменты/MusicStudio/prepare-3.6.ps1` переносит сервер,
engine и лицензии, но не готовит отдельную модель HT-Demucs/ONNX Runtime.
В проверенной dev-папке Studio нет отдельного onnxruntime DLL. Отсутствие
в этой папке не доказывает отсутствия библиотеки на всём ПК; использовать
случайную системную DLL всё равно нельзя.

## 4. Кандидат модели и доступность

Первичный источник — [карточка ONNX-экспорта](https://huggingface.co/StemSplitio/htdemucs-6s-onnx/tree/49df9b6989cf2150840ea65b0bef77a2e471b678).
Метаданные Hub на дату проверки: public, gated=false, license=mit,
revision `49df9b6989cf2150840ea65b0bef77a2e471b678`.
Файл `htdemucs_6s_fp16weights.onnx`: 136 428 532 B;
LFS SHA256 `7ce55792e2231c93fbf92de95f5fd5b3a5e6c89f7db690dfd693e8f1dce56869`.
Публичный API и HEAD-проверка доступны без авторизации. Сам бинарник не скачан,
его содержимое/выполнение не проверено. FP16 здесь — хранение весов; вход/выход
reference inference float32, меньший файл не обещает меньшую runtime-память.

Авторский `infer.py` содержит готовый путь с NumPy/ONNX Runtime без PyTorch.
Технические детали экспорта/качества в model card — заявления автора, не наши
измерения. В репозитории нет отдельного LICENSE-файла; опубликованные MIT-условия
есть в card/README. При упаковке сохранить точные условия/атрибуцию и проверить
всю цепочку, не объявлять комплект уже прошедшим лицензионную приёмку.

## 5. Runtime и оборудование

ONNX Runtime описывает разные [execution providers](https://onnxruntime.ai/docs/execution-providers/),
но поддержку графа нужно проверять отдельно. В закреплённой Studio функция
`separates_on` разрешает CUDA, а для остальных устройств оставляет CPU:
DirectML конкретно для HT-Demucs отключён с пояснением автора о памяти/скорости.
Это наблюдение upstream, не собственный замер ЛОПАТЫ и не общий запрет DirectML.

План: CPU fallback для совместимых Windows x64, CUDA при совместимых provider,
драйвере/устройстве и доступной памяти. AMD/Intel не получают CUDA-комплект;
CPU путь остаётся. Не измерять ресурсы всей игры/видеокарты как ресурсы worker.
Разделитель и генератор не занимают VRAM одновременно без необходимости.
Статусы «upstream / внедрено / доставляется / физически проверено» раздельны.

## 6. Выбор обвязки — первый инженерный проход реализации

1. Проверить, позволяет ли штатный headless путь Studio обработать управляемый
   PCM без загрузки модели YuE2, без своего сетевого downloader и с корректным
   формированием вокала/суммы сопровождения до integer-clipping.
2. Если да — использовать готовые маршруты с отдельным owned lease/явными путями.
3. Если нет — минимальный изолированный worker вокруг готового ONNX-алгоритма
   Studio либо reference inference экспортера, без нового разделяющего алгоритма.
   Причину адаптации и точную основу зафиксировать. Не тянуть всю Studio UI,
   Python/PyTorch-экосистему и генеративные веса ради одной операции.

На подготовке не выполнялись сборка/проверка этих путей, поэтому конкретная
обвязка и окончательная версия ONNX Runtime ещё не признаны выбранным комплектом.
Перед продуктовой интеграцией: pinned sources, runtime ABI/provider, SHA256,
полные notices, штатная лицензия/докачка и локальный контракт без скрытой сети.

Резервный вариант — официальный [Demucs](https://github.com/facebookresearch/demucs):
есть двухфайловый режим vocals/no_vocals, CPU и PyTorch API. Его README прямо
указывает, что two-stems не экономит полное вычисление модели. Оригинальный
репозиторий архивирован; requirements_minimal содержит torchaudio <2.1, тогда как
наш музыкальный стек использует 2.10. Нельзя устанавливать его поверх ACE/ASR
без отдельной проверки. Это причина предпочесть готовый ONNX-путь первым,
а не менять исправные окружения. Резервные веса также не скачивались.

## 7. Осталось проверить при реализации

- Реальный короткий проход CPU и доступного GPU, включая конец окна/переходы.
- Формирование двух ролей до clipping, политика headroom и длительность.
- Минимальная обвязка без весов другой музыкальной модели и скрытых загрузок.
- Состояния задания при сбое/отмене и сохранность native PCM для повтора.
- Папка на вариант, два аудиофайла и TXT, второй формат обеих ролей;
  общая часть встроенных метаданных и отдельная роль у каждого файла.
- Одна карточка, ПКМ-выбор и значок режима на кнопке, совместное воспроизведение
  без дрейфа, сохранение позиции при смене режима, копирование всей папки
  в каждом режиме без нового экспорта микса.
- Подтверждение сохранения включённого флага перед последующей генерацией;
  отдельный снимок нового запуска, отсутствие вопроса при продолжении задания.
- Измеренные тайминги/явные пропуски в TXT, корректные payload-привязки;
  отсутствие регрессии караоке/повтора и обычных результатов без разделения.
- Полный комплект доставки и лицензии, а не только модельный MIT-тег.

Локальные прочитанные исходники/карточка для подготовки находятся в
`_tmp/music-stems-research-20261021/`. Это диагностические материалы, не часть
поставки. Запусков моделей, установки пакетов, скачивания весов, нагрузочных
измерений или пользовательских изменений приложения на этом этапе не было.
