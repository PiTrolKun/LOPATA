# Коллекция произведений ЛОПАТЫ в Проводнике Windows

**Рабочее ТЗ от 09.11.2026. Статус — выполнено и принято пользователем 09.11.2026.** Исследование проведено на 0.7.64-dev; реализация проверена в 0.7.65-dev. Готовность функции определяется испытаниями из раздела 6. [Исходная идея от 17.10.2026](LOPATA_Идея_интеграции_в_Проводник_Windows_2026-10-17.md).

## 1. Что получает пользователь

Пользователь сохраняет песню и рисунок в привычные папки, в том числе на разных дисках. После включения интеграции в левой области навигации обычного Проводника Windows 11 появляется постоянный самостоятельный раздел **«ЛОПАТА»** со значком приложения. Ориентир по размещению и поведению — раздел «Яндекс Диск» на показанном пользователем экране. Приёмке подлежит отдельная строка дерева на этом уровне. Конкретное соседство и порядок строк определяет Windows.

**При щелчке по «ЛОПАТЕ» справа в той же вкладке сразу видны все найденные пользовательские работы, созданные в ЛОПАТЕ:** документы, книги, таблицы, презентации, изображения, аудио, видео, проекты и другие сохранённые результаты. Для корня используется общий запрос без ограничения по типу файла или сценарию. Группировка меняет только расположение элементов. Категории — это сворачиваемые заголовки в правой панели, как на примере пользователя. Под каждым заголовком видны относящиеся к нему файлы. Щелчок по стрелке заголовка сворачивает или раскрывает только эту группу. Всё это время слева выбрана «ЛОПАТА», а в адресной строке открыта та же коллекция. Каждый элемент ведёт к оригиналу в его папке.

Принадлежность устанавливается по служебной отметке программы-создателя в метаданных формата или в связанном потоке файла NTFS. Правило действует для результатов ручных и модельных операций. Одна и та же операция экспорта должна работать для будущих моделей без перечисления их имён. Пометка происхождения относится к файлу, не удостоверяет личность автора и не подменяет его. Название песни, имя автора, путь, слова в тексте, расширение проекта и существование соседнего JSON сами по себе ничего не доказывают. Для формата и носителя без метаданных допускается точная локальная квитанция успешного экспорта с SHA-256, размером и проверкой неизменности файла; адресной записи без такого подтверждения недостаточно. Техническое основание и ограничения этого дополнения приведены в разделе 8.

ЛОПАТА объединяет подтверждённые локальные результаты и находки Windows Search. Проводник показывает общую коллекцию и выполняет операции с правами текущего пользователя. Собственная база файлов, постоянный процесс наблюдения, сканирование всех дисков, облачная синхронизация и отдельное окно-библиотека находятся за пределами задачи. Просмотрщик метаданных можно вызывать существующим способом независимо от коллекции.

**Приоритет поиска.** В первую очередь важны работы, сохранённые после появления коллекции. Пользователь должен увидеть новую работу в обычной папке сохранения и суметь найти её после переноса в другую доступную для поиска папку. То же относится к файлу, принесённому с другого ПК с ЛОПАТОЙ. Старые работы можно показывать, если данные позволяют надёжно установить их происхождение. Полнота архива прежних версий не служит условием выпуска.

## 2. Что удалось проверить

Компьютер проверки — Windows 11 25H2, сборка 26200.9711, служба WSearch работала. В отдельную локальную папку с нейтральным именем поместили копии реальных результатов из тестовых материалов проекта и два контрольных файла. Область индексации не меняли. Windows Search OLE DB по условию DIRECTORY вернул все восемь файлов. Отдельно прочитали свойства через Shell и выполнили запросы к SystemIndex, ограниченные этой папкой.

| Файл в стенде | Встроенная запись или назначение | Что показала Windows |
|---|---|---|
| seven.png, экспорт 0.3.28-dev | PNG iTXt Software равен LOPATA, отдельная запись LOPATA содержит Program и ProgramVersion | System.ApplicationName равен LOPATA, System.Kind равен picture. Точное условие вернуло этот файл |
| four.png, экспорт 0.7.25-dev | Software содержит имя приложения, версию и набор движков | Значение System.ApplicationName — `LOPATA 0.7.25-dev; engine set 002 (2026-10-18)`. Его полное точное значение вернуло только этот PNG. Простое равенство LOPATA его пропустило |
| one.mp3, two.opus, three.flac | Независимое чтение через поставляемый ffprobe показало LOPATA_JOB, LOPATA_MODEL, LOPATA_VERSION и producer. MP3/Opus — 0.5.107-dev, FLAC — 0.5.97-dev | У всех System.Kind равен music. System.ApplicationName пуст, обе проверки точного имени программы их пропустили |

Контрольный запрос вида `SELECT System.FileName, System.ApplicationName FROM SystemIndex WHERE DIRECTORY='<file URL тестовой папки>'` подтверждал наличие образцов. Добавление `AND System.ApplicationName = 'LOPATA'` дало ровно seven.png. Отдельный запрос к LOPATA_VERSION как к колонке каталога завершился кодом 0x80040E55 (неизвестная колонка). Вне стенда среди точных совпадений были также PNG и WebP. В одном таком WebP независимо найдена XMP-запись ЛОПАТЫ. Это сведения об отдельных файлах и установленных обработчиках.

Воспроизводимые исходники корпуса: PNG с именами `2683cbf6ecc94d2497650462044f1f59_0.png` и `001a29de209e480784c6ff902dfc1d7b_0.png` из `Тесты/1/ImageGeneration`, пара music.mp3/music.opus из `Тесты/MusicStemsStand/physical-final-0107`, FLAC из `Тесты/MusicLoraLifecycle_20261021_065511/studio-065915/result`, DOCX из `Тесты/BookConverterStand/integration-output-01/docx`. Для повторения использовать копии, зафиксировать SHA-256 и не публиковать содержимое пользовательских работ.

**Отдельная проба для новых MP3.** Из одного синтетического короткого звука подготовили три ID3v2.3-файла. В первом записали стандартный кадр TENC со значением LOPATA, во втором то же значение было только в пользовательском TXXX:ENCODED-BY, в третьем метки не было. После появления всех одиннадцати файлов в SystemIndex условие `System.Media.EncodedBy = 'LOPATA'` вернуло ровно первый MP3. Совместный запрос нашёл ровно два файла — seven.png и only-tenc.mp3. У FLAC с аналогичными тестовыми тегами Shell показал в EncodedBy значение Lavf62.12.103, у Opus — пустое. [System.Media.EncodedBy](https://learn.microsoft.com/en-us/windows/win32/properties/props-system-media-encodedby)

Предикат совместной пробы, добавленный к ограничению папкой:

```sql
(System.ApplicationName = 'LOPATA'
 OR (System.FileExtension = '.mp3' AND System.Media.EncodedBy = 'LOPATA'))
```

В текущем AudioConversionMetadata.Id3 неизвестный ключ записывается как TXXX. Для MP3 первым испытать соответствие encoded_by ↔ TENC в штатном чтении и записи. Применять его к экспорту ЛОПАТЫ, где приложение действительно выполнило кодирование. Служебные подробности о версии и фактическом кодеке сохраняются в своих полях. Итоговая проверка должна пройти на файле обычного экспорта через интерфейс. Расширение в этом запросе ограничивает область действия правила TENC и само по себе совпадения не даёт.

**Окно Проводника.** Через локальный URI `search-ms:` с каноническим AQS `System.ApplicationName:="LOPATA"` и параметром `crumb=location:` для тестовой папки открылось штатное окно с единственным оригиналом seven.png. Отдельно проверенный файл описания .search-ms Shell распознал как объект сохранённого поиска, но перечисление через BHID_EnumItems вернуло E_INVALIDARG. При первом открытии URI у представления было System.Null. После установки GroupBy для конкретного окна появилась группа «Изображение». Повторное открытие того же URI в другом окне вернуло тот же файл и восстановило System.Kind. Исходный вид после теста восстановлен. Для варианта с файлом .search-ms повторное открытие и группировка остаются отдельным условием приёмки. [Интерфейс представления Проводника](https://learn.microsoft.com/en-us/windows/win32/api/shldisp/nn-shldisp-ishellfolderviewdual3)

В итоговой проверке открыт локальный URI составного запроса. Его параметр query до кодирования — `(System.ApplicationName:="LOPATA" OR (System.FileExtension:=".mp3" AND System.Media.EncodedBy:="LOPATA"))`. Штатный Проводник из 11 образцов показал только seven.png и only-tenc.mp3 в двух группах «Изображение» и «Музыка». Вызов — ShellExecute зарегистрированного URI, в .NET через ProcessStartInfo с UseShellExecute=true. В рабочей реализации создавать URI из известных свойств и локальных разрешённых расположений. Этот эксперимент подтверждает состав выдачи. Постоянный узел и его представление в существующей вкладке проверяются в этапе 3. Локальные диагностические протоколы сохранены в `_tmp/explorer-collection-research/shell-uri-trials.json` и `shell-uri-media.json`.

### Гибридный поиск произведений

Решение пользователя от 09.11.2026: коллекция объединяет два источника. Первый использует известные папки результатов и сведения об успешных локальных сохранениях. Второй находит помеченные файлы в доступных индексируемых расположениях, в том числе после переноса или создания на другом ПК. Узел «ЛОПАТА» показывает общую выдачу, сгруппированную внутри правой панели. Остаются инженерными решениями способ хранения локальной истории и выбор поискового поля для каждого формата.

| Состав гибридного поиска | Что даёт | Что проверить при реализации |
|---|---|---|
| Сначала искать в известных местах сохранения | Взять все настроенные `Results.Locations` из [StorageSettings](../../Исходники/AIHub/Models/StorageSettings.cs), настройки музыки, генерации изображений и захвата из [AppSettings](../../Исходники/AIHub/Models/AppSettings.cs), а также доступные конечные пути экспорта конкретного сценария. Показать первые совпадения, затем дополнить выдачу из остальных разрешённых индексируемых мест | Общие хранилища смешанные: сверять происхождение каждого результата, исключать модели, рабочие сессии, загруженные оригиналы и временные копии. Для разового «Сохранить как» фактический путь может отличаться от настройки. Недоступность одного корня не должна задерживать остальные |
| Локальная история успешных сохранений | При успешном сохранении или экспорте запоминать конечный путь, время и вид результата. Это даёт точечных кандидатов, включая результаты вне обычной папки. Сначала оценить, достаточно ли уже сохранённых путей из проектов | Если нужен отдельный журнал, записывать в него событие после успешного завершения экспорта. Перед показом проверять существование и метку текущего файла: путь мог устареть или перейти к чужому файлу. Учитывать повторы сохранения, сбой и очистку журнала. Содержимое работ и запросы ИИ для поиска не нужны. Отсутствие местной записи не препятствует обнаружению перенесённого файла |
| Переносимая поисковая метка для новых экспортов | Добавлять постоянное значение во встроенное поле, которое штатный обработчик конкретного формата передаёт Windows Search. Сохранять существующие пользовательские теги, версию и историю происхождения. Проверять точное значение свойства | На новом экспорте подтвердить всю цепочку из §4 и поиск на другом ПК без переноса журнала. Для формата с уже работающим полем проверить, приносит ли дополнительная метка преимущество. Техническое значение и поле выбирать по результатам стенда. Автоматическая переразметка старых файлов для этого не требуется |

**Контроль новой метки.** На синтетическом JPEG добавили значение `LOPATA-COLLECTION-V1` в EXIF XPKeywords рядом с другим ключевым словом. Файл перенесли под нейтральным именем в индексируемую папку. Shell прочитал оба слова в `System.Keywords`. Из трёх проиндексированных файлов точное условие `System.Keywords = 'LOPATA-COLLECTION-V1'` вернуло только маркированный JPEG. Два контроля содержали эту строку в имени либо в тексте. Испытание подтверждает обнаружимость на данном ПК. Пользовательские ключевые слова редактируемы: совпадение в них годится для отбора кандидатов, а для строгой выдачи требуется подтверждение происхождения. Отдельно испытать перенесённый файл на чистом профиле и другом ПК с поддерживаемым обработчиком.

**Проверка объединения.** Измерить время до первых результатов и до полной выдачи, проверить пропуски и ложные совпадения. Включить известную папку, разовое сохранение, перенос, импорт с другого ПК без местной истории и подмену файла по старому пути. При совмещении источников один и тот же файл показывать один раз, сохраняя отдельные физические копии. В стенде должны присутствовать контрольные файлы только из первого источника, только из второго и из обоих. Доступность новой записи вне индекса подтверждать отдельно, например точечной проверкой пути из журнала. Обход дисков для этого не требуется.

## 4. Поисковое правило и вид подборки

1. Для каждой группы файлов подтвердить цепочку **встроенное поле → каноническое свойство Shell → значение в SystemIndex → найденный оригинал в Explorer**. В диагностике сопоставлять идентичность файла по URL/пути. Чтение байтов, успешный SELECT без условия и полнотекстовое совпадение отвечают на разные вопросы. В протоколе фиксировать сборку Windows, версию обработчика, маркировку образца, область поиска и каждый результат.
2. Первый кандидат — точное сравнение `System.ApplicationName:="LOPATA"` в каноническом AQS. В будущем экспорте, где штатный обработчик отображает правильное форматное поле, записывать стабильное имя создателя в это поле, а полную версию и историю сохранять в исходной структуре происхождения. Для других контейнеров проверить семантически подходящее штатное поле и точное значение. Свободные комментарии, пользовательские ключевые слова, автор и общий encoder не служат доказательством. Проверить записи с похожими значениями, включая LOPATA Studio. Синтаксис равенства проверять в самом Проводнике.
3. Для старых вариантов принять только однозначно проверенное сопоставление. Несколько доказанных точных условий можно объединять через OR. Для версии с иным значением, отсутствующей колонки либо неподдерживаемого обработчика указывать конкретное ограничение охвата. Автоматическая перезапись архива пользователя, перебор версий в новых сценариях и расширение запроса до общего слова LOPATA исключаются. Если аудио или другой обязательный тип не проходит, зафиксировать разрыв и показать пользователю варианты до приёмки сокращённого объёма.
4. В обычном представлении «По типу» использовать отображаемое Windows название типа (кандидат — `System.ItemTypeText`). Примеры на экране пользователя — «MP4 Video File» и «Исходный файл Markdown». Более крупные группы по `System.Kind`, например «Изображение», ранее проверены отдельно. Вариант с собственными категориями ЛОПАТЫ, например по сценарию создания, проверить на том же составе файлов. Учесть подтверждённые произведения с неизвестным типом или сценарием.
5. Для варианта с .search-ms хранить описание поиска в известной пользовательской папке сохранённых поисков (`FOLDERID_SavedSearches`), определять её через Windows. Для программной проверки доступен `ISearchFolderItemFactory` с явными SetScope, SetCondition и SetGroupColumn. В прототипе проверить и прямой вызов без работающего главного окна ЛОПАТЫ. Успех SQL-запроса отдельно от пользовательского входа недостаточен.
6. Область по умолчанию — доступные пользователю индексируемые расположения его произведений. Учесть известные папки Windows и заданные в ЛОПАТЕ места вывода, в том числе другой диск. Дать пользователю увидеть фактический охват и добавить конкретную папку. Проверять через Crawl Scope Manager и существование строки в индексе. Отбор коллекции не должен запускать медленный обход вне индекса. Не менять настройки Windows Search, политики, состояние WSearch и список индексируемых дисков автоматически. Папки самой поставки, служебные черновики и каталоги моделей не включать как источники. В поставке есть демонстрационные песни с настоящими тегами ЛОПАТЫ.
7. Проверить на стенде постоянный узел «ЛОПАТА» в области навигации Shell. Выбор узла открывает в текущей вкладке общий список оригиналов. Категории принадлежат представлению этого списка. Для сворачивания и раскрытия групп вызывается штатное действие их заголовка в правой панели.

В прототипе корню нужен устойчивый идентификатор Shell. Для одного открытого представления DefView проверить штатную группировку по свойству и возможность предложить собственную схему. У `ICategoryProvider` папка объявляет способы группировки, у `ICategorizer` задаёт соответствие файлов группам и их отображаемые названия. В прототипе Windows 11 проверить локализованные подписи и независимое сворачивание. [ICategoryProvider](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-icategoryprovider) · [Текст категории](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-icategorizer-getcategoryinfo)

### Вариант «По сценарию создания»

У обеих группировок один состав коллекции. Например, снимок экрана в первом представлении попадёт в «Изображения», а во втором — в «Захват экрана». Два изображения из разных сценариев можно будет различить по тому, где пользователь их создал.

Для пробы взять сохранённое при создании файла значение `Scenario`. Например, захват указывает `screen-capture/…` в [OutputProvenance](../../Исходники/AIHub/Services/OutputProvenance.cs), а генерация изображения пишет сценарий в [метаданные PNG](../../Исходники/AIHub/Services/ImageGenerationMetadata.cs). Сопоставить эти значения с понятными названиями сценариев из [каталога навигации](../../Исходники/AIHub/Services/ScenarioNavigationCatalog.cs). Если происхождение ЛОПАТЫ подтверждено, но сценарий установить нельзя, оставить файл видимым в группе «Сценарий не указан».

В Проводнике проверены широкие группы по System.Kind. Для группировки по сценарию предстоит проверить получение этого значения при показе коллекции, в том числе у файла с другого ПК. На одних и тех же образцах сравнить размещение файлов в обеих группировках, полноту и отсутствие повторов. Возможность переключения между ними и начальный вид оценить на прототипе.

Документированы два способа размещения строки слева. Основной кандидат для проверки — собственный виртуальный корень со штатным сгруппированным представлением. Привязка к физической папке полезна для отдельной проверки размещения. [Исследование левой панели и план стенда](../../Документы_проекта/Исследования/2026-11-09_Проводник_узел_коллекции.md).

### Изоляция поиска от Проводника — решение для проверки

Для первого прототипа рассмотреть две части. Внутри Explorer остаётся небольшой нативный адаптер папки и групп. Гибридный поиск, чтение истории и извлечение метаданных выполняет отдельный пользовательский процесс коллекции. Он должен работать независимо от открытого главного окна ЛОПАТЫ. Основной программный интерфейс и модели для просмотра коллекции не требуются.

Обмен организовать так, чтобы поток интерфейса Проводника получал уже подготовленные результаты и быстро возвращал управление. Длительную работу запускать асинхронно, предусмотреть отмену и ограниченное ожидание. При недоступности обработчика не считать коллекцию пустой: сохранить последнее подтверждённое представление с состоянием обновления или показать установленную причину ошибки. Готовые локальные результаты можно показывать до завершения второго источника. Полученные данные проверять по версии протокола и границам размеров. Сведения о путях относятся к текущему пользователю.

Предлагаемый жизненный цикл — запуск обработчика по первому обращению к коллекции, затем освобождение после простоя. Проверить, что параллельное открытие нескольких окон не запускает несколько конкурирующих обновлений. Если главная ЛОПАТА закрывается, открытая коллекция должна продолжать работать. В тесте отдельно завершить процесс обработчика и подвесить его ответ: обычная навигация Проводника остаётся доступной, последующая попытка обновления восстанавливает обработчик. Конкретные интервалы определить измерением.

#### Автоматическое восстановление обработчика

При включённой интеграции обращение к коллекции должно самостоятельно запускать отсутствующий обработчик. Если он аварийно завершился во время просмотра, адаптер асинхронно восстанавливает соединение и повторно запускает обработчик. Открывать главную ЛОПАТУ для этого не требуется. Готовность определять успешным ответом протокола, а не только наличием процесса. Обработчик может ещё запускаться или выполнять долгий запрос; это отличать от подтверждённого завершения и отсутствия ответа на проверку готовности.

Пуск координировать для текущего пользователя: несколько окон могут запросить восстановление одновременно, но обслуживать их должен один актуальный обработчик. При успешном восстановлении повторить незавершённое чтение коллекции и уведомить открытые представления. Сохранять идентичность видимых файлов и их выделение. Проверить и восстановление после простоя при следующем открытии.

Предусмотреть ограниченное число автоматических повторов и увеличивающиеся паузы при последовательных сбоях. Лимит должен действовать совместно для окон, чтобы новая вкладка не запускала цикл заново. После исчерпания попыток оставить доступное представление и понятное действие «Повторить». Конкретные времена и число попыток подобрать на стенде. Восстановление должно учитывать отключение интеграции, удаление и обновление компонента. Их штатное завершение процесса не вызывает новый запуск. Закрытие последнего представления прекращает его незавершённые повторы. Следующее обращение при включённой интеграции запускает обработчик заново.

На время восстановления сохранять последнее целое представление с обозначением обновления. Снимок данных публиковать атомарно, без подмены готовой коллекции частичным либо пустым ответом сбойного процесса. Запоздавший ответ предыдущего обновления не заменяет более свежий снимок. Доступные локальные оригиналы из уже показанного списка открывать через штатный Shell по их реальным путям независимо от обработчика коллекции. Если исходный файл перемещён, удалён или недоступен, показывать соответствующую причину.

Дополнить приёмку: завершить обработчик при открытой коллекции и закрытой ЛОПАТЕ; открыть два окна одновременно; имитировать зависший ответ, сбой до публикации нового снимка и несколько последовательных падений. Проверить автоматическое возвращение поиска, открытие доступного оригинала во время восстановления, отсутствие дублей процессов, сохранность последнего снимка и прекращение повторов при отключении интеграции.

Традиционное расширение пространства имён загружается в Explorer как COM DLL. Вынесение поиска защищает от сбоев обработчика, но адаптер тоже требует проверки: его собственная ошибка или блокирующий вызов могут повредить работе Проводника. [Модель расширения Shell](https://learn.microsoft.com/en-us/windows/win32/shell/nse-implement)

## 5. Установка и поведение при сбоях

По уточнению пользователя от 09.11.2026 интеграция Проводника **включена по умолчанию сразу после установки**. В разделе «Интеграция Windows» пользователь может открыть коллекцию для проверки и выключить её. Явно сохранённый выбор выключить интеграцию сохраняется при последующих запусках и обновлениях. Повторное включение, перезапуск и обновление версии должны оставлять один действующий узел дерева. После выключения или удаления узел коллекции исчезает из Проводника. При отключении и удалении очищать только файлы, ярлыки и ключи, созданные этой установкой и принадлежащие этому пользователю. При конфликте имени, чужих или изменённых объектах сохранить их и сообщить причину. При частичной ошибке регистрации вернуть прежнее действующее состояние и верное положение переключателя.

Вход должен работать из обычной учётной записи, в том числе при закрытой ЛОПАТЕ, без подготовки моделей. Учитывать пробелы, кавычки, кириллицу и спецсимволы путей. Формировать XML и URI средствами сериализации. Открывать только локально созданное доверенное описание поиска. На удалённый адрес, сетевое перечисление или загрузку компонентов действие не ведёт автоматически. Локализовать настройки и объяснения для RU и EN.

При выключенном поиске, очереди индексации, недоступной папке, отсутствующем обработчике или недостаточных правах в настройках различать соответствующую причину, насколько её установила Windows. Дать простое действие для повторной проверки. Если причину доказать нельзя, указать проверенный факт. Для UNC, отключаемых носителей и файлов-заполнителей проверить фактические права, доступность и индекс отдельно, не скачивать содержимое ради поиска. Нулевая выдача из неподдерживаемой области не означает отсутствия произведений.

### Форматы без собственных метаданных

Фактический список конвертера изображений содержит 47 форматов. У QOI, farbfeld и ряда других форматов нет пригодного штатного поля для полных сведений о происхождении. Произвольный хвост или префикс делает часть таких файлов несовместимой со спецификацией; этот способ не применяется. У поддерживающих метаданные форматов записываются структурные сведения в комментарий/XMP, сохраняются пользовательские авторство, права и описание. В TIFF стабильное поле программы проверено через `-define tiff:software=LOPATA` в поставляемом ImageMagick.

Для остальных используется поток `LOPATA.Provenance` файла NTFS: JSON с программой, версией, сценарием и известной историей модели, а также длиной и SHA-256 основного содержимого. Проверка привязки выполняется перед показом; устаревший поток не подтверждает заменённые байты. Поток закрывается до окончательного переноса подготовленного файла. Матрица из 47 форматов подтвердила неизменность основного SHA-256 и сохранение потока после переименования и Win32-копирования. Это не означает поддержку переноса потока каждым архиватором, облачным клиентом или сторонним средством копирования.

FAT32/exFAT не поддерживают такие потоки. Если поток недоступен, программа явно сообщает об ограничении и сохраняет локальную квитанцию успешного экспорта с контрольной суммой. Квитанция подтверждает именно сохранённое содержимое по данному адресу; подмена, несовпадающий хеш или отсутствие квитанции не допускают файл в коллекцию. Квитанция не переносится на другой ПК вместе с обычным файлом. На другом ПК и после утраты потока обнаружимость зависит от сохранившихся метаданных формата и области Windows Search. Это ограничение точнее исходного предположения об одинаковой переносимости всех типов файлов.

### Граница поиска и ресурсов

Известные папки и журнал дают первую выдачу. Windows Search дополняет её глобальными совпадениями стандартных свойств программы; для форматов с непроецируемой меткой кандидаты берутся из включённых папок и стандартных пользовательских областей индекса. Файл с другого ПК не обязан иметь местную запись журнала. Расширение лишь отбирает кандидатов, после чего проверяется происхождение. Файлы, доступные только в облаке, автоматически не скачиваются.

Выдача ограничена 20 000 элементами и 16 МиБ снимка. Длинный обход известных папок продолжается порциями; неполная выдача и недоступность системного поиска обозначаются явно. Закрытые представления освобождают worker после простоя. Вся коллекция не требует запуска основного окна ЛОПАТЫ.

### Поставка и проверенная платформа

Проверена Windows 11 x64. Native DLL и self-contained worker поставляются в отдельных неизменяемых поколениях с общим манифестом аудита. Обновление не перезаписывает загруженную Explorer DLL и не удаляет старое поколение из-под работающего процесса. Подписанные сведения о прежних поколениях сохраняются для проверки владения при удалении. Автоматическая фоновая очистка поколений в этот этап не входит; заблокированные или изменённые файлы при удалении сохраняются с записью результата.

Путь сборки `win-arm64` предусмотрен, но физического испытания ARM64 не было. Модуль должен соответствовать архитектуре Проводника Windows; x64-пакет не считается проверенным ARM64-компонентом.

### Испытание в среде разработки

Командные процессы Codex и обычный Explorer на стенде видели разные проекции пользовательского реестра. Поэтому прямые COM-пробы успешно читали регистрацию, которую Проводник не видел; это вызывало ошибку ассоциации до вызова нашего кода. Один разрешённый пользователем перезапуск Explorer исключил старый кэш. Реальный внешний процесс, запущенный через существующее окно Explorer, зарегистрировал тот же узел штатным production API; после этого открылся обычный Проводник с четырьмя типами работ и сворачиваемыми группами. Системные ассоциации и политики ради проверки не менялись. Проверочные регистрации обеих проекций затем удалены.

Проверены группы по типу и сценарию, сохранение режима в новом окне, два окна с одним worker и автоматическое восстановление после остановки собственного проверенного процесса. Отдельные отчёты различают настоящий Explorer, изолированный DefView-host, managed/native tests и проверки форматов. Итоговая пользовательская приёмка остаётся отдельным шагом; ТЗ не архивируется автоматически.

### Включение при установке и смена поколения

Уточнение пользователя о включении по умолчанию реализуется общим шагом подписанной регистрации установки, а не только первым открытием главного окна. После проверки установленных файлов updater запускает `AIHub.exe --initialize-collection` независимо от флажка запуска приложения и тихого режима. Этот путь использует сохранённые настройки и общую политику ComponentAudit, готовит компонент и регистрирует собственный узел без главного окна и моделей. Явное сохранённое выключение сохраняется; отсутствие старого флага означает включение. Ошибка регистрации возвращает прежний конфиг, чужая установка не перехватывается. Дочерний процесс ограничен по времени и объёму вывода; ошибка не скрывается. Проверки установочного вызова и реестра проведены на изолированных данных; полный установщик на чистом ПК не испытан.

Отдельная команда также проверена реальным процессом в обычном пользовательском контексте: выход 0, без нового главного окна, сохранённые настройка аудита и ревизия конфигурации. Для старых подписанных пакетов, в которых папки Collection вообще нет, неизвестная команда не запускается. Если новый пакет уже содержит Collection, обязательный current.json должен присутствовать; частичная поставка не считается старой совместимой версией.

Обычная замена поколения не является поломкой компонента. Старый worker сравнивает свой путь с актуальным манифестом до проверки файлов нового поколения и штатно выходит при замене, сохраняя снимок. Новый путь получает отдельный ограниченный бюджет восстановления; неизменный путь не получает бесконечных повторов. Успешная подготовка текущего компонента снимает устаревший marker сбоя. Подтверждённый реальный сбой по-прежнему передаётся общему механизму уведомления; настройка аудита автоматически не включается.

### Обязательный контроль обычного Win+E

Уточнение пользователя: проверка должна проходить при полностью завершённой основной ЛОПАТЕ. Закрыть все окна коллекции, дождаться штатного простоя worker, открыть обычный Win+E и убедиться, что узел присутствует до любого открытия коллекции или настроек. Щёлкнуть узел в этом же окне, затем закрыть коллекцию и повторить Win+E дважды. Запуск отдельного Explorer-процесса по абсолютному пути не заменяет этот контроль. После замечания от 09.11.2026 цикл проверен на свежем desktop-сеансе с исходной регистрацией и Main=0; [протокол](../../Тесты/ExplorerCollection_20261109/README.md#проверка-win-e-после-полного-выхода-из-лопаты). Изменение состояния старого host не выдаётся за исправление универсального алгоритма обновления кэша Windows.
