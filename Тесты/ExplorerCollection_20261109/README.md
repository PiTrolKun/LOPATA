# Коллекция ЛОПАТЫ в Проводнике: испытания 09.11.2026

Рабочая версия — **0.7.65-dev**. Платформа — Windows 11 25H2 x64, сборка 26200.9711. [Рабочее ТЗ](../../ТЗ/Архив/2026-11-09_Коллекция_произведений_в_Проводнике_Windows.md) принято пользователем 09.11.2026 и перенесено в архив. Установщик и публичное файловое обновление не собирались и не публиковались.

## Что проверялось

Один самостоятельный узел «ЛОПАТА» в обычном Проводнике, оригиналы разных типов, сворачиваемые группы справа, выбор группировки по типу/сценарию, отдельный worker и восстановление после его аварии. Поиск объединяет известные адреса успешных экспортов, настроенные папки и Windows Search. Расширения и обычное слово LOPATA в имени/тексте не подтверждают происхождение.

## Настоящий Explorer

Проверены четыре нейтрально названных копии реальных результатов: PNG, FLAC, DOCX и LOPATAdoxAI, плюс отрицательный LOPATA.txt. В реальном правом представлении появились ровно четыре положительных оригинала, группы раскрываются и сворачиваются без перехода в другую папку. Переключение «По сценарию» сохраняется при повторном открытии. Два окна разных Explorer-процессов использовали один worker.

Для аварийной проверки предварительно сверены PID, точное время создания процесса, путь executable и SID. Завершён только worker стенда. Он автоматически восстановился через 15 секунд; контрольная сумма последнего снимка сохранилась. Проверено штатное отключение: свой CLSID/namespace удалены, прежнее отсутствие desktop visibility value восстановлено, enabled.bin=0, worker завершился.

Прямые COM-пробы первоначально проходили, а Explorer показывал ошибку ассоциации. Причиной оказались разные проекции HKCU в командной среде Codex и обычном процессе Explorer. Проверка из внешнего процесса, запущенного объектом Application существующего окна Проводника, подтвердила это различие и открыла тот же узел без изменения системных политик/чужих ассоциаций. Был один отдельно разрешённый пользователем перезапуск Explorer. Тестовые регистрации очищены в обеих проекциях.

После этого штатный safe-start запустил обычную ЛОПАТУ. Из настоящих настроек включена рабочая коллекция профиля, найдено 462 произведения. Обычный щелчок по узлу слева перевёл прежнее окно и вкладку в коллекцию; выделение «ЛОПАТА» в дереве подтверждено отдельно. Выключение из интерфейса остановило worker и сняло собственную регистрацию; повторное включение восстановило её. Worker продолжал работать при закрытом главном окне. Отображение отдельного сообщения о неполном поиске в непустом правом представлении Windows 11 физически не подтверждено: в проверенном состоянии системная строка показывала число элементов.

## Включение после установки и смена версии

По уточнению пользователя интеграция включена по умолчанию сразу после установки. Отсутствующий флаг в старых настройках означает включение; сохранённый `false` остаётся выключением. Установочный путь после проверки подписи и файлов запускает `AIHub.exe --initialize-collection`: без главного окна, моделей, перенаправления в старую версию и активации уже работающего экземпляра. Единый конфиг сохраняет прежние границы поиска и исключения служебных папок. Проверены настоящие изолированные реестр/конфиг/квитанции аудита и подписанная fixture для вызова дочернего процесса. Полный установщик на чистом ПК не запускался.

Финальная штатная сборка подготовила поколение `3911595de96a0c6ad2895723`: 0 ошибок и предупреждений. Настоящее основное окно и worker используют эту версию; статус ready, 462 файла, limited=false, ошибки нет. Отдельный `--initialize-collection`, запущенный из обычного пользовательского контекста, завершился с кодом 0 за 237 мс: нового окна не появилось, конфиг не получил лишнюю ревизию, узел зарегистрирован, ожидаемый и фактический путь worker совпали, AuditEnabled=false и marker ошибки отсутствует. Совместимость со старыми подписанными пакетами без всей папки Collection сохранена: им неизвестная команда не отправляется; неполный новый пакет без current.json отклоняется.

Уведомление пользователя об аудите разобрано по времени публикации манифеста, журналу и конфигу. Старый worker успел проверить новое поколение до обновления ожидаемого пути, затем ошибочно сообщил о несовпадении своего EXE. Теперь смена поколения распознаётся до аудита и штатно завершает устаревший worker без уведомления о повреждении. Физическая проба old A → current B: выход старого процесса с кодом 0 за 443 мс, снимок сохранён, ложного marker и квитанции B от процесса A нет; новый B готов и создаёт собственную квитанцию. Лимит восстановления привязан к новому пути worker и сбрасывается один раз при его смене; для прежнего пути остаётся ограничение трёх попыток. Успешная актуальная подготовка снимает прежнее уведомление. Пользовательский флаг аудита остался выключенным.

## Форматы и перенос

Для основных контейнеров читаются их структурные метаданные. GIF — comment extension; MP4 — provenance в штатных metadata atoms; MKV/WebM — EBML Tags; MIDI — штатный TextEvent с JSON; melody project — собственная структура документа. Бинарные чтения ограничены по размеру и не запускают внешние декодеры в worker.

Для 47 форматов конвертера изображений отдельно проверены encode, метаданные, основной SHA-256, переименование, Win32-копирование и декодирование. Служебный NTFS-поток не меняет основной поток файла. Встроенные XMP и авторство/права/описание PNG/JPEG/WebP/TIFF дополнительно прочитаны поставляемым ExifTool. При потере потока и отсутствии подходящих метаданных локальная SHA-квитанция помогает лишь на текущем ПК по записанному адресу. Без журнала и метаданных происхождение файла на другом ПК не выдумывается.

**Отдельная прежняя граница ART.** Bundled ImageMagick воспроизводимо записывает ART 64×48, который сам затем не может полностью декодировать (`unexpected end-of-file`, art.c/ReadARTImage/188), даже без новых метаданных и ADS. Для проверки неизменности формата использован полностью декодируемый ART 8×8; остальные форматы проверены на 64×48. Прежний дефект ART на некоторых данных не исправлялся сменой движка и не выдаётся за устранённый.

Переносимость NTFS-потоков зависит от носителя и копирующего средства: [потоки файлов](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams), [CopyFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfileexw), [возможности файловых систем](https://learn.microsoft.com/en-us/windows/win32/fileio/filesystem-functionality-comparison). Автоматическое скачивание облачных placeholders и полный обход дисков не выполняются.

## Проверка Win+E после полного выхода из ЛОПАТЫ

По новому замечанию пользователя исходный контроль дополнен точным жизненным циклом: Main полностью завершена, все окна коллекции закрыты, её worker штатно вышел после простоя, затем открывается обычный Win+E. Старый desktop Explorer 57780 пропускал узел, а запуск по абсолютному пути в свежем процессе 61880 показывал его. Состояние старого host проверено через его собственный Desktop COM: в enum root отсутствует, remote NameSpace возвращает ELEMENT_NOT_FOUND; в свежем процессе тот же вызов успешен. У обоих видимых регистраций флаг закрепления был установлен, shell property store возвращал true. Это отличает проблему от отсутствия флажка в настройках и от зависимости worker от Main.

Отдельные пробы FolderValueFlags=0x28, уведомлений родительского Desktop, MKDIR/ATTRIBUTES собственного root и строгого ASSOCCHANGED/FLUSH не исправили старый host. Дополнительный флаг и связанный пробный тест не оставлены в продукте: два исходника восстановлены точно из backup; реальное значение флага возвращено в исходное отсутствие. Временная собственная регистрация exec очищена без изменения общего enabled/config и политики аудита. Официальные документы использованы для проверки смысла проб, а не как доказательство их успеха: [регистрация навигационного узла](https://learn.microsoft.com/en-us/windows/win32/shell/integrate-cloud-storage), [события Shell](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shchangenotify), [образец обновления родителя](https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/Win7Samples/winui/shell/shellextensibility/explorerdataprovider/Dll.cpp#L158).

По сохраняющемуся разрешению пользователя desktop перезапущен через detached helper из обычного окружения Windows с проверкой PID, времени создания, SID и отсутствия чужих окон. Свежий desktop 41416 Windows подняла автоматически за 676 мс. Кэш и особенности привязки прежнего процесса к окружению окончательно не разделены; подтверждено, что старый host не видел раздел, а свежий видит без обхода через настройки. Продуктовый код в этом диагностическом проходе не изменён.

Финальный контроль на одном desktop-процессе, Main=0 на всех шагах:

1. Первый Win+E сразу показывает узел без предварительного открытия коллекции.
2. Адресное действие на узле открывает коллекцию в том же окне; узел выбран слева. Worker запускается самостоятельно: ready, 462 файла, limited=false, ошибки нет.
3. После закрытия этого окна новый Win+E снова показывает узел.
4. После закрытия проверочного окна и нейтрального helper ещё один Win+E сохраняет узел.
