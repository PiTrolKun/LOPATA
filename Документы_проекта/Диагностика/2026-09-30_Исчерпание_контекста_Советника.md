# Исчерпание контекста Советника — материалы для обсуждения

30.09.2026. База: 0.2.55-dev, исходники принятой реализации f5eb7ba, документация выпуска 8901664. Реализация новой задачи не начата, VERSION не менялась. Это обследование кода и прежних решений; журналы нового события на компьютере друга ещё не предоставлены.

Со слов пользователя: друг тестировал на RTX 4080 свой большой проект, ранее использованный в наших тестах. После получения сведений из первоисточника долго обсуждал шаг с Советником. Контекст закончился; вопрос вернулся в поле ввода, причина была заметна только в статусе модели. Точное выделенное окно, версия установленного приложения, выбранные источники и результат попытки RAM-резерва пока неизвестны.

## Подтверждённая текущая механика

1. Перед следующим запросом собираются все полные сообщения текущей сессии с InContext=true. Для Советника они целиком попадают в conversation; для Писателя этот массив отсутствует. Каждый успешный ответ Советника увеличивает следующую беседу. Системная инструкция, вопрос, рабочий текст, текущий маршрут, параметры, цитаты и выбранные источники занимают место дополнительно. См. [приём запроса](../../Исходники/AIHub/Controls/LiteraryStudioControl.Submission.cs), [формирование промпта](../../Исходники/AIHub/Services/LiteraryStudioPrompts.cs), [пакет](../../Исходники/AIHub/Services/LiteraryParagraphPacket.cs).
2. Полученные однажды исходные материалы не превращаются автоматически в постоянную историю инструментов: перед запросом читается текущий выбор источников. RAG первоисточника возвращает найденные фрагменты; не вся большая книга автоматически передаётся в каждый вопрос. Но прежние ответы и выбранные цитаты сохраняются в текущей беседе. См. [чтение источников](../../Исходники/AIHub/Services/LiteraryParagraphSources.cs), [StudioAsync](../../Исходники/AIHub/Services/LiteraryChatRuntime.Studio.cs).
3. Окно подбирается backend через fit по свободной видеопамяти; фактическое n_ctx читается из slots. Защитный резерв видеопамяти — минимум 1 ГиБ либо 10% меньшего измеренного свободного объёма. Это не общий фиксированный лимит для всех RTX 4080. При нехватке один раз за операцию сервер переподготавливается, чтобы переоценить окно. См. [автоматический бюджет](../../Исходники/AIHub/Services/LiteraryAutomaticBudget.cs), [расчёт запроса](../../Исходники/AIHub/Services/LiteraryChatRuntime.Budget.cs).
4. Из окна вычитаются вход и 256 токенов страховки; для обычного ответа требуется минимум 256. При переходе к порционному поиску обязательная основа должна помещаться со страховкой 256 и резервом ответа 512 (окно меньше 8192) либо 1024. Поэтому полезная вместимость для беседы меньше показанного размера окна.
5. Если полный пакет не влезает, программа пробует порционно прочитать и сократить исследовательские материалы. Перед этим проверяется основа без этих материалов, но с беседой, вопросом, рабочим текстом и выбранными обязательными условиями автора. Если уже основа не влезает, поиск не решит проблему и запрос отклоняется. Беседа намеренно не сокращается скрыто. См. [StudioAsync, строки 35–58](../../Исходники/AIHub/Services/LiteraryChatRuntime.Studio.cs:35), [разделение материалов](../../Исходники/AIHub/Services/LiteraryMemoryRequestPlan.cs).
6. Автоматическая сводка долгого обсуждения была отдельно оставлена за границами принятого ТЗ. Это подтверждено [картой идеи](../../ТЗ/Архив/КАРТА_ИДЕИ_2026-09-27_Большой_поиск_литературной_памяти.md) и [ТЗ порционного поиска](../../ТЗ/Архив/2026-09-27_Порционный_поиск_и_RAM_резерв.md). Переход к Писателю снимает прежнюю беседу с контекста и передаёт задание; возврат к Советнику оставляет задание и последний результат. Это не автоматическое сохранение всех решений долгой беседы.

## Отказ, уведомления и восстановление

- Неуспешный вопрос сохраняется в журнале, исключается из повторно отправляемого контекста и возвращается в поле ввода вместе с цитатами. Неполный ответ не считается завершённым. [Pending.Restore](../../Исходники/AIHub/Services/LiteraryStudioPending.cs), [операции Studio](../../Исходники/AIHub/Controls/LiteraryStudioControl.Operations.cs).
- В текущем Studio есть подробная локализованная ошибка с входом/окном/резервами и советом сократить материалы/беседу или освободить видеопамять. Она должна появляться в статусе и отдельной карточке в конце чата; RenderMessages вызывает RenderContextFailure. Статус раскрывается нажатием, но не предлагает действий по очистке. Без журналов/снимка/версии друга нельзя утверждать, почему он видел только статус. [отображение ошибки](../../Исходники/AIHub/Controls/LiteraryStudioControl.Status.cs), [отрисовка чата](../../Исходники/AIHub/Controls/LiteraryStudioControl.Messages.cs).
- Общее системное уведомление при остановке есть и для переднего плана, но оно говорит о необходимости открыть причину, а не объясняет заполнение беседы. [уведомления](../../Исходники/AIHub/Controls/LiteraryStudioControl.Notifications.cs).
- Диалог «Недостаточно видеопамяти» с «Да / Повторить / Отмена» показывается только при допустимом временном RAM-резерве либо подходящей ошибке CUDA. Резерв поддерживается проверенным профилем модели и предлагается, пока он ещё не использован и запрос не превышает предел самой модели. После неудачи уже выбранного резерва повторное предложение RAM не делается. Отмена становится обычным сообщением «Запрос остановлен. Ваш ввод сохранён». Это один из возможных путей наблюдаемого недостаточного пояснения, пока не подтверждённый для друга. [обработка](../../Исходники/AIHub/Controls/LiteraryStudioControl.MemoryRecovery.cs), [политика](../../Исходники/AIHub/Services/LiteraryRamReservePolicy.cs).
- RAM-резерв переносит два слоя модели для освобождения VRAM, требует проверенного запаса оперативной памяти, действует на один запрос и не гарантирует, что сколь угодно долгая беседа поместится. Он не увеличивает максимальное окно самой модели.

## Важный нюанс нынешней очистки

«Очистить чат» вызывает State.Clear: прежние сообщения остаются в сохранённом журнале, снимаются с контекста и доступны через «Вся история». Рабочий текст и книга не удаляются. Но одновременно сбрасываются Input, Quotes, Task, Result и требования к текущему варианту. Выбор источников остаётся. Поэтому после возврата неудачного вопроса эта кнопка очищает и сам вопрос; при избыточных обязательных материалах очистка беседы сама по себе может не помочь. [Clear](../../Исходники/AIHub/Services/LiteraryStudioState.cs:73), [обработчик](../../Исходники/AIHub/Controls/LiteraryStudioControl.cs:64).

## Выводы и предложения для следующего обсуждения

Наиболее вероятно накопление беседы вместе с материалами в относительно небольшом фактически выделенном окне. Это согласуется с описанным сценарием и архитектурой, но точную причину нового отказа надо подтвердить журналом. Увеличение памяти откладывает заполнение; управление долгой беседой остаётся отдельной задачей.

Предлагается сначала сделать понятное объяснение отказа с конкретным действием: начать новое обсуждение, сохранив восстановленный вопрос и цитаты. До очистки дать возможность перечитать/скопировать историю, не выполнять её скрыто. Отдельно объяснять нехватку VRAM, заполнение беседы, превышение предела модели и обрыв ответа. Формулировку и состав кнопок ещё согласовать.

Для более длинных обсуждений отдельно выбрать подход: ручное новое обсуждение либо управляемая сводка с сохранением авторских решений, запретов и неопределённостей. Не записывать предложения Советника как подтверждённые факты книги и не добавлять автоматически сводку в Желе. Раннее отображение заполнения полезно, но пока счётчик обновляется при фактической отправке; точный прогноз после правки источников/цитат потребует отдельного расчёта.

## Дополнение пользователя: только ручное управление контекстом

Согласованный пользователем образ, пока без реализации: справа от «Остановить» круглая зелёная кнопка-индикатор заполнения контекста. При заполнении мигает; по нажатию открывает отдельное окно с объяснением и тремя путями. Автоматического запуска сжатия нет.

1. Ручное удаление сообщений: следующее окно с содержимым контекста и галочками выбранного удаления. Поверх списка отдельный перетаскиваемый счётчик «занято / доступно», вне области прокрутки. Выбор пересчитывает предполагаемый результат; подтверждение внизу. Работа программная, без модели.
2. «Пересказ»: отдельное окно с процессом подготовки и готовым результатом. Внизу «Принять» и «Сжать сильнее». Пока не принято, исходный контекст не меняется.
3. «Умное сжатие»: назначение обозначено пользователем, точный алгоритм ещё обсуждается. Потребность — продолжать длинную работу на ограниченном окне, без скрытого автоматического запуска.

Технические предложения, ещё не окончательное ТЗ:

- Отдельно считать заполнение контекста и использование VRAM. Переполненная беседа не обязательно означает новую ошибку выделения памяти. Короткие запросы могут работать в уже выделенном небольшом окне; настоящее CUDA OOM требует нынешнего выбора освобождения VRAM/повтора/RAM, а не обещания, что сжатие обязательно запустится.
- Измерять токены штатными apply-template/tokenize, уже используемыми runtime. Эти endpoints оформляют/токенизируют текст, не генерируют ответ ([официальное описание](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-tokenize-tokenize-a-given-text)). Не складывать символы и не выдавать сумму независимых сообщений за точный размер финального пакета. Счётчик учитывать вместе с инструкциями, рабочим текстом, текущими материалами и резервом ответа; при неизвестном/устаревшем составе явно помечать оценку.
- Для «Пересказа» отправлять только порцию выбранной беседы и инструкцию сокращения; не добавлять к каждому проходу исходный переполненный пакет, базу RAG или всю книгу. Подбирать порции с местом для результата, сохранять промежуточные результаты и объединять их также порциями в рамках той же очереди модели. Не загружать параллельно вторую модель. Проектные факты не получать заново при каждом проходе.
- «Сжать сильнее» задаёт меньшую цель по токенам, а не безграничное повторное сокращение уже сокращённого текста. По возможности работать с исходным снимком/сохранёнными проходами; не обещать отсутствие смысловых потерь.
- Предлагаемое отличие умного режима: последние реплики сохраняются дословно, более старая часть заменяется структурированной рабочей выжимкой. Сохраняются принятые автором решения, запреты, текущая задача, открытые вопросы и ссылки на исходные реплики. Варианты модели и подтверждённые автором решения разделяются; новые сведения книги не создаются. Нужен просмотр результата и размера до «Принять».
- Исключение из рабочего контекста предлагается отделить от безвозвратного удаления сохранённой истории. Ввод, цитаты и черновик сохранить. Изменение применять атомарно к проверенному снимку; пока открыто управление контекстом, конкурирующий запрос не должен изменять тот же снимок. Отмена/закрытие/ошибка не применяют черновой результат. Принятый пересказ хранить как отдельную сводку беседы, не как факт Желе.
- Предупреждение можно начинать до полного отказа, например при 90% полезного бюджета; точный порог ещё согласовать. Мигает сам индикатор, окна автоматически не открываются. При уменьшении анимации Windows нужен статичный заметный вариант.
- В ручном списке отделить доступные к исключению сообщения от неизменяемых системных правил и независимых источников. Иначе пользователь сможет снять все сообщения, но не поймёт, почему обязательный пакет всё ещё не помещается. Возможность менять выбор источников из этого окна пока отдельно не согласована.

Открытые вопросы: означает ли «удаление» исключение из контекста при сохранённом архиве; устраивает ли предложенное отличие «Умного сжатия» от полного «Пересказа». Существующая Clear() не подходит для применения без адаптации — сбрасывает восстановленный ввод/цитаты. Реализация, ТЗ, новая версия и публикация не выполнялись.

## Данные для проверки события у друга

Версия приложения, последний успешный и первый неудачный JSONL из папки проекта `Diagnostics/LiteraryDetailed/StudioAdvisor`, снимок полного пояснения отказа и сведения, появился ли диалог RAM и какой вариант выбран. В `analysis_snapshot` видны беседа и выбор источников; `automatic_context`/`analysis_budget` показывают окно/вход при наличии события; `failure` — этап отказа. До раннего отказа `analysis_request` или финальный `analysis_budget` могут не успеть появиться, это не доказательство пустого запроса. Журнал backend дополнительно может содержать `Context budget rejected` с числами. Зафиксировать свободную VRAM при подготовке, не выводить размер окна только из названия видеокарты.

На этапе первоначального обследования код, VERSION, модели, пользовательские проекты и настройки не менялись. Тогда новые сборки, модельные прогоны, установщик, commit/push и публикация не выполнялись; последующий отдельно разрешённый стенд описан ниже. Исследование в коде использовало Atlas Scout с частичным покрытием C# и прямое чтение исходников; пустые результаты индекса не считались доказательством отсутствия механизма.


## Последующий стенд по прямой команде пользователя

30.09.2026 проверены три метода, по три возраста одной синтетической беседы, при окне 27 648 токенов из прежнего внешнего отчёта друга. [Полные измерения и смысловая оценка](2026-09-30_Стенд_сжатия_контекста_27648.md). Прогоны выполнены на ПК разработчика; журналы нового исчерпания контекста у друга этим не заменены.

Пользователь уточнил цель: уменьшение хотя бы вдвое уже достаточно, не нужен чрезмерно короткий пересказ. Все девять итогов укладываются в половину исходного объёма. По заранее закреплённым смысловым проверкам литературный Qwen GPU получил 82,3%, Qwen 4B CPU — 51,0%, mT5 CPU — 1,0%. Эти оценки не означают долю всего сохранённого смысла. CPU Qwen оказался медленнее; mT5 создаёт посторонние новостные сообщения. Проверка входов и отдельной оригинальной статьи подтверждает базовую исправность стенда.

Рекомендация для дальнейшего обсуждения: литературная модель порциями, без малого фиксированного финального лимита, с обязательным просмотром до принятия. Она также допускает критичные искажения, включая разворот явной замены имени; результат нельзя считать безошибочным. Сохранение недавних реплик дословно и сверка поздних исправлений остаются предложениями для умного режима, ещё не проверенными таким стендом.

Сжатие беседы не устраняет размер обязательных источников и не обязательно освобождает выделенную VRAM. CPU-помощник не требует GPU, но его совместное размещение с основной моделью и работа после настоящего CUDA OOM не проверялись. Код/VERSION/пользовательские данные не менялись. mT5 скачан только в локальный стенд по разрешению пользователя; зарегистрирован в REESTR, поставки и публикации нет. Окна управления контекстом и окончательное продуктовое ТЗ пока не реализованы.
