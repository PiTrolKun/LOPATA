## 1. Последние решения пользователя

1. Сначала на уже работающем YuE2 доделать интерфейс под универсальный музыкальный конвейер.
2. Затем развивать возможности по этой карте, не переделывая общее окно под каждый движок.
3. Детальные дополнительные тесты и исследования — отдельная ветка R, запускаемая при необходимости.
   Она не является обязательным предварительным марафоном перед работой над интерфейсом.
4. Обычные проверки каждой реализуемой функции остаются обязательными. Подключение
   движка требует проверки запуска, отмены, файлов, памяти и условий его поставки;
   это не равнозначно большому сравнительному исследованию качества песен.
5. Дополнение о формате и метаданных относится к основному конвейеру: предусмотреть
   его в U1, реализовать общее хранение/экспорт отдельным этапом U2. Заметка к дублю
   и известные программе сведения не должны зависеть от длинного имени файла.

Подробности интерфейса следующих этапов обсуждаются отдельно. Эта карта не означает
одобрения всех предложенных регуляторов, обязательной установки всех 13 кандидатов
или разрешения немедленно запускать длинные серии генераций.

## 2. Что уже есть

Принятые музыкальные ТЗ остаются закрытыми. Существующий сценарий содержит редактор
с подсчётом токенов и резервом контекста, пожелания к музыке, профили исполнителей,
вставку пометок и ударений, плеер, карточки треков, выбор папки, копирование аудио,
статус со скрипачом, журнал, запуск/паузу/отмену, варианты и повтор генерации.
Чат стихов и улучшение рифмы пока являются будущими функциями.

Текущий исполнитель YuE2 использует отдельный процесс для плана и отдельный для синтеза.
В задании уже сохраняются текст, стиль, длительность, оба seed, версии исполнителя
и модели, пути/хеши готового плана и аудио, завершённость вариантов. Повтор использует
сохранённый план и оба seed. Новый общий слой должен расширять эту основу с миграцией
старых записей, а не объявлять её отсутствующей.

Проверенные точки кода: `MusicWishPrompt`, `MusicGenerationJobs`,
`MusicGenerationSession`, `MusicYueWorker` в `Исходники/AIHub`.
Действующие аппаратные возможности и границы физических испытаний:
[YuE2](../Документы_проекта/YuE2_аппаратная_поддержка.md), [общая матрица](../Документы_проекта/АППАРАТНАЯ_ПОДДЕРЖКА.md).
Наличие работающего CUDA/Vulkan/CPU пути не доказывает качество каждой песни.

## 3. Основной маршрут

| Этап | Результат для пользователя | Граница готовности |
|---|---|---|
| U1. Универсальное рабочее окно | Один привычный редактор, плеер и список результатов; место выбора движка и его действий | Текущий YuE2 работает через общую структуру без потери существующих функций; принят интерфейс |
| U2. Хранение, метаданные и экспорт | Компактная библиотека, заметка и сведения внутри файла; отдельный выбор экспорта | Предпочтительно Ogg Opus, режим сохранения исходного качества, проверенная запись тегов и безопасное завершение конвертации; подробности в §10 |
| U3. Подключаемые исполнители | Дополнительный движок можно подключить к тому же окну | Сначала адаптер текущего YuE2; следующий приоритетный кандидат — headless YuE2 Studio; реальные возможности и состояния компонентов отображаются честно |
| U4. Управление этапами и результатами | Действия с планом, повтором и вариантами там, где они поддерживаются | Каждая кнопка выполняет определённое действие; происхождение результата и входы сохраняются |
| U5. Понятные регуляторы | Простые цели вместо россыпи технических чисел; дополнительные и экспертные настройки отдельно | Включаются только обоснованные соответствия параметрам конкретного движка; ручные переопределения сохраняются |
| U6. Расширение возможностей | Другие генераторы, специальные вокальные/cover/инструментальные режимы, позднее MIDI и помощники | Подключаются выбранные полезные кандидаты, а не весь список автоматически |

Порядок U2–U6 уточняется по практической пользе. Сложные части не задерживают
самостоятельно полезные изменения. Ветка R подключается к конкретному вопросу,
например почему нарушается текст или действительно ли регулятор помогает.
Для U5 необходимость подтвердить заявляемое действие может открыть один пункт R;
это не требует проходить всю ветку или испытывать все модели.

```text
Работающий YuE2 → U1: интерфейс → U2: хранение/метаданные → U3: исполнители
                                                        → U4: действия
                                                        → U5: регуляторы
                                                        → U6: новые возможности
       ↘ R: отдельный вопрос → результат → нужный этап
         (ветка выключена до возникновения необходимости)
```

## 4. U1 — общий интерфейс на существующей реализации

Предлагаемая основа, которую нужно превратить в отдельное ТЗ перед кодовыми правками:

```text
Стандартная шапка ЛОПАТЫ
┌────────────────┬────────────┬────────────────────────────────────┐
│ Текст          │ Пожелания  │ Статус, время, прогресс, журнал     │
│ произведения   │ к музыке   ├────────────────┬───────────────────┤
│                │            │ Плеер          │ Движок и главные  │
│                │            ├────┬───────────┤ настройки         │
│                │            │Теги│ Треки     │ Старт/пауза/отмена│
│                │            │    │           │ Доп. действия     │
│ Счётчики       │            │    │           │ движка/помощники  │
└────────────────┴────────────┴────┴───────────┴───────────────────┘
```

Сохранить принятые значки и подсказки, компактную раскладку, разделители, обводку
треков, ограниченную длину пути, отдельные окна сложного выбора. Основной экран
не превращать в чат: будущий чат создания стихов открывается отдельным окном.
Неподключённая будущая функция не выглядит работающей.

Общими остаются исходный текст, пожелания и локальные пометки, название, варианты,
желаемая длительность, папка результатов, плеер, библиотека и управление заданиями.
Объём поддерживаемого контекста и доступность настроек определяются выбранным
движком; число 24 576 и правила резервирования YuE2 не переносить на остальные модели.
При смене движка текст не теряется и не переписывается автоматически.

Выбор движка/модели предлагается вынести в отдельное окно: название, назначение,
установленность, требуемые компоненты, доступные устройства, память и лицензия.
В U1 достаточно текущего рабочего варианта и места будущего расширения;
добавление новых моделей и демонстрационных результатов не требуется.
Сложные параметры доступны через дополнительные окна, на главном экране — простые действия.
В U1 предусмотреть понятное поле заметки к генерации и доступ к свойствам трека/
проекта и экспорту. Подробная карточка тегов не должна перегружать узкие колонки;
точное расположение согласовать в ТЗ интерфейса. Рабочее хранение и экспорт
обозначать раздельно, без списка технических форматов внутри выбора модели.

### 4.1. Общий контракт возможностей

Это предложение по устройству программы, а не новая обязательная терминология для пользователя.
Движок сообщает, умеет ли он: работать с текстом песни; создавать/принимать план;
принимать мелодию или аудио; выдавать промежуточные токены; создавать варианты;
продолжать этап; повторять сохранённое задание; экспортировать нужный формат.
Нельзя требовать ABC, AR/NAR, два seed или одинаковые этапы от каждой модели.
Неподдерживаемые пожелания должны иметь понятное обозначение, а не молча теряться.

Статус, скрипач, время и журнал остаются общими. Исполнитель передаёт свои этапы;
цвета принятых стадий YuE2 сохраняются, новые стадии получают осмысленное соответствие.
Если процент неизвестен, показывается неопределённый прогресс, а не выдуманная точность.
Пауза может означать безопасную остановку с повтором незавершённого этапа;
её нельзя выдавать за сохранение внутренних вычислений, если движок этого не умеет.

Предлагается версионированная запись задания: движок/модель/точность/версии,
исходные пожелания, реально отправленный запрос, эффективные настройки, именованные
источники случайности, этапы и артефакты, устройства, причины отказов и состояние.
Сначала сохраняется совместимость с существующими заданиями и результатами YuE2.
Точные интерфейсы и формат хранения определить в ТЗ реализации, без создания монолита.

### 4.2. Обычная проверка U1

Проверить сохранность текста и выбора при переключениях, запуск существующего YuE2,
статус, паузу/отмену, готовый WAV, повтор, карточки, путь и буфер обмена;
проверить узкое окно, масштаб Windows, разделители и доступность кнопок.
Проверка токенов, памяти, лицензий и штатной догрузки компонентов остаётся действующей.
Большой benchmark русского вокала не является условием приёмки этой вёрстки.

## 5. U3/U4 — YuE2 Studio как следующий кандидат

Речь о Windows-проекте [timoncool/YuE2-Studio](https://github.com/timoncool/YuE2-Studio),
а не о любом одноимённом интерфейсе. README подтверждает Rust/React/Tauri и
отдельный headless `music-server`; для интеграции нужно закрепить конкретный commit
и набор зависимостей. Указанная в исходной заметке версия 3.4.0 — ориентир той заметки,
не выбранная и не проверенная версия для поставки ЛОПАТЫ.

Предлагаемая связь: WPF ЛОПАТЫ → адаптер → локальный `music-server` → `yue-server` → модель.
Заметка указывает типовые порты 8791 и 18087: это ориентиры обнаружения, не хардкод.
Чужое React-окно не заменяет рабочее окно ЛОПАТЫ. Сначала самостоятельный headless
процесс; перенос Rust-кода внутрь или собственный мост рассматривать только при
конкретной проблеме такого подключения.

| Возможность из заметки | Для чего нужна | Что выяснить при её подключении |
|---|---|---|
| Keep / Words | Лучше удерживать слова и порядок строк | Где действует: план/семантика; какие именно ограничения поддерживает выбранная версия |
| Exact checkpoint / audio tokens | Повторно озвучивать сохранённую последовательность, отделять композицию от исполнения | Какие артефакты сохраняются, совместимость версий; одинаковый seed сам по себе не обещает идентичный WAV |
| Batch score-plan selection | Сначала несколько планов, затем выбор и дорогой синтез только нужных | Очередь N планов → выбор M → аудио; ручной выбор раньше необязательной автоматической оценки |
| Повторяющиеся секции, chord mirroring | Удерживать повтор припева и музыкальную структуру | Отличать намеренный повтор текста от ошибочного зацикливания |
| Полные sampling-настройки | Управлять ABC и семантической последовательностью отдельно | Реально доступные диапазоны, значения по умолчанию, effective request |
| Раздельные AR/NAR LoRA | Возможная будущая адаптация композиции/звучания | Совместимость конкретных адаптеров; влияние на русский не доказано |

Архитектура постоянного сервера потенциально позволяет сохранять модели в памяти,
использовать готовые токены и уменьшить повторную подготовку. Это не доказательство
ускорения или лучшего русского в ЛОПАТЕ. Нужны владение процессом, изоляция заданий,
health/status, отмена, восстановление, освобождение ресурсов и безопасный локальный API.
Общие жизненный цикл, фон/трей и учёт задач ЛОПАТЫ распространяются и на новый адаптер.

Для первого рабочего подключения: закреплённые исходники/API, headless-запуск,
один проверенный путь «запрос → WAV», статусы/отмена, лицензии, доставка и аппаратная
проверка. Затем отдельно включаются поддерживаемые действия. Детальное сравнение
с нынешним исполнителем, качества BF16, Keep/Words и повторяемости находится в R.

MIT в карточке репозитория — не лицензия всех его весов, кодеков и транзитивных
зависимостей. Перед поставкой проверить минимальный состав music-server/music-engine,
runtime, модели, notices и права распространения. Результат занести в REESTR и штатный
лицензионный каталог; сейчас лицензия комплекта целиком не признана проверенной.

## 6. U5 — связанные регуляторы, а не декоративные ползунки

[ТЗ U5](Архив/2026-10-07_Музыка_U5_Круг_настройки_и_пресеты.md) создано 07.10.2026 после
согласования пользователя. [Исследование механизма, ComfyUI и отзывов](../Документы_проекта/Исследования/2026-10-07_U5_Круги_YuE2_теоретическая_подготовка.md)
обосновывает группировку; численные траектории не признаны откалиброванными.
Реализовано в 0.4.8-dev, ТЗ выполнено и принято пользователем 07.10.2026.
Визуальная приёмка подтверждена; реальная польза регуляторов и рецептов,
передача эффективных значений и влияние на ABC/WAV требуют практической проверки
в отдельной ветке R4. Сравнительные испытания этим закрытием не запускаются.
Передача пожеланий оставлена без изменений по уточнению пользователя.
Агент не проводил настоящих генераций и сравнительной ветки R; публикация разрешена.

Согласован один круг с пузырьком в стиле круглого пузырькового уровня: перекрестие,
концентрические кольца и полупрозрачный перетаскиваемый маркер. Центр — defaults
конкретной модели, расстояние — сила изменения, диагональ — обе оси.

| Элемент | Направления | Группа влияния YuE2 |
|---|---|---|
| Горизонталь | Композиция предсказуемее / свободнее | ABC temperature, top_p, top_k |
| Вертикаль | Исполнение предсказуемее / свободнее | Semantic temperature, top_p, top_k |
| Отдельный короткий регулятор | Сила влияния задания: автоматически либо слабее / сильнее | Semantic CFG для слов и музыкальных пожеланий одновременно |

Музыкальные пожелания уже есть: передавать их из существующей колонки в Style,
не создавать дублирующий выбор. Круг и технический пресет не переписывают Lyrics
и не дописывают скрытые пожелания. Прежние два круга с целями «порядок/верность
тексту/экспрессивность» остаются в исходной идее как происхождение, не текущий план.

Найденные community-рецепты разрешены как экспериментальные пресеты; начальный
каталог и правила адаптации приведены в ТЗ. У каждого — источник, назначение,
исполнитель и реальная область применённых параметров. Полный Comfy-рецепт с
acoustic CFG/другим solver не выдаётся за полностью совместимый native-пресет.

Замысел согласователя: намерение → мета-регуляторы → согласование зависимостей →
реальные параметры. Ручные переопределения сохраняются; seed, варианты и ресурсы
остаются отдельными. Настройки не обещают проверенного улучшения до целевой проверки.

Нативные семейства, которые нельзя потерять при дальнейшей работе:

- ABC и Semantic независимо: temperature, top_p, top_k, repetition penalty,
  penalty window, min_tokens, max_tokens.
- CFG/guidance; CoT full/melody/off; LM seed и noise/sound seed;
  LM batch и synth batch; ODE/flow steps; peak clip.
- Длительность, варианты, формат и параметры экспорта, включая битрейт при его поддержке.

CoT остаётся выбором режима, а не плавной шкалой. Качество/скорость через ODE,
длительность, варианты, WAV/MP3 и экспорт не нужно насильно помещать в круги.
Набор определяется исполнителем, а не общим списком выдуманных возможностей.

Три уровня интерфейса: обычный — круги/короткие эффекты/профиль;
расширенный — понятные цели с величинами; экспертный — реальные эффективные значения.
Внутреннее кольцо показывает состояние параметров: ● по умолчанию, ◉ изменён,
○ минимален, × выключен, стрелки ↑/↓ направление изменения. Значение должно
читаться также текстом; цвет или значок не являются единственным объяснением.

Ручное изменение закрепляет параметр в режиме «Вручную». Движение круга не
перезаписывает его молча; видны собственный профиль и число переопределений.
По уточнению пользователя круг и экспертное окно двусторонне отражают общие
эффективные значения: экспертные изменения обновляют пузырёк хотя бы приблизительно,
а движение круга обновляет технические значения с учётом закреплений. Приближение
касается отображения, не округления/подмены параметров. Наборы пресетов у простого
и экспертного управления отдельные; применение любого синхронно влияет на общий
профиль. Старые пресеты остаются экспертными; без координат отображаются приблизительно.
Возврат в «Авто» или к профилю — явное действие. Согласователь пересчитывает
целый непротиворечивый профиль, учитывая фиксированные значения.

Три слоя логики: базовая траектория, компенсаторы конфликтующих целей, исключение
эмпирически плохих областей в обычном режиме. Диапазон upstream не считается
автоматически безопасной областью. Экспертный выход за рекомендованное имеет пометку;
жёсткие ограничения памяти, контекста и допустимого запроса остаются обязательными.
Числа из эскиза (82/91/47/63 и ступени 0–30–60–80–100) — иллюстрации,
не готовые пресеты и не формулы для реализации.

Для каждого регулятора нужны короткие пояснения: что обычно меняется, возможная
цена изменения и когда применять. «Верность тексту» не обещает идеальный вокал.
Критерий успеха — измеримое изменение нужного свойства через согласованную группу
параметров. Красивый круг, меняющий один случайный параметр, этому не соответствует.
Если связи пока неизвестны, интерфейс можно подготовить, но активное обещание
улучшения включается после целевой проверки R4, а не на основании рисунка.

## 8. Аппаратная универсальность и поставка

Качество и стабильность важнее скорости, затем удобство и минимальный размер.
Минуты ожидания допустимы при существенном выигрыше качества. Тестовая RTX 4090
и 24 ГБ VRAM не определяют предел архитектуры или обязательное оборудование пользователя.

В исследовании качества сначала рассматривать полную точность. Если модель не
помещается на GPU, выяснить поддержку CPU offload, системной RAM, разделения
encoder/decoder/LLM/DiT/VAE по устройствам, mmap/streaming и последовательных стадий.
Квантование оценивать после этих вариантов. Это порядок рассмотрения, а не обещание,
что любая модель поддерживает каждый способ или заработает на любом ПК.

Для поставки отдельно фиксировать: возможности upstream, реализованный адаптер,
доступный комплект библиотек и физически испытанное оборудование. Выбор устройств
и память проверять до запуска. Библиотеки под железо получать через штатный загрузчик
первого запуска главного окна; веса — через существующий механизм моделей/лицензий.
Не вводить скрытые установщики, хардкод CUDA0 или обязательную NVIDIA без основания.

## 9. Сохранённые дальние направления

Русская LoRA/адаптер, отдельная подготовка мелодии, MIDI→ABC→YuE2, редактор мелодии,
управляемый певческий движок поверх инструментала, чат стихов и улучшение рифмы
остаются направлениями развития. Отображение мелодии как высоты во времени не следует
путать с формой звуковой волны. Qwen/иной текстовый помощник может готовить пожелания
и структуру задания, но не заменяет исполнитель музыки.

Эти идеи сохраняют связь с [первоначальным музыкальным ТЗ](Архив/2026-10-05_Музыкальный_сценарий_YuE2_MIDI.md).
Они не возвращают закрытые этапы в работу. Конкретный следующий ТЗ — U1;
ветка R и её материалы уже готовы к выборочному использованию при необходимости.

## 10. U2 — рабочая музыка, экспорт и метаданные

Реализация текущего объёма выделена в [ТЗ U2 от 07.10.2026](Архив/2026-10-07_Музыка_U2_Форматы_и_метаданные.md).
Согласованы четыре формата: Opus по умолчанию 320 кбит/с, MP3, FLAC и WAV;
lossy 160/192/256/320. Один дополнительный формат через «+»/«−», оба файла из
исходного PCM, одна карточка. Исполнитель/название раздельны; комментарий
сверху. Происхождение, слова, фактические seed и настройки внутри файла.
В 0.4.10-dev текущий объём выполнен и принят пользователем 08.10.2026.
ТЗ архивировано; прежний разовый запрет публикации снят командой закрытия 08.10.2026.
Проекты и история запросов реализованы отдельным принятым ТЗ. Обложка, дополнительное сведение и произвольная
конверсия старой библиотеки остаются дальнейшими пунктами карты.

Дополнение пользователя от 07.10: большие серии создают много неудачных WAV,
занимающих место; номер дубля растёт, а подпись в имени остаётся старой. После
десятков файлов без журнала трудно восстановить смысл. Каждый трек должен
объяснять своё происхождение и назначение даже за пределами папки проекта.

### 10.1. Рабочий формат не зависит от выхода модели

Предпочтительный кандидат компактного хранения — **Ogg Opus** с расширением `.opus`.
Backend может выдавать WAV, FLAC, PCM, MP3 или другой реально поддерживаемый результат.
Общий слой ЛОПАТЫ получает его, приводит к выбранному способу хранения, записывает
теги и добавляет в библиотеку. Собственный аудиоконтейнер не вводить;
MKA только ради метаданных не нужен. Внутренняя запись задания остаётся отдельной.

Ogg Opus предусматривает метаданные в comment header; это стандартный формат,
а не новый контейнер ЛОПАТЫ: [RFC 7845, §5.2](https://www.rfc-editor.org/rfc/rfc7845.html#section-5.2).
Отображение конкретных тегов в Проводнике, плеерах и сервисах зависит от их поддержки;
не обещать одинаковую индексацию lyrics и custom tags во всех сторонних программах.

Предлагаются режимы проекта:

| Режим | Рабочее хранение | Назначение |
|---|---|---|
| Компактно | Ogg Opus | Обычная библиотека и массовый перебор дублей; предпочтительный режим концепции |
| Сохранить исходное качество | FLAC для совместимого lossless-аудио либо сохранённый исходный мастер | Монтаж, дальнейшая обработка, ценные результаты; точное представление определяется реальным выходом backend |

Opus — сжатие с потерями. Последующее сохранение в WAV/FLAC не восстанавливает
отброшенную информацию. FLAC из Opus — копия декодированного звука без новых
потерь на этом шаге, но не исходный lossless master. Для исходного качества
нужно сохранить мастер до сжатия. Если сама модель отдаёт только lossy-аудио,
конвертация тоже не создаёт исходник более высокого качества.
Описание кодека: [официальный проект Opus](https://opus-codec.org/).

Битрейт/VBR, библиотека кодирования, поддержка плеером, режим по умолчанию и
политика хранения мастера фиксируются в ТЗ U2; сейчас значения не придуманы.
«Нормализация» в этой схеме означает приведение формата. Автоматическое изменение
громкости, микса, каналов или музыкального содержания этим дополнением не заказано.

### 10.2. Экспорт — отдельная операция

Намеченные форматы: FLAC, WAV, MP3, Opus. Выбор определяется наличием проверенного
кодировщика и нужной совместимостью. Источник экспорта — сохранённый мастер,
если он есть; иначе рабочий файл с честным указанием его происхождения.
Метаданные переносятся в поддерживаемые поля целевого формата. При том же формате
не выполнять ненужное повторное lossy-кодирование; правка заметки не должна портить звук.

FLAC нужен для сохранения качества подходящего исходника, WAV — для совместимости
и монтажа, MP3 — для бытового обмена, Opus — для компактного хранения/обмена.
Экспорт создаёт отдельный результат и не портит рабочую библиотеку.

### 10.3. Автоматические сведения и пользовательская заметка

| Группа | Что сохранять |
|---|---|
| Обычные музыкальные поля | Title; Artist/Author; Album/Project; Genre; Date/Year; Lyrics; Comment/Description |
| Происхождение | Версия ЛОПАТЫ; модель и её вариант; precision/quantization; backend и его версия; время генерации; проект/ID; номер трека и дубля |
| Повторяемость | Seed, а для YuE2 оба: LM seed и Sound seed; не сливать разные источники случайности в одно неясное число |
| Пользователь | Название, автор, альбом, **заметка**, оценка, личный комментарий; допускается наследование известных полей проекта |
| Альбомная структура | Album, Track number, Disc number, Project, Title, Artist, Year/Date, Genre, Comment, Lyrics; позже Cover |

Автоматически записывать всё достоверно известное программе. Автора и оценку не
придумывать; неизвестное поле остаётся незаполненным. Для lyrics сохранять именно
отправленный текст с секциями и пометками: это условие генерации, а не доказанная
расшифровка того, что модель в итоге спела.

Custom tags при поддержке: `LOPATA_MODEL`, `LOPATA_MODEL_VARIANT`, `LOPATA_PRECISION`,
`LOPATA_BACKEND`, `LOPATA_VERSION`, `LOPATA_SEED`, `LOPATA_PROJECT`;
раздельные LM/Sound seed и версия схемы также должны иметь однозначные ключи.
Окончательное соответствие полей тегам Opus/FLAC/MP3/WAV определить при реализации,
не считать произвольное имя автоматически общепринятым стандартом всех форматов.

Отдельное человеческое поле «Заметка» хранит смысл дубля, например:
«без mood», «только blues», «проверка женского вокала», «плохой порядок строк»,
«лучший русский из серии», «тест Keep/Words», «BF16, контроль»,
«тот же ABC, другой sound seed». Его можно уточнить после прослушивания.
Вариант получает снимок своих условий; новые запуски не меняют сведения прошлых.

Имя файла остаётся коротким, например `Лопата - Будильник_17.opus`.
Оно не заменяет базу данных и не обязано содержать модель, seed, жанры и результат
оценки. Заметка и техническое происхождение должны переживать переименование файла.
Обложка в стандартном поддерживаемом поле — будущее расширение, не минимум U2.

### 10.4. Что остаётся вне обычного аудиофайла

Не вкладывать в теги полный ABC, semantic tokens, checkpoint tensors, KV cache,
полные runtime logs, внутренний JSON request и сырые diagnostic traces.
Небольшие полезные seed/версии допустимы; лабораторный дамп — отдельный артефакт.

Есть три уровня хранения: обычный аудиофайл с полезными тегами; служебная запись
задания для работы/повтора; подробный пакет опыта R с request, ABC, tokens, WAV,
логами, хешами, timings, ASR и оценками. Отказ от лабораторных тегов не означает
удаление существующих данных задания, необходимых функции повтора.

### 10.5. Безопасное завершение и обычные проверки U2

```text
Выход backend → временный результат → кодирование/теги → проверка
             → фиксация готового файла и записи библиотеки
             → очистка только ненужного временного файла по политике хранения
```

Проверить декодирование, длительность, ожидаемые каналы, читаемость русского текста
и тегов. Только затем результат считается готовым. Ошибка/отмена кодирования не
удаляет единственный исправный исходник и не оставляет ложную готовую карточку.
Мастер режима исходного качества и исследовательские артефакты не являются
временным мусором. Старые пользовательские WAV не конвертировать и не удалять
задним числом как побочный эффект включения нового хранения.

В обычную приёмку входят плеер/перемотка/длительность Opus, теги и lyrics с кириллицей,
заметка после переименования/экспорта, оба seed, отсутствие лишнего lossy-перекодирования,
ошибка/отмена/нехватка места и сохранность мастера. Кодек/теггер и их лицензии
проверяются перед поставкой. Большой слепой тест битрейтов и сравнение музыкальных
моделей остаются необязательной веткой R, а не условием начала U1.
