# Узкая диагностика запуска литературного runtime — 2026-09-22

Статус: диагностический проход завершён; причина внешнего сбоя не установлена. Исправления продукта, изменение архитектуры, версии, сборка установщика и публикация запрещены текущим заданием и не выполнялись.

## Результат

На локальном ПК 12 из 12 запусков минимального стенда достигли готовности модели: по три запуска для каждой комбинации Detailed logging OFF/ON и ASCII/кириллического пути к GGUF. Воспроизвести зависимость успешного старта от подробного журналирования не удалось. Это не опровергает наблюдение пользователя на ПК друга и не доказывает отсутствие ошибки в полном приложении.

Windows-трасса содержит девять полных запусков (04–12), часть запуска 03; запуски 01–02 начались до записи. WPR сообщает EventsLost=0. У девяти полных запусков совпадают наборы загруженных образов, успешно завершаются все шесть зафиксированных открытий GGUF в каждом запуске. ACCESS DENIED в записанных FileIO/OperationEnd этих процессов до готовности не найден.

## Что проверяли

Использована неизменённая опубликованная AIHub.dll из Runtime/Publish/LOPATA-0.2.5-beta-win-x64. Стенд вызывает реальные LiteraryChatRuntime.Arguments и LiteraryRequestDiagnostics из этой сборки. Backend — llama.cpp b9442, win-cuda-12.4-x64; модель Qwen3.8-27B-Ridge 3.7 bpw, 12 599 187 008 байт.

Для сравнения созданы два hardlink на один существующий GGUF: ascii123/model.gguf и кириллица/model.gguf. Содержимое модели не менялось и не дублировалось. В обоих вариантах managed File.OpenRead прочитал заголовок GGUF. Каждый запуск использует свежий процесс, свободный порт и отдельный каталог slot-cache. Аргументы модели одинаковы, кроме путей и порта. LLAMA_ARG_* удаляются из среды дочернего процесса, как в приложении. stdout/stderr перенаправлены и читаются асинхронно; общий журнал ведётся в обоих режимах, Detailed — только при ON. После успешного HTTP /health стенд завершает только собственный сервер. Ожидание ограничено 90 секундами.

Параметры: -c 0, -np 1, -ngl 99, --device CUDA0, --fit on, --fit-target 1507, --fit-ctx 1024, --cache-ram 0, --no-context-shift, --offline, --jinja, --slots, --reasoning-format deepseek, -fa auto, -n -1, -t 8, -tb 8. Запас памяти 1507 MiB зафиксирован по внешнему журналу; полный штатный расчёт FitMarginAsync стенд не вызывает.

Это проверка границы запуска процесса, а не повтор всего UI/PrepareAsync: не повторяются discovery/лицензии/проверка модели/OwnedProcessRegistry и переключение настройки через окно. Дополнительная временная разметка стенда присутствует в обоих режимах и сама может влиять на редкую гонку. Генерация литературного ответа после готовности не проверялась.

## Системная трасса и порядок событий

Пользователь из административного PowerShell выполнил:

```powershell
wpr -start GeneralProfile -start FileIO -filemode
wpr -stop "H:\AI_HUB\_backups\20260922_runtime_probe\startup.etl"
```

WPR подтвердил успешное сохранение. Интервал ETL: 2026-09-21 20:26:16.9695581–20:29:36.2249384 UTC (локально 2026-09-22). Размер 10 423 894 016 байт, около 9,71 GiB. ProcMon не устанавливался. Для чтения использована Microsoft.Diagnostics.Tracing.TraceEvent 3.2.6 в отдельном диагностическом проекте; зависимости продукта не изменялись. Метод чтения ETW соответствует [официальному руководству Microsoft TraceEvent](https://github.com/microsoft/perfview/blob/main/documentation/TraceEvent/TraceEventProgrammersGuide.md).

События соотнесены с PID и временным окном каждого запуска, от before_start до outcome. Это существенно: Windows переиспользует PID; события прежнего процесса с тем же PID нельзя приписывать модели. В предварительной выборке обнаружен такой посторонний tzutil.exe, после ограничения окна он исключён. Опрос Process.Modules из стенда оказался ненадёжным для подсчёта DLL; выводы о библиотеках основаны на Image/Load из ETW.

В девяти полных запусках:

- Process/Start → загрузка backend/CUDA-библиотек → открытие GGUF → fitting/загрузка/прогрев по stderr → успешный /health. Первое открытие GGUF примерно через 0,18–0,22 с после Process/Start.
- Загружены llama-server-impl.dll, llama.dll, ggml-base.dll, ggml.dll, ggml-cuda.dll, cudart64_12.dll, cublas64_12.dll, cublasLt64_12.dll, nvcuda.dll и CPU-варианты ggml. Наборы образов совпадают, число событий загрузки может различаться из-за повторных загрузок. Взаимный порядок отдельных DLL отличается; устойчивого отличия OFF от ON не выявлено.
- Шесть FileIO/Create для model.gguf на запуск сопоставлены с FileIO/OperationEnd по IrpPtr: все завершились NTSTATUS 0x00000000.
- В каждом полном запуске присутствуют 15 NAME NOT FOUND (0xC0000034) и 53 PATH NOT FOUND (0xC000003A) среди OperationEnd. Это одинаковые поисковые обращения, в том числе к необязательным профилям NVIDIA, кэшам, языковым ресурсам и llama-server.exe.mun. Ошибок открытия GGUF среди них нет; все процессы после них достигли готовности. Наличие таких статусов само по себе не означает отказ загрузки модели.
- ACCESS DENIED (0xC0000022) среди записанных FileIO/OperationEnd целевых процессов до готовности не найден. Это ограниченный вывод о захваченных файловых событиях, не универсальное доказательство отсутствия любых системных отказов.
- Подробные JSONL создаются только при ON; общий лог и инструментальные события пишутся при обоих состояниях. Никакой связанной с ON смены аргументов, пути GGUF или рабочего каталога backend не обнаружено.

## Сопоставление с ПК друга

См. [первичный отчёт внешнего теста](2026-09-22_внешний_тест_литературы_0.2.5-beta.md).

На ПК друга i7-13700KF / 63,83 ГБ RAM / RTX 4080 SUPER 15,99 ГБ VRAM исходные журналы подтверждают отдельную ошибку native-открытия GGUF по кириллическому пути (No such file or directory), при том что managed-код видел файл. После переноса на ASCII последняя неудачная попытка обрывается на fitting без достаточного объяснения; успешная попытка после включения подробного журнала сохраняет сведения о готовности. Причина второго эпизода не установлена.

На локальном ПК RTX 4090 / 24 ГБ, драйвер 616.56, ACP и OEMCP Windows = 65001 (UTF-8). Кириллица здесь открывается и без подробных журналов. Кодировка ПК друга не измерена. По уточнению пользователя, версия и источник Windows почти идентичны, а на локальном ПК больше средств разработки. Поэтому различие версии Windows не объявляется причиной; возможные различия системной кодировки, библиотек, драйвера и окружения остаются непроверенными условиями.

Локальный автоматически подобранный контекст — 155392, в успешном внешнем запуске — 27648. Одинаковые команды не означают одинаковое распределение памяти на разных GPU. Прямая переносимость результата ограничена.

Просмотр кода выявляет диагностический пробел: в StructuredAnalysisAsync запись исключения через diagnostics.Write отсутствует в Detailed-файле при OFF. Поэтому по неполному внешнему журналу нельзя надёжно отличить таймаут, native-выход и ошибку управляющего кода. Это наблюдение о доступности доказательств, а не установленная причина сбоя. Код не исправлялся.

## Артефакты и воспроизводимость

Все сырые данные и стенд находятся локально в игнорируемом каталоге `_backups/20260922_runtime_probe`:

- Probe.csproj, Program.cs — минимальный стенд;
- binary-hashes.json — SHA-256 использованных бинарных файлов;
- results.jsonl; каталоги 01–12 с events.jsonl, shared.log, Detailed при ON;
- startup.etl — исходная системная трасса;
- trace-reader — отдельный считыватель ETW, trace-summary.json, trace-filtered.jsonl;
- analyze.py, analysis.json, analysis-summary.txt — сопоставление и результаты;
- docs-before — копии трёх изменяемых документов истории.

Стенд собирался командой `dotnet build _backups/20260922_runtime_probe/Probe.csproj -v:q`, затем запускался через `dotnet .../Probe.dll <каталог стенда> <полный путь llama-server.exe>`. Для повторения нужен НОВЫЙ каталог результатов с двумя hardlink и той же структурой; повторный запуск в прежний каталог перезапишет events.jsonl и смешает results.jsonl. Текущие доказательства сохранять неизменными. Новые запуски в рамках этого прохода не требуются.

ETL содержит системную активность и частные пути; его и сырые логи не включать в публичную документацию/коммит. Ничего из приватных данных друга не публиковалось. Hardlink модели не является новой копией весов.

## Итог и границы остановки
