## 3. Главные принципы

- Делать минимально достаточные правки без лишней ломки текущего UX.
- Все изменения должны быть прозрачными, объяснимыми и проверяемыми.
- AI_HUB строится как Codex-подобная рабочая среда для локальных моделей: модель не считается всемогущей, а получает инструменты, контекст, правила доступа, логи, проверки фактов и понятный контур выполнения задач.
- Если можно обойтись без новой внешней зависимости, сначала рассматривать более простое решение.
- Перед новой функцией сначала анализировать зависимый код и похожие места в проекте.
- Не хардкодить пути, порты, `localhost`, IP и имена backends, если уже есть настройки, discovery или конфиг.
- Перед внедрением проверять совместимость с:
  - интерфейсом;
  - ядром приложения;
  - локальной базой;
  - AI-хранилищем;
  - backends;
  - сборкой;
  - установщиком/обновлением, если они затронуты.

### HARD RULE — не создавать новые монолиты без причины

При добавлении новых функций сначала оценивать, не превращает ли правка текущий файл в новый центр накопления логики. Если новая логика имеет самостоятельный смысл, повторно используется, затрагивает отдельный runtime-сценарий или заметно увеличивает файл, её нужно по возможности сразу выносить в отдельный компонент, helper, service или модуль.

Крупные orchestration-файлы должны оставаться точками сборки и связи, а не местом постоянного хранения всей новой бизнес-логики.

Допускается временно оставить код в текущем файле, если вынос сейчас создаёт больше риска, чем пользы. Но в таком случае нужно явно понимать причину, держать правку компактной и при следующем связанном проходе рассмотреть вынос отдельно.

## 7. Проверки и safe-start

### HARD RULE

Не обходить safe-start, build/check и scanner без действительно веской причины.

После кодовых правок запускать проверки, соответствующие затронутой части проекта.

Для предполагаемого стека **C# / .NET / WPF** базовые проверки:

- `dotnet restore`
- `dotnet build`
- `dotnet test`, если тесты уже есть
- запуск приложения через штатный dev/start-скрипт, если он уже создан

Если проект позже получит другие части, например Python-инструменты, локальный API, web-компоненты или native backends, проверки должны быть расширены по соответствующим правилам.

### HARD RULE — сборка установщика только по команде

Тестовый установщик не собирать автоматически после каждого ТЗ.

Собирать установщик только по прямой команде пользователя, кроме случаев, когда тест именно установленной версии критичен для задачи, например проверяется поведение установщика, uninstall, ярлыки, путь установки, перенос настроек или ошибка проявляется только в установленной сборке.

Если установщик не собирался, в финальном ответе и истории явно писать, что обычные проверки прошли, а установщик не пересобирался по правилу.

### HARD RULE — публикация установщика только по отдельной явной команде

Сборка установщика и публикация в GitHub Releases — отдельные действия. Публиковать установщик и соответствующий update-feed только по явной команде пользователя на публикацию. Команда может сразу разрешать сборку и публикацию; повторное подтверждение тогда не требуется.

Успешная сборка, тестирование, приёмка или закрытие ТЗ, а также обязательный commit/push исходников при архивировании ТЗ сами по себе не разрешают публикацию установщика. Исключение, разрешающее необходимую тестовую сборку, не разрешает её публикацию. Пользователь может собирать установщики для проверки до исправления багов.

Внутренняя версия остаётся `-dev`. Публичный тестовый установщик выпускается с суффиксом `-beta`, без дополнительных цифр после beta; dev-установщики не публикуются. Публиковать только выбранный и проверенный артефакт, без известных явных багов, через отдельный `Инструменты/publish-installer.ps1`. Обычная сборка, включая `-PublicBeta`, ничего не публикует; `-Publish` применяется только при наличии указанной команды пользователя.

Установщики хранятся как вложения GitHub Releases. Политика хранения: первый установщик текущей линии major.minor и два последних (2–3 уникальных установщика). Очистку выполнять отдельным явным действием по руководству, а не побочным эффектом сборки или commit/push. Порядок проверки, публикации, продолжения черновика и очистки: [Обновления и публикация](../Документы_проекта/ОБНОВЛЕНИЯ.md).

### HARD RULE — не ухудшать baseline проверок

После любой кодовой правки Codex обязан проверить, что не добавил новые ошибки или предупреждения в доступных проверках проекта.

Если полный check ещё красный из-за старого baseline, нужно явно сравнить результат с baseline и подтвердить, что в изменённых файлах не появились новые hard errors или warnings.

Нельзя прятать новые check-проблемы через грубые заглушки, отключение анализаторов, удаление кода без проверки UX, смену API/storage contracts или большой соседний рефактор без отдельного согласования.

## 8. Windows и большие патчи

На Windows для сложных PowerShell-команд, диагностики, backup и проверок предпочитать `pwsh` / PowerShell 7, если он доступен. Обычный `powershell.exe` использовать как fallback.

### HARD RULE

Не отправлять гигантские patch-body одним куском.

Опасными считать патчи, которые:

- тянут на `600+` строк;
- смешивают несколько файлов;
- содержат длинные встроенные текстовые блоки;
- меняют архитектуру и UX одновременно.

Предпочтительная стратегия:

- один файл за раз;
- один логический блок за раз;
- маленькие патчи;
- после каждого крупного шага — проверка сборки или хотя бы синтаксиса.

Если правка разрастается:

- остановиться;
- разбить на подпатчи;
- не зацикливаться на повторении одной и той же гигантской команды.

## 10. Лицензии

При добавлении управляемого компонента разработчик обязан включить его ID в
`Исходники/AIHub/Licenses/catalog.json` через подготовку лицензионного каталога,
указать источник, дату проверки, способ поставки, проверенные условия и неизвестное.
Подключать штатные загрузки/прогрев к `ComponentLicenseGate`, не создавать отдельные
галочки и файлы согласия для каждого сценария. Код не определяет лицензии сам.
Редакция Terms меняется при изменении условий; обновление даты проверки само по себе
не отменяет согласие. После обновления каталога согласовать installer.txt и шаблон
записи установщика через `Инструменты/prepare-license-catalog.ps1`.
Неполные сведения описывать честно с датой и ссылкой; ознакомление не заменяет
отсутствующие права. Для реально распространяемых файлов сохранять оригинальные
лицензии/NOTICE и выполнять применимые требования к исходникам.

При добавлении новых зависимостей, моделей, backends или инструментов обновлять:

- `H:\AI_HUB\Документы_проекта\REESTR.md`

Всегда различать:

- runtime-зависимость;
- developer tooling;
- внешний инструмент;
- встроенную библиотеку;
- AI-модель;
- backend.

Фиксировать:

- название;
- назначение;
- лицензию;
- источник;
- версию;
- можно ли поставлять вместе с программой;
- особые ограничения.

Для текущей лицензионной идеи проекта учитывать:

- код проекта: `GPL-3.0-or-later`;
- авторство и происхождение: `NOTICE.md`;
- название/логотип/официальный статус: `BRANDING.md` или `TRADEMARK.md`;
- зависимости: `THIRD_PARTY_NOTICES.md`.

## 11. Версионирование

### HARD RULE

Вести строгую нумерацию версий проекта.

Базовый формат:

- `0.X.Y` до первой стабильной публичной версии.

Правила:

- не менять номер версии молча;
- повышать среднюю цифру `X` при создании каждого нового полноценного пользовательского сценария; первый полноценный сценарий `Анализ изображений` переводит проект на `0.1.0`;
- после такого повышения начинать счёт исправлений и небольших улучшений этого сценарного этапа с `Y = 0`, а последующие кодовые доработки снова повышают `Y`;
- перед релизом или публичной сборкой явно фиксировать версию, тип релиза и состав изменений;
- при кодовых изменениях повышать `Y`, когда проект войдёт в фазу версионируемых сборок;
- при изменениях зависимостей, backends, моделей, установщика или формата данных фиксировать это в `REESTR.md` и релизных заметках;
- не публиковать release/update-feed, если артефакт реально не собран и не проверен.
- По возможности держать одну истину о версии программы. UI, окно About, статусные строки, установщик, updater, release notes и будущие модули должны читать версию из основного источника версии проекта, а не хранить отдельные ручные копии.

## 13. Повторяемые баги и каталог лечения

### HARD RULE

При повторном возникновении багов не гадать и не лечить по памяти.

Сначала сверять:

- `H:\AI_HUB\Документы_проекта\КАТАЛОГ_ПОВТОРЯЕМЫХ_БАГОВ.md`

Искать по маркерам:

- `[BUG:...]`
- `[TAG:...]`
- `[FIX:...]`
- `[PROC:REPEATED-BUG-RECOVERY]`

Порядок:

1. Сверить симптомы и гипотезу с каталогом.
2. Проверить, не был ли уже потерян старый известный фикс.
3. Только потом предлагать новое лечение.
4. Если повторяемый баг подтверждён и вылечен, обязательно дополнить каталог.

## 14. Безопасность AI-хаба

Для проекта AI_HUB дополнительно учитывать:

- не удалять пользовательские результаты без явного подтверждения;
- не удалять закреплённые модели;
- не скачивать и не запускать backends без понятного подтверждения пользователя;
- не менять системные настройки Windows без подтверждения;
- не выполнять опасные команды без подтверждения;
- не хранить secrets в коде и публичных документах;
- не давать моделям прямой бесконтрольный доступ к файлам, интернету, shell или системным настройкам;
- все действия моделей через инструменты должны проходить через правила, разрешения и логирование.

### Разрешение пользователя на закрытие AI HUB (2026-09-04)

- Codex может самостоятельно закрывать AI HUB, если это необходимо для
  текущей работы, без повторного запроса разрешения. Это разрешено и во время
  скачивания модели: штатное возобновление загрузки предусмотрено.
- Прямое текущее указание пользователя не закрывать приложение имеет приоритет.
- Предпочитать штатное закрытие и кратко сообщать о нём. Сохранять данные и
  учитывать несохранённые результаты; возобновление скачивания не гарантирует
  сохранность произвольной незавершённой операции.
- Разрешение относится только к AI HUB, не к игре или другим приложениям,
  и само по себе не разрешает запуск новых загрузок или длительных тестов модели.
