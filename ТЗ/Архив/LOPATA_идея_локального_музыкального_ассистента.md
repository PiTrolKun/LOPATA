# Идея: локальный музыкальный ассистент для ЛОПАТЫ

Дата: 2026-10-04

> **Связь с NabyScape — LOPATA Edition.** В музыкальной интеграции NabyScape заранее предусмотрят подключение ассистента к общему плееру ЛОПАТЫ. Голосовое управление и поиск по медиатеке будут реализованы позднее по отдельному ТЗ. [Рабочее ТЗ NabyScape](2026-11-18_NabyScape_LOPATA_Edition.md#подключение-будущего-музыкального-ассистента)

## Суть

Сделать в ЛОПАТЕ обычный локальный музыкальный проигрыватель с классическим ручным управлением кнопками, но дополнить его полноценным локальным голосовым управлением по аналогии с Алисой в умном доме.

ИИ не заменяет привычный интерфейс плеера. Он нужен для понимания естественных и неточных голосовых запросов пользователя и для поиска нужной музыки внутри собственной локальной коллекции.

Примеры запросов:

- «Включи Rammstein».
- «Поставь альбом Mutter».
- «Включи Du Hast».
- «Следующая».
- «Пауза».
- «Громкость 30 процентов».
- «Сделай потише».
- «Перемешай этот альбом».
- «Что сейчас играет?».
- «Включи ту песню КиШа, где мужик в лес пошёл».
- «Поставь что-нибудь у Nightwish про призрака, длинное такое».
- «Включи ту старую песню, где женщина поёт про дождь».

## Основной принцип

Ручное управление остаётся классическим: библиотека, кнопки воспроизведения, очередь, плейлисты, поиск, громкость.

Голосовое управление является вторым способом управления теми же функциями.

Базовая цепочка:

микрофон → локальный STT → распознанная фраза → разбор намерения → поиск по локальной медиатеке → команда проигрывателю

Простые команды вроде «пауза», «следующая», «громкость 50» могут обрабатываться без LLM обычными правилами.

Сложные и неточные формулировки передаются ядру, например Qwen3 8B, которое превращает запрос пользователя в структуру поиска.

Пример:

«Включи ту длинную песню Nightwish про призрака»

может быть разобрано как:

- исполнитель: Nightwish
- тема: ghost / призрак
- длительность: длинная
- тип поиска: смысловой
- приоритет: локальная библиотека пользователя

## Проблема локальных музыкальных коллекций

Нельзя серьёзно полагаться только на ID3-теги и имена файлов.

В локальных коллекциях часто встречаются файлы вида:

- `01 - track.mp3`
- `Rammstein-Du_Hast(320).mp3`
- `Nightwish - Ghost Love Score live 2005.mp3`
- `track07.flac`

Поэтому нужен отдельный слой автоматического определения и обогащения музыки.

## Обогащение медиатеки

Предлагаемая цепочка:

файл → попытка идентификации → интернет-обогащение → локальная карточка композиции → локальный RAG

### 1. Первичное определение

Использовать:

- имя файла;
- путь и структуру папок;
- существующие метаданные;
- предполагаемые исполнитель / название / альбом / версия.

### 2. Аудиофингерпринт

Если уверенность низкая, использовать аудиоотпечаток по типу Chromaprint / AcoustID.

Это позволяет определить композицию по самому звучанию, даже если имя файла и теги бесполезны.

Аудиофингерпринт является важной частью концепции, потому что он решает проблему плохо оформленных и скачанных из разных источников музыкальных коллекций намного надёжнее одного парсинга имени файла.

### 3. Интернет-обогащение

После определения композиции локальный парсер может подтягивать доступные сведения:

- правильное название;
- исполнитель;
- альбом;
- год;
- жанры;
- альтернативные названия;
- участники;
- краткое описание;
- связанные произведения;
- другие доступные данные о композиции.

Интернет используется только для пополнения локальных знаний о медиатеке.

После индексации обычное использование должно по возможности оставаться полностью локальным.

Ключевой принцип:

**Интернет нужен для пополнения знаний о медиатеке, но не для её использования.**

## Локальная карточка композиции

После идентификации для каждой песни создаётся внутренняя карточка.

Пример:

**Nightwish — Ghost Love Score**

- Альбом: Once
- Год: 2004
- Жанровая область: symphonic metal
- Вокал: женский
- Длительность: длинная композиция
- Темы и смысл: любовь, утрата, драматическая романтика
- Альтернативные названия и варианты написания
- Локальный путь к файлу
- Источники данных
- История прослушивания пользователя

Эти карточки формируют основу локального RAG.

## RAG и смысловой поиск

RAG нужен не для воспроизведения музыки, а для поиска по смыслу.

Можно хранить несколько слоёв данных:

1. Точные факты:
   - исполнитель;
   - название;
   - альбом;
   - год;
   - жанр;
   - длительность.

2. Смысловое описание:
   - о чём композиция;
   - ключевые образы;
   - настроение;
   - персонажи;
   - события.

3. Тексты песен:
   - только если они уже есть у пользователя или получены из допустимого источника;
   - не строить основу системы на массовом скрейпинге случайных сайтов.

4. Собственный аудиоанализ:
   - настроение;
   - энергичность;
   - вокал / инструментал;
   - примерный жанр;
   - BPM;
   - другие музыкальные признаки.

5. Пользовательский контекст:
   - что слушал недавно;
   - что часто включает;
   - избранное;
   - плейлисты;
   - что играло до или после конкретного трека.

## Поиск по кривым запросам

Система должна терпеть:

- неточные названия;
- ошибки STT;
- транслит;
- опечатки;
- неполные воспоминания;
- описание содержания вместо названия;
- описание звучания;
- ссылки на недавнюю историю прослушивания.

Примеры:

«Включи ту песню, где поётся про волка».

«Найди песню КиШа про лес».

«Включи что-нибудь тяжёлое с женским вокалом».

«Поставь тот трек, который я вчера слушал перед Rammstein».

«Включи что-нибудь из того русского рока, что я слушал на прошлой неделе, где мужской вокал и что-то про смерть».

## Гибридный поиск

Поиск желательно строить не на одном признаке, а на объединении нескольких источников.

Например:

- совпадение названия;
- исполнитель;
- смысл текста;
- смысловое описание;
- аудио-признаки;
- история пользователя;
- недавние прослушивания;
- плейлисты;
- избранное.

Вес разных источников можно менять в зависимости от формулировки запроса.

Если пользователь говорит:

«где поётся про...»

повышается вес текста и смыслового описания.

Если пользователь говорит:

«что-нибудь похожее по звучанию»

повышается вес аудиоанализа.

Если говорит:

«то, что я вчера слушал»

повышается вес истории.

## Поведение при неуверенности

Система не должна молча угадывать при двух почти равных кандидатах.

Пример:

«Ты имеешь в виду Ghost Love Score или Phantom of the Opera?»

Если файл определить не удалось, карточка может оставаться частичной:

- исполнитель неизвестен;
- название предположительное;
- источник данных не подтверждён.

Не выдумывать сведения для заполнения карточки.

## Голосовой ответ

TTS нужен только там, где ответ действительно полезен.

Например:

Пользователь: «Что сейчас играет?»

LOPATA: «Nightwish — Ghost Love Score».

Для простых команд голосовой ответ не обязателен:

«Пауза» → просто пауза.

«Следующая» → просто следующий трек.

## Архитектурная идея

ИИ не должен анализировать музыкальный поток при каждом воспроизведении.

Тяжёлая работа выполняется один раз при добавлении или индексации музыки:

- распознать файл;
- получить аудиоотпечаток;
- подтянуть сведения;
- сформировать карточку;
- построить embeddings / RAG;
- при необходимости провести аудиоанализ.

После этого голосовые запросы должны обрабатываться быстро.

Основной принцип:

**обычный музыкальный плеер + локальный голосовой ассистент + локальный RAG по собственной коллекции.**

Это не попытка заменить музыкальные сервисы и не аналог «Моей волны».

Цель — перенести удобство голосового управления в стиле Алисы на собственную локальную медиатеку пользователя.
