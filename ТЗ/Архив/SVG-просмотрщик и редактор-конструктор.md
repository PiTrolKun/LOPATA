# ЛОПАТА — SVG-просмотрщик, редактор-конструктор и пошаговая генерация

**Дата обсуждения:** 23 октября 2026 года  
**Статус:** сохранённая концепция для дальнейшего развития проекта; **не техническое задание и не утверждение о реализации всех функций**.  
**Контекст:** развитие уже существующего в ЛОПАТЕ сценария «Генерация векторной графики» на основе Qwen3.8-27B-Ridge 3.7 bpw. Локальные скриншоты пользователя показывали DEV-версию **0.6.10-dev**.

## 1. Главная идея

Не пытаться поместить все способы создания и изменения SVG внутрь одного окна генерации. Развить ранее обсуждавшуюся **пошаговую генерацию** в самостоятельную рабочую среду для векторной графики:

1. **Генератор SVG** создаёт целые иллюстрации по естественным запросам пользователя.
2. **Просмотрщик SVG** открывает готовые файлы, обеспечивает удобный масштаб и перемещение по изображению.
3. **Редактор-конструктор** открывает несколько SVG как отдельные **листы**, подобно вкладкам листов в Excel, и позволяет вручную переносить между ними объекты и группы.
4. **Встроенный мини-чат генерации** создаёт дополнительные векторные элементы прямо в рабочем процессе редактора, используя тот же путь генерации, но более узкие требования к результату.
5. Всё вместе работает с **настоящей векторной геометрией SVG**, а не с растровой копией изображения.

Короткая формула: **генератор создаёт материалы; просмотрщик показывает; редактор собирает; мини-чат добавляет недостающие элементы**.

- Короткий чат создания отдельных векторных объектов внутри редактора.
- Сохранение композиции, собранной из элементов разных листов, в полноценный SVG.

## 3. Интеграция с Windows: открыть SVG как обычный файл

**Желаемое поведение:** пользователь в Проводнике дважды щёлкает по файлу `.svg` либо выбирает «Открыть с помощью → ЛОПАТА». Приложение сразу открывает **просмотрщик** с этим файлом.

- Предусмотреть регистрацию ЛОПАТЫ как доступного обработчика типа `.svg` в Windows 11.
- Пользователь сам решает, назначать ли ЛОПАТУ приложением по умолчанию; установка не должна принудительно перехватывать ассоциации.
- Просмотр не должен требовать загрузки Qwen, музыкальных моделей или какого-либо другого ИИ. Работает как самостоятельная лёгкая утилита.
- Воспользоваться уже существующими и хорошо работающими масштабированием и панорамированием, показанными в просмотрщике генератора; оценить возможность выделения общего компонента просмотра.
- У просмотрщика есть явное действие **«Открыть в редакторе»**. Оно открывает текущий SVG как лист редактора (либо добавляет лист в уже открытый редактор).
- Просмотр SVG, его редактирование и генерация нового SVG — **три разных действия**, а не обязательная цепочка.

**Сценарий:** `Проводник Windows → файл.svg → просмотрщик ЛОПАТЫ → [Открыть в редакторе] → лист редактора`.

## 4. Редактор как гибрид Paint и Excel

Основная метафора — **свободное визуальное редактирование, как в Paint, с организацией рабочих пространств, как у листов Excel**.

### 4.1. Листы, а не физическая склейка файлов

Важнейшее уточнение из обсуждения: «склеить несколько SVG» **НЕ означает автоматически соединить файлы в единый XML-документ сразу при открытии**.

- Каждый открытый SVG получает собственную вкладку **листа внизу окна**, как в Excel.
- У каждого листа свой холст, содержимое, масштаб просмотра и элементы.
- Пользователь переключается между листами; исходные файлы остаются раздельными.
- Можно создать **пустой лист композиции**, взять нужную часть из одного SVG, скопировать на лист сборки, затем взять другую часть из другого SVG.
- Переносимые элементы на целевом листе становятся самостоятельными экземплярами, которые можно размещать, масштабировать и редактировать независимо от исходного листа.
- Можно копировать целую иллюстрацию, группу или отдельный элемент, если структура позволяет его выбрать.

**Аналогия:** на одном листе кот-рокер, на втором несколько гитар, на третьем декоративные рамки; на четвёртом пользователь собирает собственную композицию.

### 4.2. Лист, слой, группа, объект — разные понятия

- **Лист** — отдельное пространство документа/исходника (аналог Excel).
- **Слой** — логический порядок наложения элементов **внутри листа**.
- **Группа** — набор контуров и фигур, который можно выделять, копировать и преобразовывать вместе.
- **Примитив или контур** — непосредственный SVG-элемент: `path`, `circle`, `rect` и т. п.

Один нарисованный персонаж может состоять из десятков контуров и окружностей. Визуально это один кот, но технически это множество SVG-узлов. Поэтому «один объект» для пользователя **не означает одну XML-фигуру**.

### 4.3. Ручные инструменты — без обязательного ИИ

Основной ожидаемый набор для редактора:

- выделить объект/группу на холсте и увидеть его в списке элементов;
- переместить, изменить размер, повернуть, отразить, дублировать;
- изменить базовые цвета, прозрачность, обводку там, где это возможно;
- изменить порядок наложения;
- группировать и разгруппировать;
- копировать, вырезать, вставлять между листами;
- отменить или повторить ручное действие;
- сохранить отредактированный лист и итоговую композицию.

Идея таблицы **в духе Excel**: список объектов и редактируемые числовые свойства (X, Y, масштаб, угол, цвет, прозрачность, порядок). Выделение на холсте синхронизируется с выбором записи, и наоборот. Не нужно воспроизводить все возможности Excel: важен принцип точного управления данными.

Выполнение этих операций должно быть быстрым и локальным. Не нужно запускать Qwen, чтобы передвинуть гитару или поменять цвет кнопки.

## 5. Мини-чат SVG внутри редактора

Это **продолжение ранее обсуждавшейся пошаговой генерации**, перенесённое из ограниченного окна генератора в независимую рабочую среду.

### 5.1. Главное правило: одна строка запроса — один результат-объект

Пользователь вводит естественное короткое задание, например:

> Нарисуй кота рокера с гитарой.

или:

> Нарисуй две концертные колонки.

или:

> Сделай красную кнопку с белым плюсом.

**Не нужно обрезать замысел до «нарисуй только лапу кота».** Короткий запрос может описывать полноценный образ — хоть кота с гитарой. Ограничение относится к **формату использования результата**: он должен быть удобным единым модулем для вставки в другую композицию.

Требуется различать:

1. **Одна смысловая сущность в редакторе**: пользователь выделяет и перемещает созданный результат как единый блок.
2. **Множество допустимых внутренних SVG-частей**: группа может содержать множество фигур, контуров, градиентов и деталей.
3. **Отсутствие необязательной сцены**: мини-генератор не должен по собственной инициативе придумывать масштабный фон или многочисленное окружение; если требуется фон, это отдельный элемент или явная часть задания.

Удобная техническая форма — **одна импортируемая группа `<g>`** с вложенной геометрией и связанными определениями. Но конкретный формат исполнения предстоит решить отдельно.

### 5.2. Ограничение сложности через длину запроса

Предпочтение пользователя: **простое, заметное ограничение объёма ввода — условно одна строка**. Цель — не превращать мини-чат в генератор многостраничных спецификаций вроде тяжёлого стресс-теста с котом-часовщиком, часами, зубцами и точным временем.

- Короткая естественная фраза лучше длинного инженерного промпта для этого режима.
- Критерий — небольшой законченный результат, который можно переносить как элемент конструктора.
- Если пользователь хочет сложную сцену, ему естественнее создать несколько модулей и собрать их вручную либо воспользоваться основным генератором целой иллюстрации.
- Важная оговорка: **одна строка не гарантирует простоты задачи**. «Нарисуй средневековый город» — короткий, но сложный запрос. Мини-генератору всё равно потребуется ограничение масштаба результата. Числовой лимит символов пока **не утверждён**.

### 5.3. Модель и системная роль

- Базовый кандидат — **та же уже используемая Qwen3.8-27B-Ridge 3.7 bpw («Гамма»)**, а не новая специализированная SVG-модель.
- Режим редактора даёт ей **узкую системную задачу**: создать самодостаточный SVG-объект/группу без ненужного окружения, с понятной геометрией и совместимостью со вставкой в редактор.
- Запрос пользователя остаётся человеческим; система накладывает правила результата.
- Это **не обещание ускорения**: потенциально меньшие объём вывода и время рассуждений могут дать выигрыш, но эффект нужно измерять на практике. Скорость одного токена сама по себе от более короткого промпта не увеличивается.

### 5.4. Вставка результата

Возможные способы, оставленные на выбор будущей реализации:

- вставка готового блока на **текущий лист**;
- создание нового листа-источника, откуда объект можно перенести вручную;
- черновик с предварительным просмотром и подтверждением вставки.

Необходимо явно показывать, куда попадёт новый объект, и не портить существующую композицию при неудачной генерации. Сохранение вариантов и отмена операций полезны, но конкретный UI **ещё не утверждён**.

## 6. Два сценария создания SVG должны сосуществовать

### Полный генератор

- Можно просить сложную иллюстрацию, описывать детали, окружение и композицию.
- Можно наблюдать реальное рассуждение Qwen, а затем постепенное появление SVG по мере записи ответа.
- Задача потенциально сложная и продолжительная; текущий подход ценит **честное отображение процесса**, а не декоративную имитацию прогресса.
- Результат — полноценный SVG-файл, который можно открыть в просмотрщике и/или отправить на отдельный лист редактора.

### Мини-генератор редактора

- Один короткий естественный запрос.
- Один компактный автономный **векторный модуль**.
- Не стремится заменить весь лист новой сценой.
- Пользователь определяет итоговую композицию самостоятельно, комбинируя элементы.
- Использует узкое системное требование и существующий путь SVG-генерации.

Это **не два конкурирующих художника**, а два режима использования одной технологии.

## 7. SVG как «лего»

Базовая философия: каждый уже созданный SVG — **не одноразовая картинка**, а источник повторно используемых геометрических деталей.

- Кот из одного файла, гитара из другого, рамка из третьего могут участвовать в одной новой композиции.
- Из одного источника можно брать не весь рисунок, а конкретную группу или деталь.
- Вынутую группу можно преобразовывать независимо от оригинала.
- С одного набора материалов можно создавать множество иконок, кнопок, плашек, персонажей, сцен и иных векторных ресурсов.
- При этом **не обязательно** создавать автоматический ИИ-поиск деталей или автономную сборку: главная концепция уже жизнеспособна на ручном копировании между листами.

Показательные сценарии:

1. Открыть несколько готовых SVG; на пустом листе собрать новую иконку из уже имеющихся фигур.
2. Создать персонажа в основном генераторе; открыть его в редакторе; затем генерировать и добавлять отдельные аксессуары.
3. Вырезать декоративный элемент одного рисунка и использовать его в кнопке интерфейса.
4. Открыть готовый сторонний SVG из Проводника и изменить его вручную без загрузки ИИ.

## 8. Технические особенности, которые нельзя упускать

Эти пункты **не готовое ТЗ**, а риски, которые следует учитывать, когда концепция перейдёт к проектированию:

### 8.1. Совместимость SVG при переносе между листами

- Разные размеры и `viewBox`: корректно переносить геометрию и нормализовывать трансформации.
- Конфликтующие `id`: при копировании переименовывать связанные определения и корректировать ссылки `url(#...)`, `href` и т. д.
- Переносить необходимые определения из `<defs>`: градиенты, маски, фильтры, `clipPath`, символы.
- Сохранять порядок элементов и вложенные `transform`, обводки, прозрачность и стили.
- Предусмотреть ситуацию, когда визуально единая сущность не сгруппирована или её части перекрываются: автоматическое «понимание», где именно гитара или лапа, нельзя гарантировать по произвольному SVG.

### 8.2. Безопасное открытие стороннего SVG

- SVG — XML/веб-формат и может содержать скрипты, внешние ресурсы и другие нежелательные конструкции.
- Открывать чужие файлы в ограниченном безопасном режиме; отключать исполнение скриптов, опасные внешние обращения и нежелательные побочные эффекты.
- Не считать произвольный импортируемый SVG автоматически пригодным для безопасного редактирования и предпросмотра без проверки.

### 8.3. Не смешивать данные и долгие вычисления

- Просмотр и обычные ручные правки работают **без модели**.
- Генерация через Гамму — отдельная операция с управлением временем, отменой и ошибками.
- Желательно не блокировать работу редактора во время длительной генерации, если текущая архитектура это допускает.
- При сохранении избегать незаметной порчи исходника; новый лист, исходный файл и собранный проект должны иметь понятные правила сохранения.
- Нужен способ сохранять **рабочую сессию с несколькими листами** и их связями, не превращая их преждевременно в один общий SVG. Формат проектного файла ещё не выбран.

## 9. Принцип интерфейса

Пользователь должен чувствовать, что работает не с программированием SVG, а с **наглядным конструктором**:

- визуальный холст, увеличение и перемещение;
- вкладки открытых листов **снизу**, как в Excel;
- панель объектов и точных свойств, как таблица;
- инструменты выделения, копирования, изменения геометрии, как в простом графическом редакторе;
- небольшой мини-чат для создания недостающих деталей;
- действие «Открыть в редакторе» непосредственно из просмотрщика;
- отсутствие обязательной загрузки ИИ ради просмотра/обычной правки.

Редактор следует рассматривать как **отдельную среду**, а не как всё более сложную панель внутри окна SVG-генерации.

## 10. Возможная последовательность пользовательской работы

1. В основном сценарии ЛОПАТЫ по запросу «Нарисуй кота рокера с гитарой» создаётся SVG.
2. Пользователь просматривает результат и сохраняет его.
3. Позже открывает файл двойным щелчком в Проводнике — появляется знакомый просмотрщик ЛОПАТЫ с удобным зумом.
4. Нажимает «Открыть в редакторе»: кот становится первым листом.
5. Открывает другой SVG: появляется второй лист-вкладка внизу.
6. Создаёт пустой третий лист для будущей композиции.
7. Копирует кота или его группу с первого листа, декоративный элемент со второго — на третий.
8. На третьем листе недостаёт концертной колонки. В мини-чате пишет одной строкой «Нарисуй чёрную концертную колонку».
9. Мини-генератор создаёт отдельный SVG-модуль, который добавляется на лист по выбранному механизму.
10. Пользователь самостоятельно размещает, масштабирует, дублирует элементы и сохраняет общую композицию.

**Смысл:** уже нарисованные части не нужно генерировать заново; последующие операции преимущественно быстрые и ручные.

## 11. Принципы и границы концепции

1. **Не заменять** основной генератор SVG; расширить возможности использования его результатов.
2. **Не делать редактор обязательным** для генерации и просмотра.
3. **Не путать листы со слоями** и не выполнять физическую склейку SVG при каждом открытии.
4. **Не урезать смысл короткого запроса** в мини-чате до одной анатомической детали: «кот с гитарой» может оставаться единым смысловым объектом.
5. **Не путать один пользовательский объект с одним SVG-контуром**: внутри допускается сложная группа.
6. **Не требовать ИИ для простых ручных операций**.
7. **Не обещать скорость без испытаний**; цель ограничения задачи — контролируемость и потенциальное уменьшение времени работы.
8. **Переиспользовать существующий просмотрщик**, насколько это возможно, вместо создания дубля.
9. **Не ориентироваться на полный функционал Illustrator/Inkscape**: идея — простой, удобный, модульный редактор-конструктор.
10. **Не считать концепцию уже реализованной**: текущие скриншоты подтверждают генератор и живой предпросмотр, остальное является направлением развития.

## 12. Итог

ЛОПАТА может развить SVG-направление из отдельной генерации изображений в **целую локальную среду работы с векторными файлами**:

> **Проводник Windows → самостоятельный SVG-просмотрщик → редактор с листами → копирование и ручная сборка → мини-генерация недостающих модулей → новый SVG.**

Ключевая идея пользователя — **не «сшивать SVG-файлы», а сделать из каждого файла отдельный лист-источник, из которого можно забирать нужные детали на лист будущей композиции**. Мини-чат позволяет пополнять набор материалов, не уходя из редактора. Всё это развивает старую концепцию пошаговой генерации, освобождая её от границ одного окна сценария.
