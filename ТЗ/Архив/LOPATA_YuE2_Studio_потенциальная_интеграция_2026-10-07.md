# ЛОПАТА — YuE2 Studio как потенциальный новый backend

Дата фиксации: 2026-10-07

## Зачем это важно

YuE2 Studio потенциально может закрыть или существенно ослабить две главные болячки текущего музыкального контура ЛОПАТЫ:

1. Потери, повторы и случайные перестановки строк lyrics.
2. Нестабильность речи/фонетики и общее падение good-case rate при генерации.

Ключевая мысль:

> Не встраивать чужой интерфейс YuE2 Studio в ЛОПАТУ, а использовать его headless/backend-часть под нашим интерфейсом.

---

## 1. Что такое YuE2 Studio

YuE2 Studio — отдельный Windows-проект поверх `yue2.cpp`.

Архитектура проекта:

```text
React / Tauri UI
        ↓
Rust music-server :8791
        ↓
yue2.cpp yue-server :18087
        ↓
YuE2
```

В проекте есть отдельный бинарник `music-server.exe`.

Его entry point прямо описан как standalone entry point для сервиса, существующий для development и headless use.

То есть backend изначально предусмотрен для headless-работы без интерфейса Studio.

---

## 2. Как это может выглядеть в ЛОПАТЕ

Предпочтительная схема:

```text
ЛОПАТА / WPF
      ↓
YuE2 Studio adapter
      ↓
music-server.exe
      ↓
yue-server
      ↓
YuE2
```

Наш интерфейс, редактор песни, библиотека, история, плеер и будущая адаптивная правая ИИ-панель остаются в ЛОПАТЕ.

YuE2 Studio используется как:

- backend;
- сервис управления YuE2;
- источник расширенных функций;
- эталон реализации сложных операций над YuE2.

---

## 3. Почему это особенно интересно после сегодняшних тестов

Текущая самописная интеграция ЛОПАТЫ работает примерно так:

```text
request
→ yue-plan.exe
→ процесс завершился
→ сохранённый ABC
→ yue-synth.exe
→ процесс завершился
→ WAV
```

YuE2 Studio использует постоянный `yue-server`, который обслуживает запросы как отдельный движок.

Потенциальные плюсы:

- меньше собственных обвязок;
- естественный доступ к промежуточным состояниям;
- удобнее повторное использование планов и токенов;
- удобнее batch-генерации;
- удобнее exact replay;
- проще поддерживать дополнительные режимы без переписывания всего в ЛОПАТЕ.

## 4. Самые важные функции YuE2 Studio для наших проблем

### 4.1. Keep / Words lyric preservation

В YuE2 Studio 3.4.0 заявлены `Keep / Words lyric preservation`.

Это напрямую связано с нашей главной структурной проблемой:

- пропуск строк;
- повтор строк;
- перестановка строк;
- сокращение секций;
- произвольное обращение модели с lyrics.

Это не гарантирует полного лечения, но функция явно нацелена на тот же класс проблем, который мы сегодня наблюдали вручную.

Обязательно:

- изучить реализацию;
- проверить, на каком этапе она действует;
- проверить, влияет ли она на ABC;
- проверить, влияет ли она на semantic tokens;
- прогнать наши русские benchmark-песни.

### 4.2. Exact checkpoint / audio tokens

Studio умеет хранить и повторно использовать точные промежуточные токены/состояния.

Это особенно важно для диагностики:

```text
Lyrics
↓
ABC / Score
↓
Semantic tokens
↓
NAR
↓
VAE
↓
Audio
```

С exact tokens можно:

- повторять одну и ту же semantic-последовательность;
- менять только acoustic render;
- проверять один и тот же план с разными параметрами;
- отделять ошибку planner от semantic-stage;
- добиваться exact replay;
- строить нормальный исследовательский стенд.

### 4.3. Batch score-plan selection

Studio умеет работать с несколькими планами/кандидатами.

Это практически совпадает с нашей идеей:

> YuE2 надо оценивать не по одному прогону, а сериями.

Вместо:

```text
1 prompt
→ 1 random plan
→ 1 song
```

можно исследовать:

```text
1 prompt
→ N score plans
→ выбор лучшего
→ render выбранного плана
```

Особенно полезно для автоматического режима:

```text
сгенерировать несколько ABC
→ проверить структуру/lyrics
→ отбраковать плохие
→ рендерить только лучшие
```

### 4.4. Повторяющиеся секции и chord mirroring

Studio умеет согласовывать повторные секции.

Это может быть полезно для:

- одинаковых припевов;
- повторов Verse/Chorus;
- более стабильной структуры песни;
- уменьшения расхождения одинаковых секций между собой.

### 4.5. Полный контроль sampling

Studio открывает практически все параметры YuE2:

- temperature;
- top_p;
- top_k;
- repetition penalty;
- penalty window;
- min/max tokens;
- flow-matching steps;
- guidance;
- seeds;
- output format.

Для обычного пользователя ЛОПАТЫ это не обязательно показывать, но для стенда, профилей и расширенного режима это очень полезно.

### 4.6. LoRA для разных половин модели

YuE2 Studio поддерживает отдельные LoRA для:

- composition / AR;
- sound / NAR.

Это хорошо совпадает с нашей гипотезой о будущем русском адаптере.

Возможный путь:

```text
AR LoRA
→ улучшает планирование, lyrics, структуру, порядок

NAR LoRA
→ улучшает sung phonetics, голос, акустическую реализацию
```

## 5. Возможная польза именно против двух наших главных багов

### Баг A — пропуски и перестановки строк

Потенциальные инструменты Studio:

- Keep / Words lyric preservation;
- batch score-plan selection;
- редактирование ABC;
- repeated-section mirroring;
- exact replay;
- checkpoint tokens;
- отдельная AR LoRA.

Рабочая гипотеза:

> Если Studio умеет удерживать lyrics на уровне планирования, часть структурного хаоса можно убрать ещё до synthesis.

### Баг B — сломанная речь / псевдославянская фонетика

Потенциальные инструменты Studio:

- BF16 model set;
- exact semantic replay;
- отдельная NAR LoRA;
- повтор одного и того же плана с другим acoustic seed;
- сравнение Q8 / BF16;
- сохранение точных промежуточных состояний.

Рабочая гипотеза:

> Если фонетическая деградация рождается после нормального ABC, Studio поможет локализовать semantic/NAR часть и тестировать её отдельно.

## 6. Особенно важное отличие — BF16

В документации YuE2 Studio есть примеры, сделанные на RTX 4090 с рекомендованным BF16-набором.

Для нас это важно, потому что текущая ЛОПАТА использует `YuE2-3B Q8_0 GGUF`.

А Q8 участвует именно в:

- AR Score / ABC;
- AR Semantic.

VAE у нас F32.

Поэтому Studio даёт удобную возможность построить реальное сравнение:

```text
A. ЛОПАТА сейчас:
Q8 + yue2.cpp

B. Studio:
BF16 + yue2.cpp/yue-server

C. при необходимости:
другие quant-профили
```

Главная метрика: `good-case rate`, а не единичное лучшее звучание.

## 7. Возможный путь внедрения

### Этап 1 — внешний headless backend

Самый разумный первый вариант:

```text
ЛОПАТА запускает music-server.exe
↓
проверяет health/status
↓
общается по localhost HTTP/API
↓
получает план/трек/токены/состояние
```

Плюсы:

- минимум вторжения;
- легко обновлять;
- легко откатывать;
- легко сравнить со старым backend;
- не нужно переносить Rust-код в C#;
- Studio можно заменить новой версией отдельно от ЛОПАТЫ.

### Этап 2 — адаптер ЛОПАТЫ

Нужен отдельный backend-adapter, например:

```text
IMusicBackend
    ├─ YuE2CurrentBackend
    └─ YuE2StudioBackend
```

Универсальная часть сценария остаётся общей:

- текст;
- проект;
- название;
- история;
- плеер;
- варианты;
- библиотека;
- метаданные;
- экспорт.

Правая ИИ-панель адаптируется под backend.

### Этап 3 — решить, нужен ли перенос кода внутрь

Только если внешний `music-server.exe` окажется неудобен.

Тогда можно рассмотреть:

- использование нужных Rust crates;
- сборку собственного bridge;
- частичное заимствование реализации.

Но это не первый шаг.

## 8. Лицензия

Сам YuE2 Studio — MIT.

MIT допускает использование, модификацию и распространение при сохранении copyright notice и текста лицензии.

Но не надо бездумно копировать весь Studio целиком: в полном проекте много сторонних компонентов со своими лицензиями.

Для ЛОПАТЫ лучше использовать минимально необходимый набор:

```text
music-server
music-engine
нужные части управления YuE2
```

и отдельно проверить dependency/license closure именно для этого набора.

Лицензии самих весов YuE2 остаются отдельным вопросом и не меняются от использования Studio.

## 9. Что особенно интересно в архитектуре Studio

Studio уже реализует то, к чему мы сами пришли вручную:

```text
песня
→ план
→ сохранённый score
→ сохранённые audio/semantic codes
→ повторный render без нового планирования
```

Это хорошо подходит под будущий автоматический отбор:

```text
N plans
→ анализ
→ M лучших
→ render
→ ASR-проверка
→ 1–3 кандидата пользователю
```

## 10. Что Codex должен проверить после отката

1. Поднять YuE2 Studio headless `music-server`.
2. Проверить доступный API.
3. Прогнать одну и ту же песню через текущий backend ЛОПАТЫ и Studio backend.
4. Использовать одинаковые lyrics/style.
5. Проверить BF16.
6. Проверить Keep/Words.
7. Проверить batch plan selection.
8. Проверить exact checkpoint/audio tokens.
9. Проверить повтор одного плана.
10. Сравнить ABC.
11. Сравнить semantic tokens.
12. Сравнить WAV/ASR.
13. Посчитать:
    - потерянные строки;
    - повторы;
    - перестановки;
    - broken words;
    - языковой дрейф;
    - длительность;
    - время генерации;
    - good-case rate.
14. Проверить, можно ли использовать Studio как постоянный backend без его UI.
15. Проверить минимальный набор файлов и лицензий для интеграции.

## 11. Основные benchmark-тексты

### A. «Будильник для Сани»

Проблемный тест:

- хорошие/плохие прогоны;
- перестановки строк;
- фонетический дрейф;
- высокая зависимость от seed.

### B. «Всё для людей»

Положительный сложный benchmark:

- несколько ролей;
- длинная структура;
- стабильный русский;
- хороший контрольный пример.

### C. Простой классический текст

Проверяет:

- базовую русскую фонетику;
- сохранность строк без сложной режиссуры.

### D. Известная песня

Только лабораторный тест:

- возможная training-set familiarity;
- отличие нового текста от знакомого модели материала.

---

## 12. Рабочая гипотеза

YuE2 сама по себе остаётся моделью с высоким потолком качества и низкой предсказуемостью.

YuE2 Studio может не «исправить модель», но потенциально:

- уменьшить вероятность плохих планов;
- дать инструменты сохранения lyrics;
- позволить отбраковывать плохие ABC до рендера;
- дать точный replay;
- дать доступ к exact tokens;
- упростить диагностику;
- дать BF16 baseline;
- позволить отдельные AR/NAR LoRA;
- повысить итоговый good-case rate без смены самой YuE2.

---

## 13. Главный вывод

YuE2 Studio стоит рассматривать не как конкурирующее приложение и не как чужой интерфейс, а как:

> **потенциально более зрелый backend для YuE2 внутри ЛОПАТЫ.**

Если Keep/Words и batch plan selection реально уменьшают наши две основные проблемы, это может дать больший практический эффект, чем дальнейший ручной prompt-engineering текущего Q8-контура.

Приоритет после отката:

```text
1. Headless YuE2 Studio backend
2. BF16
3. Keep / Words
4. Batch plan selection
5. Exact tokens / replay
6. Сравнение good-case rate
```
