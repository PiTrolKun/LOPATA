# Фоновый каталог ЛОПАТЫ

`LOPATA.CollectionWorker` — отдельный процесс без окна и моделей ИИ. Проводник читает
его ограниченный снимок; чтение метаданных и запросы Windows Search выполняет worker.

## Запуск

```powershell
LOPATA.CollectionWorker.exe --root "<каталог данных>" --serve
LOPATA.CollectionWorker.exe --root "<каталог данных>" --scan
```

Обычный каталог данных — `%LOCALAPPDATA%\AI_HUB\Collection`. `--serve` требует
включённый `CollectionConfig` и `enabled.bin`. `--scan` — разовый диагностический
проход с JSON в stdout; он не включает интеграцию Проводника.

Перед каждой операцией worker вызывает тот же `ComponentAudit.cs` и тот же
`CollectionComponent.cs`, которые использует основное приложение; исходники связаны
при сборке. Квитанции общие: родительский каталог данных / `ComponentAudit`.
Проверяются `Collection/current.json` и обязательные файлы выбранной ревизии.
Текущая настройка `behavior.componentAuditEnabled` читается из ограниченного по
размеру `settings.json` и фиксируется на операцию. При отсутствии файла используется
сохранённая настройка `CollectionConfig.AuditEnabled`; повреждённые настройки требуют
полной проверки. Первый запуск и сброс установки требуют полного аудита даже при
выключенной настройке; следующие операции используют общую политику квитанций.

Только для изолированных исследовательских запусков без установленного payload есть
явный `--diagnostic`. Он требует заданный `--root` и пустой `ExpectedWorkerPath`.
Производственную конфигурацию этот режим не обходит. Без него отсутствие manifest
является ошибкой компонента. При компонентной ошибке с выключенным аудитом worker
оставляет `component-audit-failure.json` для уведомления основным приложением.

`ExpectedWorkerPath` задаёт исполняемый файл выбранной ревизии. Пустое значение
разрешено для изолированных проверок. При смене пути предыдущий процесс завершает
работу; запись снимка проверяет путь процесса и ревизию конфигурации под общей
блокировкой. Сам worker не запускает следующую ревизию: это делает клиент.

## Источники и ограничения

1. Завершённые экспорты из `CollectionJournal.RecordCompleted`.
2. Настроенные каталоги результатов.
3. Кандидаты Windows Search из индексируемых метаданных и выбранных областей.

Каждый результат заново проверяется по встроенному происхождению. Название файла,
соседний JSON и обычное упоминание ЛОПАТЫ в содержимом не подтверждают происхождение.
Пути — реальные оригиналы; worker не создаёт каталог копий и не меняет оригиналы.

Снимок ограничен 20 000 записей и 16 МиБ. Локальная партия ограничена 12 секундами;
следующий проход продолжает незавершённый обход. Пока обход не закончен или достигнут
лимит, статус — `partial`. Запрос ОС ограничен таймаутами; зависший процесс можно
перезапустить отдельно от Проводника. Неизвестные форматы метаданных пропускаются.

## Протокол файлов

- `snapshot.bin`: версия 1, ограниченный снимок UTF-16LE для native-адаптера.
- `snapshot.revision`: привязка снимка к конкретному сохранению конфигурации.
- `worker.pid`: 12 байт — PID `uint32` и время создания процесса `uint64 FILETIME`.
- `heartbeat`: обновляется каждые 2 секунды.
- `leases/<PID>.lease`: активная клиентская аренда; свежесть — 15 секунд.
- `refresh.request`: запрос обновления; обычный период — 20 секунд.
- `quit.request`: штатное завершение конкретного запущенного процесса.
- `status.json` и `status.bin`: состояние и признак неполного результата.

Без действующих аренд worker завершается через 60 секунд. Перед принудительным
завершением клиент должен сверить PID, FILETIME и точный путь исполняемого файла.
Сбой поиска сохраняет проверенный снимок той же конфигурации. Смена областей или
выключение/включение создаёт новую ревизию; запоздавший ответ старой не публикуется.

## Проверки 09.11.2026

```powershell
dotnet test Исходники/LOPATA.Collection.Tests/LOPATA.Collection.Tests.csproj --verbosity quiet
dotnet build Исходники/LOPATA.CollectionWorker/LOPATA.CollectionWorker.csproj --verbosity quiet
```

Результат: 27/27 тестов; сборка без предупреждений и ошибок. Среди проверок:
чужие файлы и похожие метки, замена оригинала по прежнему пути, запоздавший ответ,
выключение/включение, продолжение ограниченного обхода, смена корней и запрет
публикации старым исполняемым файлом даже с новой ревизией конфигурации.

Физическая проверка отдельного worker с имитацией клиентской аренды:
`H:\AI_HUB\_tmp\collection-worker-recovery-20261109-153237\report.json`.
Подтверждены обновление heartbeat, точная идентичность PID, сохранение снимка после
принудительного завершения, повторный запуск тестовым клиентом, обнаружение переноса,
отбрасывание подменённого файла и остановка при выключении. Настоящие PNG, FLAC и DOCX
использованы под нейтральными именами; обычный файл с названием ЛОПАТЫ исключён.

Физическая смена двух отдельных неизменяемых путей worker:
`H:\AI_HUB\_tmp\collection-worker-handoff-20261109-154125\report.json`.
Старый процесс завершился штатно за 938 мс при действующей аренде; прежний путь больше
не запускается, новый запускается с корректной PID-квитанцией и находит оригинал.
В обоих каталогах одинаковая сборка — проверен протокол смены пути, а не обновление
между выпусками. После проверок все собственные тестовые процессы завершены.

Эти два протокола не проверяют настоящую автоматическую реанимацию native-адаптером
внутри Проводника. Они не меняли HKCU и пользовательский каталог интеграции.
Они были выполнены до добавления обязательного аудита payload; для повторения
прежнего протокола нужно предоставить настоящий manifest либо явно использовать
описанный выше изолированный диагностический режим.

Физический аудит настоящего отдельного worker:
`H:\AI_HUB\_tmp\collection-worker-audit-20261109-164120\report.json`.
Создан изолированный payload из текущего worker, его зависимостей и настоящей native
DLL как пассивного проверяемого файла. Manifest использует canonical revision v2.
Подтверждены полный первый аудит при выключенной настройке, общая квитанция между
запусками, последующая проверка присутствия, чтение текущей настройки из settings,
отказ при изменённом содержимом с включённым аудитом, удаление квитанции после
неудачной полной проверки, обязательная повторная проверка с выключенным аудитом,
успешное восстановление после ремонта и отказ при отсутствии обязательного файла.
Сформирован маркер компонентной ошибки; успешная проверка после ремонта удаляет
устаревший собственный маркер. Native DLL не активировалась, реестр и
рабочая интеграция Проводника не изменялись; тестовые процессы завершены.

Отдельно запущен настоящий self-contained single-file worker, подготовленный
`build-collection.ps1`, с неизменяемым staged payload из двух файлов:
`H:\AI_HUB\_tmp\collection-worker-singlefile-audit-20261109-163855\report.json`.
Подтверждены готовность, обязательный первый полный аудит при выключенной настройке,
совпадение корня и ревизии общей квитанции с manifest, повторная проверка присутствия,
штатная остановка и неизменность staged-файлов. Эта сборка предшествует только
последующему удалению устаревшего маркера ошибки; его отдельная проверка указана выше.
