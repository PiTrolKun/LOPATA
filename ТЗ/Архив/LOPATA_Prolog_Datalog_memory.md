# Дополнение к литературному сценарию ЛОПАТЫ
## Prolog/Datalog-подобная «средняя память» и современные аналоги

Дата фиксации идеи: 2026-09-08

---

## 1. Зачем нужен отдельный слой памяти

В литературном сценарии предполагаются две одновременно работающие модели:

- **ИИ1 — Писатель**: получает задачу, текущую сцену/главу и только нужный контекст; пишет текст; после утверждения пользователем может обновлять общее состояние произведения.
- **ИИ2 — Советник/Критик**: видит текущую работу, собственный чат, общую память и при необходимости глубокий архив/RAG; сам общую память не изменяет.

Между их локальными контекстами и глубоким RAG нужен отдельный слой — **«средняя память»**.

Её задача — не хранить весь текст книги как один огромный контекст, а быть **адресуемой картой текущего состояния произведения**.

Главная метафора:

> Даже если внутри со временем живёт эквивалент полной «Войны и мира», модель должна ориентироваться там как в Google Maps: не загружать всю карту, а быстро находить нужный адрес и соседние связи.

---

## 2. Почему обычный RAG здесь недостаточен

RAG хорошо отвечает на вопросы вида:

- где это уже встречалось;
- в какой старой главе была нужная сцена;
- как дословно звучала реплика;
- какие фрагменты семантически похожи на запрос.

Но для текущего состояния истории важны другие вопросы:

- кто что сейчас знает;
- кто где находится;
- какие отношения актуальны;
- какие сюжетные линии открыты;
- какой факт уже заменил старый;
- что является каноном, а что только планом или идеей;
- какие сущности связаны между собой независимо от сходства формулировок.

Поэтому предполагаемая архитектура:

**локальный контекст модели → средняя адресуемая память → глубокий RAG/архив**

Средняя память отвечает: **«что истинно и важно сейчас?»**  
RAG отвечает: **«где это было и что именно там написано?»**

---

## 3. Почему возникла идея Prolog/Datalog

Для средней памяти хочется получить свойства, похожие на исходный код:

- одна строка или небольшой блок несёт понятный факт;
- сущности имеют устойчивые имена;
- связи явно выражены;
- поиск по символам дешёвый и точный;
- модель может запросить только нужные куски;
- изменения можно делать патчами;
- старые значения можно заменять, а не бесконечно дописывать;
- файл остаётся читаемым человеком;
- структура хорошо знакома LLM по программному коду.

Отсюда идея взять **Prolog/Datalog-подобный синтаксис**.

Важно: речь не обязательно идёт об использовании полноценного Prolog-интерпретатора. Можно использовать только его идею представления фактов и отношений как основу собственного текстового формата `.lopata`.

Пример:

```prolog
person(kaido).
role(kaido, protagonist).
location(kaido, immortal_void_sect).

relation(kaido, tiger, teacher_student).
trust(tiger, kaido, high).

thread(power_control, active).
opened(power_control, chapter_6).

knows(kaido, power_is_unstable).
```

Для литературной памяти это естественно, потому что большая часть состояния мира выражается отношениями:

```text
кто → где
кто → знает → что
кто → доверяет → кому
событие → связано → с чем
линия → активна / закрыта
предмет → принадлежит → кому
персонаж → находится → где
```

## 4. Возможный формат `.lopata`

Рабочая идея: использовать фирменное расширение, например:

`project.lopata`

Внутри — UTF-8 текст с Prolog/Datalog-подобной структурой.

Пример:

```prolog
person(kaido).
name(kaido, "Кайдо").
role(kaido, protagonist).
state(kaido, learning_power_control).

person(tiger).
name(tiger, "Тигр").
relation(kaido, tiger, teacher_student).
trust(tiger, kaido, high).

thread(power_control).
thread_status(power_control, active).
thread_started(power_control, chapter_6).

event(ch06_release_power).
participant(ch06_release_power, kaido).
caused(ch06_release_power, terrain_transformation).

% Канон:
fact(kaido_first_release, "Кайдо впервые сознательно перестал полностью подавлять силу.").

% План:
plan(ch07, "Показать дальнейшее обучение контролю силы.").

% Идея, ещё не канон:
idea(show_distant_observers, "Показать последствия через реакцию далёких наблюдателей.").
```

При желании можно добавить устойчивые идентификаторы строк/фактов:

```prolog
f000341: trust(tiger, kaido, high).
f000342: thread_status(power_control, active).
f000343: location(kaido, immortal_void_sect).
```

Тогда модель или программа сможет ссылаться не только на сущность, но и на конкретный факт.

## 5. Язык программирования или только формат

Есть два возможных пути.

### Вариант A — настоящий Prolog/Datalog

`.lopata` содержит допустимые факты и правила, а ЛОПАТА использует настоящий движок.

Плюсы:

- готовая логика запросов;
- вывод связей;
- правила;
- развитая теория;
- возможность механически проверять часть утверждений.

Минусы:

- избыточная сложность для первого варианта;
- возникает зависимость от runtime;
- можно случайно превратить память книги в экспертную систему, хотя цель проще.

### Вариант B — собственный DSL, вдохновлённый Prolog/Datalog

ЛОПАТА использует только синтаксическую идею:

```text
predicate(subject, object).
```

Программа сама индексирует строки, связи и идентификаторы.

Плюсы:

- минимальная сложность;
- можно оставить только нужные возможности;
- полный контроль над версионированием и патчами;
- файл остаётся простым текстом;
- LLM всё равно видит знакомую кодоподобную структуру.

**Для первого прототипа этот вариант выглядит предпочтительным.**

## 6. Как модель должна искать в такой памяти

Предполагаемый порядок retrieval:

### 1. Точный символический поиск

Если запрос связан с известной сущностью:

```text
kaido
tiger
power_control
```

сначала поднимаются строки и блоки с этими символами.

### 2. Поиск связей

Из найденных фактов программа получает соседние сущности:

```prolog
relation(kaido, tiger, teacher_student).
thread_involves(power_control, kaido).
```

и при необходимости расширяет локальную область.

### 3. Семантический fallback

Если пользователь написал что-то неточное:

> «тот момент, когда Кайдо впервые отпустил силу»

а точного идентификатора он не знает, подключается семантический поиск по описаниям/индексу.

### 4. Глубокий RAG

Если нужны конкретная старая сцена, формулировка или исторический контекст, запрос уходит уже в архив глав.

Итого:

**точный символический поиск → связи → semantic fallback → глубокий RAG**

---

## 7. Почему это похоже на работу Codex с кодовой базой

Идея возникла в том числе из наблюдения за Codex и инструментами поиска по репозиторию.

Codex не обязан держать весь проект в контексте. Он:

1. получает задачу;
2. определяет нужные сущности;
3. ищет файл, символ или участок;
4. открывает небольшой фрагмент;
5. при необходимости расширяет поиск;
6. работает с локальной областью.

Для книги хочется получить аналогичное поведение:

**средняя память = репозиторий текущего состояния произведения**  
**персонажи/линии/отношения = символы**  
**RAG = глубокий архив исходного текста**

Размер памяти тогда перестаёт быть главным ограничением. Важнее качество адресов и поиска.

# 8. Что уже делают в похожем направлении

Ниже — не точные аналоги литературного сценария ЛОПАТЫ, а подтверждение того, что похожая идея «структурированная память + маленький рабочий контекст + глубокий архив» уже применяется и исследуется.

---

## 8.1 Lemmalog — Datalog как память LLM-агента

Проект: **JordyZomer/lemmalog**

GitHub:  
https://github.com/JordyZomer/lemmalog

Design document:  
https://github.com/JordyZomer/lemmalog/blob/main/datalog-context-engine-design.md

Lemmalog прямо позиционируется как **Datalog engine for LLM agent memory**.

Основная идея проекта:

- LLM извлекает базовые факты на границе ingestion;
- факты хранятся в Datalog;
- правила выводят связанные знания;
- отслеживается provenance — происхождение факта;
- поддерживаются временные состояния и замена знаний;
- derived views обновляются инкрементально;
- система может использоваться через MCP как общая память агента.

Ключевая мысль design document: проблема долгого контекста возникает потому, что context рассматривают как buffer, а не database.

Это очень близко к нашей исходной идее: модель не должна каждый раз «помнить лучше», ей нужно дать адресуемое внешнее состояние.

### Отличие от идеи ЛОПАТЫ

Lemmalog — универсальная память агента и полноценный Datalog engine.

В ЛОПАТЕ предполагается более узкий вариант:

- конкретно состояние длинного произведения;
- человекочитаемый `.lopata`;
- возможно, только Datalog-подобный синтаксис без полноценного логического движка;
- отдельный RAG для полного текста книги;
- две асимметричные модели: Писатель и Советник.

## 8.2 kb-prolog — локальная Prolog-first knowledge base

Проект: **mat-mgm/kb-prolog**

GitHub:  
https://github.com/mat-mgm/kb-prolog

Это локальная knowledge base, построенная вокруг Prolog.

Знания хранятся в форме:

```prolog
statement(Subject, Predicate, Object, Properties)
```

Проект поддерживает:

- гипер-реляционные связи;
- утверждения об утверждениях;
- content-addressable storage;
- SHA-256 для файлов;
- версии утверждений;
- цепочки замены старых утверждений;
- «time travel» по истории;
- Prolog как основной runtime.

### Почему это интересно для нашей идеи

Это показывает, что Prolog-подобное представление актуальных знаний с версионностью не является только историческим приёмом.

Для `.lopata` особенно интересны:

- явные отношения subject-predicate-object;
- версии фактов;
- замена старого состояния новым;
- возможность сохранять provenance/историю отдельно от текущей истины.

## 8.3 Narrative World Model — память именно для длинной художественной прозы

Работа: **Narrative World Model: Narratology-Grounded Writer Memory for Long-Form Fiction**

arXiv:  
https://arxiv.org/abs/2607.05577

Дата публикации: июль 2026.

Авторы исходят из того, что обычного retrieval для длинной прозы недостаточно.

Для истории важны:

- кто знает секрет и когда узнал;
- как менялись отношения;
- произошло ли событие до того, как оно было раскрыто читателю;
- была ли завершена старая сюжетная линия;
- какое состояние сущности актуально сейчас.

NWM использует:

- typed temporal-state graph;
- narratology-grounded структуру;
- query-conditioned hybrid retrieval.

В исследовании система существенно превосходит flat retrieval, GraphRAG и сравниваемый temporal knowledge-graph baseline на многошаговых вопросах о состоянии длинной истории.

### Почему это важно для `.lopata`

Работа независимо подтверждает базовую мысль:

> Для длинного произведения недостаточно искать просто семантически похожие абзацы. Нужно отдельно представлять текущее состояние мира и его изменения.

### Отличие от нашей идеи

NWM делает формальный temporal graph.

Мы обсуждаем более простой и, возможно, более «LLM-native» вариант:

- кодоподобный текст;
- устойчивые символы;
- адресуемые строки;
- простой программный индекс;
- семантика как fallback;
- глубокий RAG отдельно.

## 8.4 openovel — file-native story state и разделение foreground/background

Проект: **Feed-Scription/openovel**

GitHub:  
https://github.com/Feed-Scription/openovel

Это local-first интерактивная fiction-система.

Архитектура разделяет:

- быстрый foreground narrator;
- более медленных background agents;
- обычные Markdown/JSON-файлы состояния;
- canon;
- guidance;
- context cards;
- memory;
- structured story state;
- agent notebooks.

Foreground narrator видит только небольшой рабочий набор контекста и recent canon, а background loop поддерживает файлы состояния.

В README проекта отдельно подчёркивается, что default runtime **не требует vector store, RAG database или graph database**: story state хранится в обычных файлах.

### Почему это интересно

Это хороший современный пример того же общего принципа:

> быстрый исполнитель не должен постоянно читать весь мир; фоновые механизмы поддерживают внешнее файловое состояние, из которого собирается маленький рабочий контекст.

### Отличие от идеи ЛОПАТЫ

openovel — интерактивная fiction-система с foreground narrator и командой фоновых агентов.

В литературном сценарии ЛОПАТЫ предполагаются:

- ИИ1-Писатель, который не знает об ИИ2;
- ИИ2-Советник, который видит больше, но не может менять канон;
- пользователь как единственная граница утверждения;
- отдельная средняя память;
- отдельный глубокий RAG;
- чистый текст произведения без чатовой шелухи.

# 9. Что в нашей идее уже подтверждено практикой, а что остаётся экспериментом

## Уже подтверждено другими системами/исследованиями

- внешняя память полезнее бесконечного раздувания prompt context;
- структурированные факты и отношения полезны для долговременной памяти;
- Datalog действительно используется для памяти LLM-агентов;
- Prolog всё ещё применяют как основу knowledge base;
- long-form fiction выигрывает от отдельной модели текущего состояния;
- foreground/background разделение хорошо подходит длинным AI-сценариям;
- file-native state остаётся жизнеспособным подходом в современных AI-системах;
- semantic retrieval не обязан быть единственным механизмом поиска.

## Остаётся экспериментом ЛОПАТЫ

- насколько хорошо небольшая локальная модель будет ориентироваться по `.lopata` как Codex по коду;
- нужен ли реальный Datalog engine или достаточно синтаксиса;
- насколько полезны жёсткие ID строк/фактов;
- как часто нужно переписывать/уплотнять текущее состояние;
- какой объём локального блока лучше отдавать модели;
- насколько хорошо работает схема: **symbolic lookup → relation expansion → semantic fallback → RAG**;
- можно ли сохранять среднюю память очень большой без заметного ухудшения навигации;
- насколько хорошо две независимые модели смогут использовать один общий слой с разными правами доступа.

# 10. Предварительное решение для прототипа

Наиболее простой первый вариант:

1. Создать текстовый UTF-8 файл `project.lopata`.
2. Использовать Datalog/Prolog-подобный синтаксис фактов.
3. Не подключать полноценный Prolog runtime.
4. Каждому факту дать устойчивый ID.
5. Программа строит собственный индекс: predicates, entities, relations, line/fact IDs, reverse references.
6. ИИ1 и ИИ2 получают инструменты поиска по этому индексу.
7. При неясном запросе подключается семантический поиск.
8. Полные главы остаются в отдельном RAG/архиве.
9. ИИ2 имеет только read-only доступ к `.lopata`.
10. ИИ1 предлагает patch; программа применяет его только после пользовательского утверждения текста.

Пример патча:

```text
REPLACE f000341
trust(kaido, tiger, medium).

ADD f000512
thread_status(power_control, progressing).

ADD f000513
fact(ch07_control_progress, "Кайдо научился частично ограничивать воздействие силы на окружение.").
```

Такой подход сохраняет главное свойство системы:

> **книга может расти бесконечно, а рабочий контекст модели остаётся маленьким.**

# 11. Итог

Идея `.lopata` не заключается в попытке заменить RAG древним Prolog.

Она заключается в создании **промежуточного адресуемого слоя текущего состояния**:

```text
Контекст модели
      ↓
.lopata — карта актуального мира
      ↓
RAG — полный архив произведения
```

Prolog/Datalog интересны потому, что их представление знаний изначально строилось вокруг:

- фактов;
- отношений;
- символов;
- логических связей;
- точечных запросов.

И эти свойства снова оказываются полезны в эпоху LLM с дорогим контекстом.

Самый интересный эксперимент для ЛОПАТЫ:

> **можно ли превратить долговременную память художественного произведения в «кодовую базу», по которой маленькая модель будет ориентироваться так же естественно, как современный coding-agent ориентируется по репозиторию.**

Если это сработает, механизм потенциально будет полезен далеко за пределами одного литературного сценария.
