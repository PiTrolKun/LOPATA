# ЛОПАТА — концепция лёгкой установки и дельта-обновлений

## Статус идеи

27.09.2026: по поручению пользователя создано [ТЗ для продолжения обсуждения](../../ТЗ/2026-09-27_Лёгкая_установка_и_файловые_обновления.md), реализация не начата. [Согласованная схема версий](../../Документы_проекта/ВЕРСИОНИРОВАНИЕ.md) уточняет прежние примеры этой концепции. Дополнительно согласован выбор ветки в настройках: «Стабильная» проверяет полные установщики, «Бета» — быстрые файловые патчи. Установщик спрашивает о ветке без предвыборки; пояснение к Бете сообщает о более частых обновлениях и возможных неотполированных элементах. Согласованы переход старых установок через один полный установщик, Inno Setup с отдельным updater C#/.NET, восстановление после сбоя, учёт файлов патчей при удалении и группировка мелких файлов. Настройка ветки меняет только поиск/скачивание будущих обновлений, установленная версия при переключении остаётся прежней. Дополнительно согласованы общий поток версий для обоих направлений без отдельного перевода из класса Бета и обязательный вопрос полного установщика о ветке каждый раз, без предвыборки, включая запуск из программы и отложенное обновление. Способ доставки сам по себе не меняет номер или суффикс; технические детали упаковки и совместимости ещё обсуждаются. Текст ниже сохранён как исходная концепция, а не как команда на выполнение всех предложений; прежние предложения о Stable/Dev уточнены выбором «Стабильная»/«Бета».

Цель — изменить не саму логику программы, а способ её установки, обновления и доставки промежуточных версий пользователям.

На момент обсуждения полный установщик ЛОПАТЫ уже приближается к **600 МБ**, хотя в программе реализовано примерно **3,5 сценария**. При небольших правках сейчас приходится публиковать и скачивать полный установщик, поэтому публичные установщики выпускаются в основном после завершения крупных стеков работ.

Хороший пример — литературный сценарий: он может меняться до десяти раз за день, поэтому в публичном установщике его долго вообще нет, хотя рабочий код уже существует в репозитории.

---

## Основная идея

Перейти от модели:

**«каждая версия = новый полный установщик»**

к модели:

**«установка = синхронизация локальных файлов с опубликованным состоянием ЛОПАТЫ»**.

Полный установщик перестаёт быть главным носителем каждой новой версии.

Вместо этого появляется маленький установщик-загрузчик (bootstrapper), который умеет:

1. получить манифест актуальной версии;
2. определить, какие файлы отсутствуют или устарели;
3. скачать только нужные;
4. проверить их SHA-256;
5. разложить по нужным каталогам;
6. удалить файлы, которые больше не входят в текущую версию;
7. создать ярлыки и необходимые системные записи;
8. запустить ЛОПАТУ.

После установки тот же самый механизм используется для обновлений.

---

## Главный принцип обновления

Не пытаться скачивать буквально изменённые строки исходного кода.

После компиляции пользователь не имеет отдельных `.cs`-файлов проекта. Даже если изменены три строки в одном исходнике, результатом может стать новый целый `AIHub.dll`.

Поэтому базовый и практически достаточный вариант:

**скачивать только те готовые файлы программы, содержимое которых изменилось.**

Например новая версия отличается только:

- `AIHub.dll`;
- `ru.json`;
- `en.json`;
- новой библиотекой `SomeNewLibrary.dll`.

Тогда пользователь скачивает только их, а не очередные ~600 МБ.

Это даёт основную практическую выгоду без сложности настоящей побайтовой бинарной дельты.

## Манифест версии

Каждая опубликованная версия получает манифест состояния программы.

Условный пример:

```text
version = 0.1.88-dev

AIHub.exe
size = ...
sha256 = ...

AIHub.dll
size = ...
sha256 = ...

Localization\ru.json
size = ...
sha256 = ...

Runtime\SomeLibrary.dll
size = ...
sha256 = ...
```

Дополнительно манифест может содержать:

- список файлов, которые нужно удалить;
- минимально допустимую версию bootstrapper;
- принадлежность файлов к отдельным компонентам;
- канал публикации;
- URL или идентификаторы файлов в GitHub Releases;
- размер загрузки;
- контрольные суммы.

Updater сравнивает удалённый манифест с реальными локальными файлами.

Логика:

```text
локальный hash совпадает
→ файл не скачивать

hash отличается
→ скачать новую версию

файла нет
→ скачать

файл локально есть, но в новом манифесте отсутствует
→ удалить
```

Таким образом конкретная предыдущая версия пользователя постепенно перестаёт быть критически важной.

---

## Не цепочка патчей, а синхронизация состояния

Необязательно создавать отдельные пакеты:

```text
0.1.80 → 0.1.81
0.1.81 → 0.1.82
0.1.82 → 0.1.83
```

При быстром цикле разработки такая схема накопит слишком много промежуточных патчей.

Предпочтительный вариант — публиковать описание **актуального состояния**.

Например пользователь находится на `0.1.70`, а текущая версия `0.1.88-dev`.

Updater сравнивает его установку с манифестом `0.1.88-dev` и скачивает только то, чего не хватает для превращения локальной установки в `0.1.88-dev`.

Пользователь с `0.1.87-dev` при этом загрузит ещё меньше, потому что большинство его файлов уже совпадает.

## Bootstrapper

Основной установщик превращается в маленький отдельный EXE.

Условно:

`LOPATA_Installer.exe`

Он почти не содержит самой ЛОПАТЫ и меняется редко.

Его задача:

```text
запуск
↓
выбор каталога установки
↓
получение manifest
↓
проверка локального состояния
↓
загрузка необходимых файлов
↓
проверка SHA-256
↓
установка
↓
запуск ЛОПАТЫ
```

После этого тот же механизм может использоваться как updater и как средство восстановления программы.

По сути первоначальная установка — это частный случай обновления, когда локально ещё нет никаких файлов.

---

## Безопасная установка обновления

Файлы работающего приложения нельзя бездумно заменять во время его работы.

Поэтому желательно иметь отдельный маленький updater/bootstrapper.

Пример последовательности:

```text
ЛОПАТА работает
↓
получает новый manifest
↓
определяет нужные файлы
↓
скачивает их во временный каталог
↓
проверяет SHA-256
↓
запускает отдельный updater
↓
ЛОПАТА закрывается
↓
updater заменяет файлы
↓
проверяет итоговое состояние
↓
запускает ЛОПАТУ
```

Желателен кратковременный резерв изменяемых файлов:

```text
старые файлы → временный backup
↓
обновление
↓
проверка

успех
→ backup удалить

ошибка
→ вернуть backup
```

Пользовательские проекты, модели, результаты, настройки и данные Qdrant этот механизм не должен затрагивать. Он работает только с файлами, принадлежащими установленной версии приложения.

## Stable и Dev

Такая система особенно полезна при реальном темпе разработки ЛОПАТЫ.

Можно оставить два канала.

### Stable

Для обычного пользователя.

Большой стек функций завершён и проверен → публикуется стабильная версия.

Обновления редкие и сравнительно крупные.

### Dev

Пользователь сознательно включает:

**«Получать промежуточные версии»**

После этого рабочие изменения можно публиковать хоть несколько раз в день.

Например:

```text
10:15 — 0.1.88-dev
13:40 — 0.1.89-dev
18:20 — 0.1.90-dev
23:00 — 0.1.91-dev
```

Пользователь каждый раз получает только изменившиеся файлы.

Необязательно публиковать обновление после каждого Git-коммита. Несколько технических коммитов Codex могут относиться к одной работающей итерации.

Рациональнее иметь отдельное действие:

**«Опубликовать dev-обновление»**

и вызывать его только тогда, когда текущее состояние хотя бы запускается и имеет смысл отдавать тестирующим пользователям.

---

## Что это меняет для разработки

Сегодня новая функция может существовать в репозитории долго, прежде чем попасть в публичный установщик.

После перехода на файловые обновления функция может появляться у пользователей практически сразу после появления первого рабочего каркаса.

На примере литературного сценария:

```text
первый каркас
→ dev-обновление

добавлен редактор
→ маленькое dev-обновление

добавлен Writer
→ маленькое dev-обновление

добавлен Advisor
→ маленькое dev-обновление

добавлен RAG
→ маленькое dev-обновление
```

Таким образом момент появления функции у пользователей больше не привязан к моменту сборки очередного большого полного установщика.

---

## GitHub как инфраструктура

Собственный сервер для этой схемы не обязателен.

GitHub Releases может оставаться источником опубликованных файлов:

- bootstrapper;
- manifest;
- файлы или пакеты компонентов;
- полный офлайн-установщик;
- метаданные версии.

Для ЛОПАТЫ это сохраняет существующий подход: GitHub остаётся единственным публичным каналом доставки.

---

## Компонентная доставка

Следующий возможный этап — деление установки на независимые компоненты.

Например:

```text
core
dotnet
llama
chatllm
qdrant
localization
scenario-image
scenario-literary
другие будущие сценарии
```

У разных компонентов разная частота изменений.

Если изменился только интерфейс литературного сценария, нет причин повторно скачивать:

- .NET Runtime;
- llama.cpp;
- Qdrant;
- остальные неизменившиеся backend-компоненты.

Даже без пользовательского выбора модулей внутреннее деление на компоненты позволит updater'у эффективнее понимать, что действительно нужно обновлять.

---

## Модульная установка сценариев — возможное развитие

Если сценариев станет много и общий объём ЛОПАТЫ вырастет до нескольких гигабайт, можно пойти дальше.

Пользователь устанавливает минимальное ядро.

Когда впервые запускает определённый сценарий, ЛОПАТА сообщает, например:

> Для этого сценария требуется дополнительный компонент размером 84 МБ. Установить?

После подтверждения загружаются только зависимости этого сценария.

Тогда пользователь не обязан изначально скачивать функции, которыми он никогда не пользуется.

Это особенно важно в будущем, если разные сценарии потребуют:

- собственных движков;
- дополнительных библиотек;
- словарей;
- вспомогательных утилит;
- больших runtime-компонентов.

На текущем этапе такую модульность реализовывать необязательно. Сначала достаточно файлового обновления и разделения общих тяжёлых компонентов.

---

## Три уровня экономии

В перспективе система может дать три независимых уровня сокращения загрузки:

1. **Не скачивать всю программу при небольшом патче.**
2. **Не скачивать заново неизменившиеся тяжёлые runtime/backend-компоненты.**
3. **Не устанавливать вообще те сценарии и дополнительные компоненты, которыми пользователь не пользуется.**

---

## Проверка и ремонт файлов

Так как updater уже умеет сравнивать SHA-256 локальных файлов с манифестом, практически бесплатно появляется функция:

**«Проверить файлы программы»**

Она может:

- найти повреждённые файлы;
- найти отсутствующие;
- удалить лишние файлы, оставшиеся от старой версии;
- повторно скачать только проблемные элементы.

Получается аналог проверки целостности файлов в игровых клиентах.

---

## Полный офлайн-установщик

Полный установщик полностью убирать нежелательно.

ЛОПАТА позиционируется как локальная/offline-система, поэтому должен оставаться сценарий:

> скачать один файл на ПК с интернетом → перенести → установить на другой компьютер без сети.

Можно иметь два варианта:

```text
LOPATA_Installer.exe
маленький сетевой bootstrapper

LOPATA_Offline_<version>.exe
полная автономная установка
```

Сетевой вариант становится основным и рекомендуемым.

Офлайн-установщик публикуется значительно реже — например, только после завершения большого этапа.

---

## Базовые полные версии

После завершения крупного этапа можно периодически публиковать новую полную базу.

Пример:

```text
Полный offline installer 0.1.70
↓
dev-обновления .71 ... .89
↓
крупный этап завершён
↓
Полный offline installer 0.1.90
↓
новая база
↓
dev-обновления .91 ...
```

Старая история промежуточных dev-файлов при необходимости может очищаться после появления новой полноценной базы.

---

## Что пока не нужно

На первом этапе нет необходимости реализовывать настоящий SteamPipe.

Не нужны:

- сложное разбиение каждого бинарного файла на чанки;
- побайтовые бинарные патчи;
- собственная CDN;
- сервер обновлений;
- сложная система дедупликации блоков;
- огромная матрица патчей между каждой парой версий.

Такие решения значительно усложнят updater, а основную экономию уже даст простое правило:

**изменился файл → скачать новый файл; не изменился → не трогать.**

Если когда-нибудь отдельные бинарники станут очень большими и часто будут меняться частично, бинарные delta/чанки можно добавить позднее.

## Итоговая концепция

ЛОПАТА должна рассматривать установленную программу не как результат запуска конкретного большого установщика, а как **локальное состояние набора файлов и компонентов**.

GitHub публикует эталонное состояние версии.

Bootstrapper/updater приводит локальную установку к этому состоянию.

```text
GitHub
manifest + файлы
       ↓
bootstrapper / updater
       ↓
сравнение SHA-256
       ↓
скачиваются только отличия
       ↓
проверка
       ↓
актуальная ЛОПАТА
```

Основные преимущества:

- маленькие обновления вместо ~600 МБ;
- возможность быстро отдавать промежуточные функции пользователям;
- независимые Stable/Dev-каналы;
- установка и обновление используют один механизм;
- возможность проверки и ремонта файлов;
- лёгкий сетевой установщик;
- сохранение редкого полного offline installer;
- основа для будущей модульной установки сценариев;
- отсутствие необходимости поднимать собственный сервер;
- хорошая масштабируемость при дальнейшем росте ЛОПАТЫ.

Главная практическая мысль:

> **Полный установщик перестаёт быть самой версией программы. Версией становится опубликованное состояние файлов, а установщик — лишь средство получить это состояние.**
