# ЛОПАТА — идея сценария программирования: 1С

**Статус:** идея для будущего сценария. Реализация не разрешена и не планируется этим документом.  
**Дата фиксации:** 27.09.2026.  
**Фокус документа:** только сценарии программирования и обучения программированию. Всё постороннее из исходного обсуждения сознательно исключено.

---

## 1. Зачем вообще отдельное направление 1С

Для общего программирования локальные LLM пока заметно уступают современным агентам уровня Codex и аналогов. Поэтому делать ещё одного универсального локального «помощника по Python/C#/Java» малоинтересно: локальная модель будет полезна в основном для небольших проектов и простых задач.

У 1С ситуация другая:

- это большая практическая ниша, особенно в РФ и СНГ;
- язык BSL русскоязычный по происхождению и имеет огромный пласт русскоязычного кода, документации, форумов и практических решений;
- для 1С уже существует отдельная открытая AI-экосистема: специализированные модели, MCP-серверы, анализаторы, бенчмарки и датасеты;
- узкая специализация позволяет локальной модели конкурировать не «со всем Codex», а в конкретной предметной области;
- за пределами русскоязычной среды такой сценарий может выступать ещё и мостом к большому русскоязычному массиву знаний 1С: пользователь задаёт вопрос на своём языке, а система ищет/понимает русскоязычные материалы и возвращает объяснение на нужном языке.

Идея не в том, чтобы заменить опытного 1С-разработчика одной LLM, а в том, чтобы собрать **локальный специализированный контур 1С** из готовых компонентов.

# 2. Один сценарий — два под-сценария

## 2.1. Под-сценарий «Программирование»

### Минимальный полезный вариант

Даже первый вариант может быть полезен в режиме «под копипаст»:

1. пользователь описывает задачу;
2. при необходимости даёт фрагмент BSL/структуру объекта;
3. модель пишет или исправляет код;
4. система проверяет его анализатором;
5. пользователь получает готовый фрагмент для вставки в Конфигуратор/EDT.

Это уже лучше обычного чата, если модель получает реальные сведения о конкретной конфигурации и автоматическую BSL-проверку.

### Желаемая конечная точка

Постепенно приблизить режим к логике Codex:

**задача → исследование проекта → поиск нужного объекта/модуля → подготовка изменения → правка → статическая проверка → тест/запуск, где возможно → исправление → отчёт пользователю.**

Желательные возможности:

- чтение структуры конфигурации;
- поиск объектов метаданных;
- чтение и изменение BSL-модулей;
- навигация по ссылкам/зависимостям;
- проверка синтаксиса и типичных ошибок;
- объяснение, какие файлы/объекты будут изменены;
- режим предварительного показа изменений;
- автоматическая проверка после записи;
- при наличии 1С/EDT — более глубокая проверка на реальном проекте;
- локальная работа без обязательной отправки конфигурации в облако.

Это не обязательно реализовывать сразу. Архитектуру можно наращивать от «умного генератора кода» до локального агента.

---

## 2.2. Под-сценарий «Обучение / А как сделать это?»

Второй режим не должен пытаться немедленно выполнить всю работу за пользователя.

Примеры запросов:

- «Как сделать кнопку, которая создаёт новый документ?»
- «Почему запрос возвращает дубли?»
- «Как получить остатки регистра на дату?»
- «Что означает `&НаСервереБезКонтекста`?»
- «Почему эта процедура не компилируется?»
- «Покажи простой пример и объясни каждую строку».

Возможности режима:

- объяснение простым языком;
- маленькие примеры вместо огромной готовой конфигурации;
- пошаговые задания;
- проверка решения пользователя;
- указание на конкретную ошибку;
- сравнение нескольких способов решения;
- постепенное усложнение;
- объяснение на объектах реального подключённого проекта;
- перевод терминологии и объяснений на другой язык;
- режим «покажи готовое решение» по желанию пользователя.

Для базовых упражнений можно использовать OneScript как независимый исполнитель совместимого BSL без обязательной установленной платформы 1С. Для платформенных задач всё равно потребуется настоящая 1С/EDT или другой проверяемый стенд.

# 3. Готовая специализированная модель

Готовая SFT-адаптация **Qwen3.8-27B** для разработки под 1C:Enterprise.

Заявленные области:

- BSL;
- структура BSL+XML выгрузок;
- схемы XML;
- навигация по метаданным;
- пояснение и правка BSL;
- внутренние стандарты кодирования;
- работа с открытыми кодовыми базами 1С.

Модель опубликована в GGUF и ориентирована на локальный запуск через `llama.cpp`.

### Лицензия

**Apache-2.0**.

На странице модели указаны примерно:

- Q2_K — **10,9 ГБ**;
- Q3_K_S — **12,3 ГБ**;
- Q3_K_M — **13,5 ГБ**;
- Q3_K_L — **14,6 ГБ**;
- Q4_0 — **15,7 ГБ**;

Автор модели прямо предупреждает о возможных галлюцинациях:

Поэтому модель имеет смысл только вместе с проверяемыми инструментами и реальным контекстом конфигурации.

# 9. Готовый бенчмарк для объективной проверки модели

## `genlab-1c/prism`

**PRISM** — открытый исполняемый бенчмарк генерации BSL-кода.

Главная ценность: модель оценивается не по красивому ответу, а по реальному выполнению.

Метрика SMOP:

- **S — Syntax**: компилируется ли код;
- **M — Meaning**: выполняет ли требуемую задачу;
- **O — Optimization**: нет ли неоптимального поведения/антипаттернов;
- **P — Platform**: правильно ли используются объекты и данные 1С.

Есть задачи двух типов:

- чистый BSL;
- платформенные задачи с конфигурацией 1С.

### Лицензия

**MIT.**

### Возможная роль в ЛОПАТЕ

Практически готовый стенд для сравнения:

1. базовая Qwen3.8-27B;
2. `qwen3.8-27b-1C`;
3. другая специализированная локальная модель;
4. будущая собственная LoRA;
5. разные промпты/MCP-контуры.

Вместо субъективного «кажется, модель стала лучше» можно получать измеримый результат.

Источник:  
https://github.com/genlab-1c/prism

# 11. Большой BSL-корпус — полезный, но юридически грязный

## `pupkaZALUPKA/1c-bsl-dataset`

Большой корпус 1С/BSL:

- около **452 тыс.** очищенных процедур/функций;
- код собран из публичных GitHub-репозиториев;
- near-dedup;
- дополнительно присутствуют сохранённые материалы ITS и Habr.

### Почему интересен

Технически это уже почти готовое сырьё для:

- retrieval;
- RAG;
- анализа стиля;
- исследования;
- подготовки собственной SFT/LoRA после очистки.

### Почему нельзя сразу тащить в продукт

Автор прямо указывает:

- лицензии исходных GitHub-репозиториев **не проверялись индивидуально**;
- лицензия самого HF-датасета указана как **unknown**;
- присутствуют материалы ITS/Habr.

Поэтому для «лицензионного щита» ЛОПАТЫ этот корпус **не считать готовым источником обучающих данных**.

Можно рассматривать для исследования, но для собственной распространяемой LoRA понадобится:

- происхождение каждой записи;
- отбор только совместимых лицензий;
- удаление сомнительных материалов;
- отдельный лицензионный реестр.

Источник:  
https://huggingface.co/datasets/pupkaZALUPKA/1c-bsl-dataset

# 12. Нужна ли своя LoRA сразу

**Нет.**

Рациональный порядок:

1. взять обычную Qwen3.8-27B;
2. взять готовую `qwen3.8-27b-1C`;
3. подключить одинаковые MCP/BSL-инструменты;
4. прогнать обе через PRISM;
5. проверить несколько реальных задач;
6. только после этого решать, есть ли смысл обучать собственную LoRA.

Причины:

- готовая специализированная модель уже существует;
- базовую и специализированную модель можно сравнить честно;
- уже есть бенчмарк;
- уже есть небольшой SFT seed;
- большая часть реальной точности в 1С всё равно будет зависеть не только от весов, но и от доступа к реальной конфигурации, документации и проверяющим инструментам.

### Когда своя LoRA станет оправданной

Если тесты покажут устойчивые типы ошибок:

- путает конкретные платформенные API;
- плохо пишет запросы;
- неверно использует клиент/серверный контекст;
- нарушает стандарты;
- плохо объясняет код новичку;
- слишком часто подмешивает паттерны других языков.

Тогда LoRA можно обучать уже целенаправленно под измеренную проблему.

```text
│ метаданные  │        │ Server         │       │ стандарты    │
│ проект      │        │ проверка       │       │ примеры      │
└──────┬──────┘        └───────┬────────┘       └──────────────┘
       │                       │
       └──────────────┬────────┘
                      │
              ┌───────▼────────┐
              │ тест / повтор  │
              │ исправления    │
              └────────────────┘
```

В учебном режиме дополнительно может использоваться OneScript для простых исполняемых упражнений.

# 14. Международный вариант

Сценарий может быть интересен не только РФ/СНГ.

Причина: большая часть накопленного практического опыта 1С исторически русскоязычная, тогда как международная документация и сообщество значительно меньше.

Возможная механика:

**вопрос пользователя на английском/другом языке → поиск по русским и международным источникам → внутреннее понимание → ответ на языке пользователя → BSL в выбранном варианте синтаксиса.**

Это позволяет использовать русскоязычный массив знаний как скрытую базу для иностранного разработчика.

Для будущей проверки отдельно исследовать:

- какие официальные материалы разрешено индексировать/распространять;
- английский синтаксис и терминологию 1С;
- качество локальных моделей при переводе русских практических решений в английскую 1С-терминологию;
- спрос в конкретных странах/локализациях.

# 16. Предлагаемая последовательность будущего прототипа

Не ТЗ, а логичный порядок эксперимента.

### Этап 1. Чистый модельный тест

- базовая Qwen3.8-27B;
- `qwen3.8-27b-1C`;
- одинаковые настройки;
- PRISM;
- ручной набор реальных 1С-задач.

Цель: понять, насколько специализированная модель вообще даёт выигрыш.

### Этап 2. Добавить инструменты

Подключить:

- BSL Language Server;
- `mcp-1c`.

Повторить те же тесты.

Цель: отделить выигрыш от дообучения модели от выигрыша благодаря реальному контексту и проверке.

### Этап 3. MVP «под копипаст»

Простейший интерфейс:

- вопрос;
- поле BSL;
- ответ;
- диагностика;
- кнопка «проверить ещё раз».

### Этап 4. Учебный режим

- «А как сделать это?»;
- объяснение;
- маленький пример;
- упражнение;
- проверка;
- OneScript для подходящих задач.

### Этап 5. Агентный режим

Если предыдущие этапы себя оправдали:

- чтение проекта;
- поиск нужного объекта;
- подготовка правки;
- подтверждение;
- запись;
- автоматическая диагностика;
- повтор исправления.

### Этап 6. Собственная LoRA — только при доказанной необходимости

Собрать чистый лицензированный корпус под реальные обнаруженные ошибки и сравнить через тот же PRISM.

---

# 17. Главная идея

Не пытаться победить Codex универсальной локальной моделью.

Вместо этого:

> **взять узкую, практически важную для аудитории область, где уже есть русскоязычная база знаний и готовые инструменты, дать локальной модели реальный контекст проекта и автоматическую проверку, а затем постепенно наращивать агентность.**

Для 1С уже существует достаточно бесплатных компонентов, чтобы первый серьёзный эксперимент провести без создания собственного языка, IDE, модели и бенчмарка с нуля.
