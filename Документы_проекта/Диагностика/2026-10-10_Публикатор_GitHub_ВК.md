# Публикатор GitHub → ВК: реализация и границы проверки

Дата: 10.10.2026. Локальная версия: 0.5.4-dev. ТЗ активно, пользовательская приёмка впереди.

## Реализовано

- «Обработка / утилиты → Публикатор разработчика GitHub → ВК», отдельная команда трея и три навигационных тега.
- Таблица сохранённых направлений: источник, сообщество, режим, последний Release источника, последняя публикация, состояние. Добавление и удаление; дополнительные команды в «Действия направления».
- Три шага добавления: сообщество/скрытый ключ и проверка без публикации; публичный GitHub-репозиторий; ручной либо явно включённый автоматический режим и интервал проверки.
- Вся опубликованная история Releases с пагинацией, включая beta/prerelease. Старые выпуски доступны через «Показать все», выбор галочками. Первая настройка сама старую историю не отправляет.
- Предпросмотр обычной отправки и постепенной очереди, от старых к новым. Интервал по умолчанию — сутки. Приостановка, продолжение с подтверждением и очистка очереди. Проверки работают только при запущенной ЛОПАТЕ, включая трей.
- После простоя — максимум один запланированный пост за проход для направления. Новый срок отсчитывается от фактической отправки, массового догоняющего выпуска нет. Новые автоматические релизы добавляются к очереди; после выбранной истории обычная автоматическая отправка продолжается.
- История связывает Release ID с VK post ID, временем и состоянием. Перед запросом долговечно записывается попытка. Обрыв ответа/перезапуск переводит её в «Требуется проверка», без автоматического повтора. Человек подтверждает существующий пост ссылкой либо его отсутствие. Повтор уже опубликованного требует отдельного подтверждения.
- Удаление направления затрагивает только его локальную очередь, историю и ключ. Посты ВК сохраняются; повторное создание направления не восстанавливает удалённую историю отправок.
- DPAPI CurrentUser, скрытое поле, секрет исключён из журналов и обычного экспорта. HTTPS POST с ключом в теле, перенаправления отключены. Сырые ошибки ВК с request_params не показываются и не записываются. Это не защита от вредоносного ПО с правами того же пользователя.
- Разделённые модели/сервисы/окна; независимый лёгкий планировщик без LLM и без тяжёлой модельной очереди. Новые сторонние библиотеки не добавлены, используется существующий Markdig и Windows DPAPI.

## Что ещё не подтверждено

Реальный VK wall.post НЕ выполнялся: пользователь ещё не ввёл локально ключ и не подтвердил тестовый пост. Тестовые HTTP-ответы не доказывают поддержку ключа сообщества на сервере ВК. Схема VKCOM 5.199 перечисляет user token для wall.post, тогда как текущий интерфейс сообщества предлагает разрешение стены. Это расхождение остаётся открытым до практического теста.

Проверка подключения проверяет доступ к сообществу, разрешение wall и принадлежность ключа сообщества; для пользовательского ключа — разрешение wall и is_admin. Она не создаёт пост и не объявляет право реальной отправки доказанным. Отправка задаёт owner_id отрицательным ID сообщества и from_group=1. Если ВК отклонит ключ сообщества, расследовать ответ по безопасному коду ошибки и поддерживаемую авторизацию пользователя, не расширять права наугад.

Базовый практический тест: в локальном мастере подключить сообщество и репозиторий, оставить ручной режим; через «Показать все» выбрать один выпуск, просмотреть текст и лично подтвердить публикацию. Затем проверить автора/ссылку на стене, перезапуск и отметку отправленного выпуска. Ключ не отправлять в чат/скриншот. До этого VK-интеграция и ТЗ не считаются окончательно принятыми.

Первая версия публикует текст и ссылку на Release; вложения/загрузка медиа, приватные репозитории и другие соцсети не входят. Описание длиннее безопасного предела явно сокращается со ссылкой на оригинал.

## Откат и поставка

До правок сохранены оригиналы с SHA256: `_backups/20261010_github_vk_publisher/files.json`. Новые файлы перечислены в `created-files.json` там же. Для отката остановить приложение, восстановить только перечисленные оригиналы; созданные исходники удалить только по этому списку. Папку пользовательской истории Publisher не удалять при откате без отдельного решения: это уничтожит сведения об отправках.

Рабочее хранилище: `%LOCALAPPDATA%/AI_HUB/Publisher/directions.json`, атомарное сохранение и эксклюзивная блокировка. Повреждённый файл не сбрасывается автоматически. DPAPI-ключ связан с текущей учётной записью Windows.

Commit/push и публикация не выполнялись; ТЗ не архивировано. Полный и миниустановщик не пересобирались по регламенту. Постороннее удаление Cloud Import и пользовательские файлы сохранены.
