# Проверка технологий файловых обновлений

Дата: 27.09.2026. Статус: исследование официальной документации по поручению пользователя. Реализация, стенд и выбор новой зависимости не выполнялись. После обсуждения пользователь согласовал предложенный подход и уточнил: настройка ветки меняет только поиск/скачивание будущих обновлений, сохраняя установленную версию. Согласование не означает начало реализации; точные форматы, Native AOT и детали стенда ещё предстоит определить.

Связанный документ: [ТЗ лёгкой установки и файловых обновлений](../ТЗ/2026-09-27_Лёгкая_установка_и_файловые_обновления.md).

## Основа и согласованный подход

По текущим файлам проекта: приложение — C#/.NET 10 WPF (`Исходники/AIHub/AIHub.csproj`), установщик — Inno Setup (`Инструменты/Installer/LOPATA.iss`). Он устанавливает программу в выбранный каталог и два backend в отдельные каталоги LocalAppData. `ApplicationUpdateService` выбирает полный EXE и проверяет его размер/SHA-256; самостоятельного механизма файловых патчей ещё нет.

Согласованный подход: сохранить Inno Setup для полного установщика и будущего сетевого установщика; общий расчёт файлов, загрузку и восстановление реализовать отдельным модулем C#/.NET. GitHub Releases использовать для хранения манифестов и пакетов. Обновлять целые изменившиеся файлы по целевому манифесту, как согласовано пользователем. Это собственный механизм на стандартных средствах платформы: его надёжность придётся подтверждать стендом, она не следует автоматически из документации .NET.

## Что подтвердили официальные источники

### Выбор ветки в установщике

Inno Setup поддерживает пользовательскую страницу с переключателями, чтение/запись их состояния и обработчик, запрещающий переход далее. Значит, вопрос без предвыборки и проверку явного ответа можно реализовать штатными средствами. Особенность: `NextButtonClick` вызывается и при тихой установке; отказ продолжить завершает её. По последующему решению пользователя полный установщик всегда должен показывать вопрос без предвыборки, включая запуск из ЛОПАТЫ и отложенное обновление. Пользовательский процесс нельзя переводить в тихий режим ради пропуска вопроса. Если стенду понадобится безоператорный режим, явные служебные параметры для него определить отдельно, без скрытого выбора по умолчанию и без изменения пользовательского процесса. Источники: [страница выбора](https://jrsoftware.org/ishelp/topic_isxfunc_createinputoptionpage.htm), [события установщика](https://jrsoftware.org/ishelp/topic_scriptevents.htm).

### Обрыв загрузки и выключение питания

Документация .NET предупреждает: ошибка распаковки ZIP может оставить частично извлечённые файлы. `File.Replace` заменяет один файл с возможностью backup; исходный и целевой файлы должны находиться на одном томе. `Flush(true)` позволяет сбросить промежуточные буферы на диск. Эти операции не образуют готовую транзакцию всей установки. Источники: [распаковка ZIP](https://learn.microsoft.com/en-us/dotnet/api/system.io.compression.zipfile.extracttodirectory?view=net-10.0), [File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-10.0), [FileStream.Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-10.0).

Inno Setup также описывает границу, после которой последующая ошибка уже не откатывает сделанную установку. Microsoft рекомендует искать альтернативы Transactional NTFS, а не строить новую зависимость от него. Источники: [порядок установки](https://jrsoftware.org/ishelp/topic_installorder.htm), [альтернативы TxF](https://learn.microsoft.com/en-us/windows/win32/fileio/deprecation-of-txf).

Вывод для нашей реализации: сначала скачать и полностью проверить пакеты, распаковать в отдельное место; затем закрыть приложение и нужные процессы backend, применить изменения с журналом и резервом. Временные файлы для замены готовить на томе соответствующего целевого каталога. Отдельный запускатель/восстановитель должен работать даже при повреждении основных файлов приложения и не запускать смешанный набор после сбоя. Согласование нескольких каталогов/томов — наша обязанность. Восстановление после отключения питания остаётся обязательным приёмочным тестом; документация не заменяет его.

### Целостность и происхождение обновления

Предложение: подписывать манифест выпуска, который содержит хеши файлов и пакетов. SHA-256 позволяет сверить содержимое с манифестом; подпись добавляет проверку его происхождения. .NET имеет средства проверки ECDSA; Inno Setup — отдельные `.issig`-подписи для внешних файлов. Конкретный формат, совместимость с установленной версией Inno, хранение и смену ключей определить при реализации. Закрытый ключ не включать в приложение или публичный репозиторий. Источники: [ECDsa.VerifyData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.ecdsa.verifydata?view=net-10.0), [подписи Inno Setup](https://jrsoftware.org/ishelp/topic_issig.htm).

Это не заменяет Authenticode и не обещает убрать предупреждение Windows о неизвестном издателе: Inno отдельно поясняет различие. Ключи и сертификаты в этом исследовании не создавались.

### GitHub и состав пакетов

Официальный лимит — до 1000 вложений в одном Release, каждое меньше 2 GiB. Следовательно, схема «один файл программы = одно вложение» плохо подходит для полного состояния крупной установки. Предлагаются пакеты с достаточно мелким составом: приложение, ресурсы и редко меняющиеся компоненты отдельно. Если архив содержит и изменённые, и неизменённые файлы, скачивается архив целиком: гранулярность нужно измерить и согласовать с требованием не перекачивать неизменные файлы. Источник: [лимиты Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Для открытого REST API лимит без авторизации — 60 запросов в час на исходный IP. Проверка обновлений должна кешировать результат, учитывать ответы ограничения частоты и избегать частого обхода множества выпусков. Это не лимит количества скачанных файлов. Источник: [ограничения REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

GitHub поддерживает неизменяемые выпуски: сначала создать черновик, загрузить все вложения и затем публиковать. Это подходящий кандидат для защиты состава опубликованной версии; настройка не включалась. Если манифест использует пакеты прежних выпусков, их нельзя удалять, пока существуют поддерживаемые ссылки. Источник: [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

### Удаление программы после патчей

Inno удаляет установленные им файлы и явно описанные дополнительные объекты; документация прямо предостерегает от удаления всего каталога приложения маской. Вывод для отдельного updater: новые файлы патча нужно учитывать в собственном реестре принадлежности и связать его со штатным удалением. Иначе новые файлы могут остаться после uninstall. Не менять внутренний бинарный журнал Inno вручную; способ интеграции выбрать отдельно. Источники: [UninstallDelete](https://jrsoftware.org/ishelp/topic_uninstalldeletesection.htm), [журнал повторной установки](https://jrsoftware.org/ishelp/topic_appendnotes.htm).

### Автономность обновлятора

Обновлятор не должен зависеть от тех файлов .NET/программы, которые он заменяет или восстанавливает. Native AOT — кандидат для отдельного небольшого служебного EXE: он работает без установленного .NET, но требует собственного сборочного окружения и проверки совместимости. Применение AOT ко всему WPF-приложению не предлагается. Размер отдельного EXE пока не измерен. Источник: [Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).

## Проверенная готовая альтернатива: Velopack

Velopack создаёт бинарные дельты файлов и может скачивать несколько последовательных дельт, восстанавливая полный пакет. При отсутствии подходящей основы, слишком длинной/дорогой цепочке или сбое реконструкции он может перейти к полной загрузке. Встроенный путь поэтому отличается от нашего требования сравнивать целевое состояние и получать нужные файлы без обязательной цепочки. Источники: [дельты](https://docs.velopack.io/packaging/deltas), [интеграция и fallback](https://docs.velopack.io/integrating/overview).

В Windows Velopack использует собственную структуру установки; при обновлении заменяется каталог `current`. Настройки и данные в нём сохранять нельзя. Переход нашей существующей схемы с отдельными backend и Inno потребовал бы дополнительной миграции. По итогам обсуждения выбран подход с отдельным файловым updater; Velopack не выбран. Библиотека не устанавливалась; совместимость на стенде не проверялась.

## Решения, согласованные после исследования

1. **Старые установки:** выпустить один переходный полный установщик, который добавит новый updater, учёт принадлежащих программе файлов и вопрос о ветке. После него Бета получает файловые обновления. Старый клиент новый тип патча сам не понимает; установка патча «поверх как угодно» не обещается.
2. **Смена ветки в обе стороны:** настройка управляет только тем, какие будущие обновления искать и скачивать. Само переключение не меняет установленную версию и не запускает установку или откат. Поток версий общий: если последний полный установщик старее установленного патча, текущая версия остаётся, поиск идёт среди более новых полных установщиков. Отдельного перевода из класса Бета и изменения суффикса по способу доставки нет. Фактический установленный выпуск и ветку поиска показывать раздельно. Применение обновления — отдельное действие.
3. **Сохранность установки:** резерв предыдущего рабочего набора и восстановитель вне заменяемой части; не удалять резерв до подтверждения удачного запуска новой версии. При откате исполняемых файлов не откатывать пользовательские проекты вслепую; учитывать совместимость форматов.
4. **Гранулярность пакетов:** принята отдельная доставка крупных компонентов и небольшие группы мелких файлов. Допустима небольшая добавочная загрузка неизменённых файлов внутри необходимого пакета. На стенде сравнить размеры загрузки и количество запросов; точный состав групп ещё предстоит выбрать.

Согласованный вопрос полного установщика без предвыборки обязателен каждый раз, в том числе при запуске из приложения и отложенном обновлении: пользователь может передумать. Он меняет направление будущих проверок, а не уже выбранный устанавливаемый выпуск. Согласованные решения не реализованы, текущие номера/суффиксы версий не менялись. Никаких сборок, скачивания зависимостей, запусков установщика, commit/push, публикаций или изменения настроек репозитория не выполнялось.
