## 1. Результат и границы

Пользователь Studio сможет сначала получить несколько музыкальных планов,
понятно сравнить и прослушать их нотную основу, выбрать нужные, при желании
изменить план и затем создать песни. Невыбранные планы не создают полные треки.
Обычная кнопка генерации сохраняет нынешний простой сценарий.

Включены A1, A2 и уточнённый A3. Основной исполнитель — закреплённая Studio 002;
поддержку новых действий в 001 включать только после проверки возможностей.
Существующие задания/профили 001 не ломать и не переводить молча на 002.
У ACE нет этого ABC-планировщика; его интерфейс и принятые режимы сохраняются.

Вне объёма: обучение/создание своих LoRA и русская адаптация A6; повторная
реализация ACE repaint A4 и принятого MIDI→ABC A5; полный нотный редактор DAW,
распознавание нот из аудио, новые облачные обращения и скачивание моделей
в рамках одной подготовки. Расширение MIDI до аккордов/слогов не включается
автоматически в A2.

## 2. Интерфейс и согласованное размещение кнопок

Уточнённое решение пользователя 22.10.2026: одна кнопка «Музыкальные планы»
в нижнем горизонтальном ряду правой панели, рядом с MIDI/кавером. Внутри окна
сохраняются вкладки выбора планов, редактора и секций/повторов. Отдельные кнопки
для каждой вкладки не нужны. Повторное открытие в текущем рабочем сеансе
восстанавливает последнюю вкладку, повторное нажатие при открытом окне не сбрасывает её.
Сохранить компактный стиль существующих кнопок и не допускать наложений.

Для неподдерживающей модели соответствующая кнопка остаётся видимой, но
неактивной. Пояснение прямо называет поддерживающую модель: «Доступно для
YuE2 Studio». Если ограничение связано с набором движков/компонентами, указать
и его. Подсказка должна открываться даже у неактивной кнопки; причина также
доступна средствам доступности. Не скрывать кнопку и не менять модель при нажатии.
Доступность вычислять отдельно для каждой механики по фактической поддержке,
без ложного обещания работы всех режимов в любом профиле Studio.

В отдельном окне планов — список слева и выбранный план справа. Вкладки и
единый вход проверяются в RU/EN и обеих темах.

Карточка показывает название/номер, происхождение (сгенерирован/импортирован/
из песни/из MIDI), темп, размер, тональность и секции, если они прочитаны,
дату и наличие правок. Не угадывать отсутствующие значения и не давать оценку
«лучший план» без основания. Действия: получить планы, открыть ABC, взять план
из готовой генерации, прослушать основу, править, сохранить редакцию, выбрать.

По умолчанию показывать человеческую сводку; ABC-текст открывается отдельно
для тех, кому он нужен. Предпрослушивание — простые ноты локально, без нейросети,
с прямой подписью «Это мелодия плана; звучание песни будет другим».
Если преобразование для preview неполное, показать ограничения; не перезаписывать
ради прослушивания оригинальный план.

## 3. A1 — получить и выбрать планы

1. Снять неизменяемый снимок текста, пожеланий/style, cot full/melody,
   sampling/seed, модели/engine set и активных LoRA с влиянием.
2. Дать отдельно выбрать число планов 1–8, по умолчанию 3. Это не число
   полных песен и не новый предел поиска LoRA. cot=off не создаёт ABC:
   объяснить необходимость full/melody до запуска, без тихой смены режима.
3. Получать планы очередью, показывать и сохранять каждый завершённый сразу.
   Начать с одного модельного запроса одновременно; не размножать модели в GPU.
   Штатный пакетный ответ plans[] можно использовать позже при доказанной пользе,
   но не терять все промежуточные планы ради ожидания большого batch.
4. Каждый готовый план проходит доступную проверку. Ошибку отдельного плана
   показать на его карточке; другие сохранённые планы остаются пригодными.
5. По окончании/остановке очереди освободить собственные модельные процессы.
   Ожидание выбора пользователя не удерживает GPU и не занимает тяжёлую очередь.
6. Можно выбрать один или несколько планов. «Создать песни по выбранным» сначала
   показывает число будущих полных треков. Для каждого выбранного плана создаётся
   обычное задание с готовым ABC; повторного планирования нет. Дополнительные
   дубли используют тот же выбранный ABC и отдельные зафиксированные sound seed.
7. Если пользователь нажал синтез до конца подготовки остальных планов,
   предложить завершить очередь либо остановить её после текущего подтверждённого
   результата; два тяжёлых запуска одновременно не начинать.

Штатный /v1/scores использует короткий служебный рендер 1 с/1 шаг. В интерфейсе
писать «без полного синтеза песни», а не «модели/аудио не используются».
Служебный звук не попадает в готовые треки, плеер, экспорт и список песен.

## 4. A2 — импорт, проверка и версии ABC

Принимать ABC из выбранного UTF-8 файла, вставки, собственного плана генерации
или явной копии из MIDI-пути. Импорт копируется в хранилище проекта;
внешний исходник не меняется и не становится ненадёжной зависимостью задания.
Первый ограничитель размера — 200000 байт UTF-8 по notation-пути Studio;
контекст фактического запроса дополнительно проверяется штатным tokenizer.

Сохранять исходную редакцию, черновик и применённые версии с parent ID и хешами.
Правка не меняет уже созданные песни, старые задания и пользовательский текст.
Должны быть отмена неприменённой правки, возврат к прежней редакции и явное
применение выбранной. Экспорт нового ABC, если доступен, содержит безопасную
комментарий-преамбулу происхождения LOPATA; точную копию чужого оригинала
ради этой отметки не переписывать.

До дорогого синтеза проверить: непустой совместимый диалект, заголовок,
голоса/размеры/длительности, доступные секции и аккорды, допустимый размер
контекста, соответствие cot. Не обещать поддержку всего стандарта ABC.
Использовать parser закреплённой Studio через минимальный изолированный helper
либо endpoint новой ревизии обёртки; выбор закрепить после небольшого прототипа
без загрузки моделей. Не подменять проверку потерей данных через MIDI round-trip.

План с неподдержанными конструкциями остаётся доступен для исправления.
Не выкидывать ноты/голоса/секции молча и не сочинять новый план вместо него.
Парсируемость не гарантирует точное исполнение моделью.

## 5. A3 — сохранение плана и согласование секций

### 5.1. Привязка плана к тексту

Keep/Words в текущем Studio — привязка ABC к style/lyrics/cot, а не гарантия
дословного пения. В пользовательском интерфейсе: «Использовать этот план
после изменения текста/пожеланий», по умолчанию выключено.

При изменении связанных входов показать, что именно изменилось, и предложить
новый план либо явное повторное использование прежнего. До выбора не отправлять
устаревший план, не удалять его и не переписывать слова. Хешировать точные
эффективные входы, включая style после обработки LoRA; LoRA и их силы сохранять
отдельно и также отмечать изменение. При импорте без маркера один раз явно
привязать план к текущему снимку. Сохранять совместимость метки %yue2-words.

### 5.2. Следовать секциям текста

Подключить подтверждённый harmony.follow_lyrics для планирования full при наличии
секционных меток. Объяснение: «План следует порядку куплетов, припевов и других
частей текста». Это не закрепление одной гармонии для всех повторов.
Не добавлять незаявленные штрафы разнообразия аккордов вместе с этой галочкой.
Без распознаваемых меток показать причину недоступности и предложить разметку;
текст автоматически не переписывать. Предел закреплённого пути — 64 секции.

### 5.3. Согласование слов с секциями плана

Подключить lyric_timing только там, где реально строится lyric_schedule:
ABC, cot≠off, поддержанный путь, cfg_scale=1.0 и отсутствие несовместимого replay.
При других условиях выключить действие с понятной причиной, а не отправлять
параметр, который backend проигнорирует. Изменение CFG — отдельное явное решение
пользователя. Сохранить прежние значения старых проектов/заданий; новая функция
по умолчанию не меняет их звучание. Зафиксировать фактически построенное расписание.

### 5.4. Повторяющиеся части и аккорды

Готовый вызов копирования аккордов в закреплённом API не подтверждён.
Реализовать отдельное явное действие правки плана: выбрать исходную секцию
и целевые повторы, показать изменения до применения. В первом объёме переносить
только последовательность символов аккордов между секциями с совместимой
длиной/сеткой; остальные ноты и текст сохранять. Не объявлять два куплета
одинаковыми только по названию и не менять тональность автоматически.
Несовместимую сетку объяснять, а не грубо растягивать или портить план.
Результат — новая отменяемая редакция. Полный перенос мелодии/слогов не входит
в эту команду. Это дополнительная логика ЛОПАТЫ, не обещание готовой функции Studio.

## 6. Хранение и жизненный цикл

Выделить MusicScore-модель/хранилище/очередь и отдельные controller/window;
не складывать бизнес-логику в MusicGenerationSession или общий runner.
К проекту относятся наборы планов, их версии, выбранные ID, настройки A3 и
снимки входов. Готовые артефакты записываются атомарно с SHA256; статусы
pending/running/ready/failed/cancelled не подменяются статусом готовой песни.

Новый проект начинает с пустого набора и без применённого плана; настройки
предыдущего кавера/плана не протекают в него. Открытие старого проекта даёт
выключенные новые настройки. Повтор песни использует исторический план/runtime,
а не свежую выбранную редакцию и текущий набор движков.

Долгая очередь планирования входит в общий controller фоновых операций,
с checkpoint, паузой/продолжением, отменой, треем и уведомлением о результате.
Сохранённые планы не пересчитываются после восстановления; незавершённый
план можно пересчитать с тем же снимком/seed. Выбор/редактирование — простой
локальный жизненный цикл; после аварии черновик не выдаётся за применённый.

Перед синтезом зафиксировать выбранный ABC и его редакцию. Если Studio
выполнила штатную раскладку/перенос, сохранить отдельно фактический ABC,
расписание/параметры и отличие от выбранного. Источники/преобразования должны
прослеживаться до песни. Если невозможно подтвердить нужный план по receipt,
не объявлять соответствие доказанным. Сохранить штатные операции двух слоёв,
таймингов, форматов, копирования и метаданных.

Изменения immutable runtime только новой ревизией, с исходниками/лицензиями
и контрольными суммами. Устройство выбирает нынешняя политика; не фиксировать
CUDA0. Игра и другие приложения остаются отдельной нагрузкой при измерениях.

## 7. Последовательность и проверки при реализации

1. Небольшой CPU-прототип проверки/разбора ABC без моделей; подтвердить контракт
   полного плана, summary/preview и минимальную необходимость новой обёртки.
2. Хранилище версий и очередь планов A1, общий background lifecycle, карточки.
3. Импорт/редактор A2, CPU-preview и запуск обычного синтеза с выбранным планом;
   привязка к тексту из 5.1 входит в этот же полезный проход.
4. Подтверждённые секционные режимы 5.2/5.3 и редакция повторов 5.4.
5. Небольшая профильная проверка и доступный реальный короткий проход,
   приёмка получена 22.10.2026 по реализованному объёму.

Обязательные проверки: выбор не первого из трёх планов; синтез только выбранных;
пауза/отмена между планами и во время одного, восстановление после перезапуска;
изменение текста/LoRA, повреждённый импорт, неразбираемые конструкции/большой
контекст, версия после правки, готовый проект и пустой новый проект;
невозможные сочетания MIDI/кавер/ABC не запускаются и объясняются до модели.
Новый план не суммируется молча с другим музыкальным источником; возможность
использовать его для будущего кавера потребует отдельного подтверждённого пути.

Для A3 проверить реальный request/receipt: маркер снимается, keep действует,
follow передан, lyric_schedule создан при CFG=1 и не обещан при CFG=1.11;
правка аккордов меняет только выбранные совместимые повторы и отменяется.
Сохранить совместимость старых jobs/projects и обычной генерации, RU/EN,
светлую/тёмную тему, клавиатуру, доступные имена, теги и переходы единого каталога.
Ресурсные проверки отделить от оценки звучания. Совпадение всех нот/слов,
работа всех пар LoRA и всего оборудования не являются обещанным результатом.

На подготовительном этапе сборка, тесты приложения, модели, скачивание,
новая версия и публикация не требовались. Реализация начата по последующей
команде пользователя; этот документ не означает приёмку нового функционала.
