# Технологии для утилиты «Захват экрана»

Дата проверки: 02.10.2026. Основание: [рабочее ТЗ](../../ТЗ/Архив/2026-10-02_Захват_экрана_скриншоты_GIF_и_видео.md) и просьба пользователя сравнить альтернативы. Исследование документации и текущих исходников; компоненты не устанавливались, прототипы не запускались, скорость и размеры готовой поставки не измерялись. Выбор ниже — инженерная рекомендация для обсуждения, а не принятый состав реализации.

## 1. Что действительно требуется

Windows 11 x64, .NET 10/WPF; окно ЛОПАТЫ, монитор под курсором, весь виртуальный рабочий стол и область. PNG/JPEG/WebP; GIF до минуты; видео с выбором формата, качества без изменения пропорций, четырьмя режимами звука. Работа из трея, расширенные сочетания клавиатуры/мыши, отсутствие отдельного скачивания пользователем. Кадры нельзя накапливать за всю запись в RAM. UI, буфер обмена и сохранение результатов остаются нашей механикой.

Уточнение пользователя во время исследования: предпочтительна работа на CPU, поскольку GPU может одновременно выполнять модель. Следующее уточнение разрешает два пути с выбором по доступности GPU; программный путь остаётся обязательным, аппаратный возможен при достаточных ресурсах. Это предпочтение не означает запрет системного GPU-захвата или обещание нулевой VRAM: WGC/DDA используют графические ресурсы. Главный критерий — правильная запись одновременно с тяжёлой моделью; поздняя финализация и временное снижение внутреннего разрешения допустимы.

В текущем AIHub.csproj нет готового экранного/аудиозахвата. В ComponentCatalog существует загружаемый runtime.ffmpeg: указан LGPL shared архив около 70,5 MB и оценка распаковки 260 MB. Это данные каталога, а не измерение установленного компонента и не размер будущего комплекта. Наличие записи не подтверждает пригодность бинарного состава. Проект ЛОПАТЫ — GPL-3.0-or-later; при поставке всё равно проверяются конкретные версии, зависимости и условия.

## 2. Получение кадров

| Вариант | Подходящие задачи | Ограничения и решение для нас |
| --- | --- | --- |
| Windows Graphics Capture (WGC) | Окно и монитор, кадры Direct3D 11 | Основной кандидат. HWND можно выбрать через interop; область вырезается из кадра. Для всего рабочего стола нужна композиция мониторов. Проверить скрытое/свёрнутое окно, HDR, смену размера и рамку захвата. |
| DXGI Desktop Duplication (DDA) | Мониторы, области, повторяющаяся запись | Сильная альтернатива WGC для экрана. Есть сведения об изменённых участках. Поворот дисплея, курсор, несколько адаптеров и восстановление после смены режима требуют обработки. Отдельное перекрытое окно этим способом не выделяется. |
| GDI / BitBlt / PrintWindow | Простые разовые снимки и ограниченный резервный путь | Не брать единственным движком видео. PrintWindow синхронен и зависит от отрисовки владельцем окна; гарантировать скрытое GPU-окно нельзя. |
| ScreenCapture.NET.DX11 | Готовая .NET-обёртка DDA, зоны и уменьшение | Сокращает низкоуровневую работу, но не решает звук/кодирование/захват отдельного окна. README отмечает гибридные GPU. В csproj ветки master указаны net8.0, win-x64 и LGPL-2.1-only. |
| ScreenRecorderLib | Готовый путь записи H.264 через Media Foundation, PNG | Самый предметный кандидат для ускорения реализации видео. MIT; требуются Visual C++ Runtime и Media Foundation. Не подтверждена замена всего ТЗ одним пакетом: широкий набор контейнеров, GIF, WebP и сложные источники нужно проверить отдельно. |

Основания: [WGC](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture), [CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), [DDA](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api), [PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow), [ScreenCapture.NET README](https://raw.githubusercontent.com/DarthAffe/ScreenCapture.NET/master/README.md), [csproj](https://raw.githubusercontent.com/DarthAffe/ScreenCapture.NET/master/ScreenCapture.NET.DX11/ScreenCapture.NET.DX11.csproj), [ScreenRecorderLib README](https://raw.githubusercontent.com/sskodje/ScreenRecorderLib/master/README.md), [MIT](https://raw.githubusercontent.com/sskodje/ScreenRecorderLib/master/LICENSE).

WGC не требует превращать WPF в веб-приложение. Vortice.Windows — обёртки DirectX/WIC, а CsWin32 — генератор выбранных Win32 interop-объявлений; это вспомогательные средства, не дополнительные движки записи. У Vortice проверена MIT-лицензия. [Vortice](https://github.com/amerkoleci/Vortice.Windows), [лицензия](https://raw.githubusercontent.com/amerkoleci/Vortice.Windows/main/LICENSE), [CsWin32](https://github.com/microsoft/CsWin32).

Для собственного индикатора существует WDA_EXCLUDEFROMCAPTURE: Windows предусматривает исключение окна управления записью из захвата. Применимость проверять на выбранном пути, а не обещать для любого движка. [SetWindowDisplayAffinity](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).

## 3. Кодирование видео и целые движки

| Вариант | Сильная сторона | Цена и граница применения |
| --- | --- | --- |
| Media Foundation напрямую | Системный MP4 + H.264/AAC, меньше сторонней поставки | Кодирование и временные метки интегрируем сами. Для CPU-предпочтения явно выбираем программный encoder, проверяем фактический transform; аппаратное ускорение не включаем по умолчанию. Поддержка декодирования не означает наличие записи; MKV/WebM нельзя объявить готовыми по наличию плеера Windows. |
| FFmpeg в комплекте ЛОПАТЫ | Широкий выбор контейнеров/кодеков, GIF, преобразования | Хороший кандидат для всех требуемых выходов. Отдельный служебный процесс позволяет изолировать ошибки. Размер зависит от сборки; LGPL/GPL определяется включёнными компонентами. nonfree исключается из распространяемой поставки. |
| FFmpeg как весь захват | DDA-фильтр ddagrab, кадры остаются на GPU для совместимого кодировщика | Реальная альтернатива передаче сырых кадров через pipe. Управление окном, несколькими мониторами и звуком всё равно нужно сопоставить с ТЗ; одного командного примера недостаточно. |
| FFMpegCore / прямой запуск worker | Удобное управление FFmpeg из C# | FFMpegCore — MIT-обёртка, не замена и не лицензия самого кодировщика. Можно задать локальный BinaryFolder без downloader. Для наших нескольких команд собственный узкий контроллер процесса также достаточен. |
| GStreamer | Гибкие цепочки, Direct3D 11, WGC/DDA и работа с памятью GPU | Серьёзная альтернатива, особенно для сложных потоков. Плагинная поставка и interop — дополнительная работа; точный размер неизвестен. LGPL основы не отменяет проверку плагинов. |
| OBS / libobs | Развитые источники, композиция и запись | Для небольшой утилиты предварительно избыточен по интеграции и сопровождению. Это оценка сложности, не измерение скорости. Имеет смысл, если появятся сцены/трансляции; сейчас их нет в ТЗ. |

Источники: [форматы Media Foundation](https://learn.microsoft.com/en-us/windows/win32/medfound/supported-media-formats-in-media-foundation), [аппаратные transforms](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-readwrite-enable-hardware-transforms), [FFmpeg лицензия](https://ffmpeg.org/legal.html), [ddagrab](https://ffmpeg.org/ffmpeg-filters.html#ddagrab), [FFMpegCore](https://github.com/rosenbjerg/FFMpegCore), [GStreamer d3d11screencapturesrc](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11screencapturesrc.html), [условия GStreamer](https://gstreamer.freedesktop.org/documentation/application-development/appendix/licensing.html), [OBS API](https://docs.obsproject.com/), [COPYING OBS](https://raw.githubusercontent.com/obsproject/obs-studio/master/COPYING).

Рабочий набор сочетаний для сравнения: MP4/H.264/AAC; MKV/H.264/AAC либо другой проверенный аудиокодек; WebM/VP9/Opus. Это кандидаты, не окончательная матрица доступности. Проверяются программный резерв и аппаратный путь на имеющемся оборудовании. GPL-компонент не исключается только из-за названия GPL: исходники ЛОПАТЫ уже GPL, но обязательства конкретного комплекта необходимо выполнить.

С CPU-приоритетом программный H.264/libx264 становится основным кандидатом FFmpeg для MP4/MKV, программный VP9/libvpx — кандидатом WebM. VP9 нельзя считать равным H.264 по скорости без стенда. NVENC/AMF/QSV не выбирать автоматически. Существующий LGPL runtime.ffmpeg не следует считать содержащим libx264: понадобится другой проверенный состав с соответствующей GPL-поставкой либо программный H.264 Media Foundation. [FFmpeg codecs](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb), [системный H.264 encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder).

GDI стоит оставить участником сравнения для разовых снимков/низкого FPS, но не называть полностью независимым от GPU. Перевод кадров WGC/DDA в CPU-память также имеет стоимость. При нагрузке на CPU не менять разрешение/FPS скрытно: ограничивать потоки/очередь и сообщать о реально неподдерживаемом выбранном режиме.

| KGySoft.Drawing.Core GifEncoder | Специализированная GIF-анимация, квантование и dithering | Предметная альтернатива FFmpeg для GIF. Собственная лицензия заявляет совместимость с GPL; проверить пакет и notices. Оценить задержки кадров, оптимизацию повторов, RAM и текст. |
| FFmpeg palettegen/paletteuse | Построение палитры и управляемое dithering | При выбранном FFmpeg может убрать ещё один GIF-компонент. Для качественной общей палитры проверить временный сжатый материал и второй проход, не хранить минуту сырых кадров в RAM. |

## 5. Звук

Основной кандидат — WASAPI: loopback для звука выбранного устройства воспроизведения и capture для микрофона. Loopback не требует наличия аппаратного Stereo Mix. NAudio — MIT-обёртка, уменьшающая объём interop; прямой WASAPI остаётся альтернативой. [Microsoft loopback](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording), [NAudio](https://github.com/naudio/NAudio), [лицензия](https://raw.githubusercontent.com/naudio/NAudio/master/license.txt).

Смешивание двух источников — наша задача либо подтверждённая функция выбранного recorder. Нужно согласовать sample rate, вести временные метки, компенсировать расхождение часов и проверить паузы/отключения. Нельзя считать простой запуск двух источников доказательством синхронизации. Не вводить виртуальный аудиодрайвер или обязательный Stereo Mix ради захвата PC-звука.

## 6. Расширенные горячие клавиши

RegisterHotKey принимает модификаторы и одну обычную клавишу. Для такого подмножества полезен: регистрация сообщает конфликт, можно отключить autorepeat. Для нескольких обычных клавиш, мыши и HID нужен другой путь. [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey).

Предварительное предпочтение: единый сервис состояния кнопок, Raw Input для расширенных событий и RegisterHotKey для подходящих назначений. Raw Input получает клавиатуру/мышь/HID, может работать в фоне; сам по себе не резервирует комбинацию у других программ и не подавляет её передачу. На один класс устройств внутри процесса возможна только одна регистрация получателя — библиотеки не должны конкурировать за неё. [Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input), [RegisterRawInputDevices](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerrawinputdevices).

Low-level hooks — альтернативный/дополнительный путь, например для режима назначения; обработчик должен быть быстрым, иначе Windows может убрать hook. Microsoft рекомендует Raw Input для большинства подобных задач. SharpHook предлагает готовые глобальные события клавиатуры/мыши, но требует общей единственной hook-инстанции; произвольные HID-кнопки и конфликт чужого назначения этим не решаются. [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc), [SharpHook](https://raw.githubusercontent.com/TolikPylypchuk/SharpHook/master/README.md).

Не обещать достоверное обнаружение всех конфликтов расширенных сочетаний: проверяем свои дубли, регистрации Windows и известные системные ограничения; для наблюдаемых событий чужие приложения могут иметь такое же действие. Отдельно решить точное совпадение набора кнопок, момент срабатывания, приоритет пересекающихся назначений и сброс после сна/смены режима. Кнопки производителя распознаются только в том виде, в котором Windows действительно получает событие. Обычный текст и историю клавиш не собирать.

## 7. Рекомендация и конкурирующие комплекты

1. **Универсальный комплект — предварительное предпочтение под полное ТЗ и CPU-приоритет:** WGC для окна/мониторов; DDA как альтернативный экранный backend при подтверждённой необходимости; WASAPI/NAudio; WIC для PNG/JPEG; FFmpeg в собственной поставке с программным кодированием для GIF/видео и при пригодности WebP. Расширенный ввод — собственный Windows-сервис. За счёт нескольких узких слоёв механика не зависит от одного recorder. Не внедрять одновременно все запасные backend без причины.
2. **Компактный комплект на Windows:** тот же захват/звук, Media Foundation для MP4, ImageSharp либо libwebp + KGySoft для изображений/GIF. Он может оказаться удобнее и легче по поставке, если выбранный набор видеоформатов покрывается. При требовании MKV/WebM потребуются дополнительные muxer/encoder или второй компонент; не сокращать требования молча.
3. **Комплект с готовым recorder:** ScreenRecorderLib плюс нужные GIF/WebP-модули. Проверить первым как способ уменьшить объём реализации MP4. Если его композиция, жизненный цикл или форматы не подходят, уйти на первые два варианта без изменения пользовательской механики.
4. **GStreamer:** резервная архитектура для сложных GPU-цепочек. Пока нет подтверждённого выигрыша, оправдывающего новый плагинный стек. OBS/libobs не в основном shortlist этой небольшой утилиты.

Рекомендация не означает, что FFmpeg быстрее Media Foundation или что готовая библиотека медленнее собственного кода. Такой вывод пока не измерен. Прямой D3D-путь может уменьшить копирование, но только если композиция и encoder действительно работают на совместимых устройствах.

## 8. Что проверить перед окончательным выбором

После разрешения на реализацию провести небольшой адресный стенд двух ведущих путей видео; не устанавливать все рассмотренные движки. Затем выбрать один основной backend и необходимые резервные функции.

- Окно видимо/перекрыто/свёрнуто/скрыто в трее; два монитора с разным DPI, отрицательные координаты, поворот, область через границу мониторов; несколько GPU; HDR → пригодный SDR.
- Видео 1080p и 4K, исходное ультраширокое/вертикальное соотношение; CPU/RAM/GPU/VRAM, пропущенные кадры, задержка старта/остановки, итоговый размер. Сравнивать одинаковые источники, частоту и качество. Основной стенд — CPU-кодирование при параллельной генерации модели на GPU: отдельно измерять скорость модели до/во время записи, память и стабильность. CPU может участвовать в инференсе и тоже стать узким местом. Аппаратный encoder проверяется только как дополнительный вариант.
- GIF 60 секунд: статичный UI, прокрутка текста, движущаяся сцена; читаемость, цвета, FPS/задержки, итоговая оптимизация, временный диск и ограниченная память.
- PC + микрофон: старт, тишина, длительная синхронизация, смена устройств; запись без аудио.
- Ошибка сохранения, остановка/выход, завершение MP4 и сохранность частичного материала; выбранные контейнеры открыть и проверить структурно.

## 9. Уточнение: CPU, GPU 99% и правильный временный материал

Пользователь уточнил: нулевой GPU не нужен; CPU лишь предпочтителен. Итоговый файл может выдаваться позже, но исходный материал должен собираться корректно при занятой видеокарте. Это переносит приоритет на надёжность сбора и временные метки, а не на немедленную финализацию.

В проверенных API/README нет универсальной таблицы процентов CPU для ЛОПАТЫ. Документация даёт настройки: FFmpeg/libx264 — threads/preset/quality; системный H.264 encoder — worker threads 0–16, где 0 означает автоматический выбор. Число потоков не равно проценту CPU; ограничение потоков не доказывает готовность кодировать выбранные FPS в реальном времени. [FFmpeg](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb), [H.264 encoder](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder).

Расчёт объёма работы: 1920×1080×30 = 62,2 млн пикселей/с; 3840×2160×30 = 248,8 млн; 4K60 = 497,7 млн. Рост числа пикселей не означает такой же точный рост процентов CPU: влияют процессор, сцена, кодек/качество, копирование и диск. Снимок даёт кратковременную нагрузку; для записи тяжёлые этапы продолжаются либо переносятся в финализацию. Обёртки ScreenRecorderLib/FFMpegCore/NAudio сами не задают универсальную стоимость полного процесса.

Microsoft описывает разные GPU engines и отдельное управление памятью. Процент Task Manager представляет наиболее занятый engine; compute 99% не доказывает занятость copy/video на 99%. Общие ядра/память при этом могут быть разделяемыми. Теоретически захват продолжится, но может увеличиться ожидание копирования/кадра или снизиться скорость модели; это прогноз, не гарантия. [GPU scheduler и показатели](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/).

DDA объединяет несколько обновлений, если клиент не успел обработать последнее; AccumulatedFrames позволяет обнаруживать такую ситуацию, но не возвращает отдельные старые картинки. Следовательно, ждать освобождения GPU перед началом сбора нельзя. Для WGC также не полагаться на frame pool как на архив всей записи. [DXGI_OUTDUPL_FRAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_outdupl_frame_info).

Предложение: отдельный быстрый сбор → короткая RAM-очередь → временный материал на диске → финальное GIF/видео. Сжатый промежуточный формат снижает диск ценой CPU; несжатый 4K30 — около 995 MB/s и 59,7 GB за минуту, поэтому сырой кэш не универсальное решение. Определить промежуточный формат на стенде. Сохранять аудио/время и временный материал при ошибках. Финализацию можно отложить, но каждый пропуск сбора обнаруживать и объяснять; не скрывать его повтором кадра как якобы полной записью.

Ни один рассматриваемый API не даёт обещания без потерь при произвольном насыщении всех ресурсов. Критерий выбора — корректный сбор под реальной GPU-моделью при заявленных режимах; отдельно оценить CPU/диск и VRAM. Закрытие/повторный запуск и восстановление незавершённого временного материала остаются технической проверкой, не уже реализованной возможностью.

## 10. Последние уточнения: два пути и адаптация под тяжёлую модель

Главная цель — параллельная работа с очень мощной моделью. По последнему уточнению пользователя игра — только пример, игровые тесты не нужны. По одному показателю загрузки сравнивать все нагрузки нельзя: могут различаться занятые GPU engines, память, CPU и характер задержек. [Microsoft](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/).

Для стенда предложены CPU- и GPU-пути в общем контуре захвата/временного материала. Проверять выбор до старта и возможность перехода через самостоятельные фрагменты, которые затем собираются в одинаковую геометрию. Не обещать безопасное переключение encoder внутри одного открытого файла. Приоритет измерений: правильность материала и времени, состояние/скорость модели, RAM/VRAM/CPU, затем качество и время финализации.

Проверка состояния модели включает завершение ответа, ошибки нехватки памяти, сбои и длительное отсутствие продвижения. Сравнить одинаковую модель/контекст без записи и с ней, отдельно учесть период роста нагрузки. Требования захвата адаптируются до неограниченного роста очередей/памяти. Сохранённый ролик при сорванной модельной операции не подтверждает цель. Нулевая потеря производительности и отсутствие любых сбоев не объявлены гарантированными.

Допускается адаптивное внутреннее разрешение: по устойчивой перегрузке ступенчато вниз, по восстановлению вверх. В итоговом файле размеры и пропорции фиксированы; обычное увеличение сниженных фрагментов лишь выравнивает размер. [FFmpeg scale](https://ffmpeg.org/ffmpeg-filters.html#scale). Если узкий участок — получение кадра или копирование до resize, последующее уменьшение может не помочь: место адаптации проверяется отдельно. Для текста оценить потерю читаемости; автоматическое снижение FPS отдельно не согласовано. Обычные снимки остаются в исходном разрешении.

Предыдущие советы держать аппаратный путь только ручной опцией и не уменьшать внутреннее разрешение уточнены последними решениями пользователя. Порогов переключения, минимального разрешения, нейросетевого апскейла или обещанного процента CPU пока нет. Реализация и ресурсный стенд не запускались.
