# 1С: программирование и обучение — рабочая открытая заготовка

**Статус: обсуждение, проект ТЗ от 10.11.2026. Реализация не начата.** Создание этого документа, перенос идеи и набросок интерфейса разрешены. Разработку, загрузку моделей и установку исполнителей начинать после отдельной команды пользователя. Документ обновляется по итогам обсуждения.

Управление проектами находится в сворачиваемой левой панели; кнопка её возврата всегда доступна. Эти требования заменяют прежнее предложение сохранять правки в пользовательские исходники.

## 1. Принятые вводные

- Основной процесс: пользователь копирует код/ошибку в ЛОПАТУ и переносит результат в 1С сам. Загруженные файлы и папки — материалы для чтения, а не разрешение редактировать чужой проект.
- Основной пользователь сценария имеет **минимальный опыт**. Нужны понятные шаги, небольшие примеры и объяснение результата, а не обязательное владение Конфигуратором, EDT, MCP или терминалом.
- У владельца ЛОПАТЫ нет установленного тестового стенда 1С и практического опыта работы с ней. Не делать его техническим тестировщиком и не перекладывать на него подбор библиотек/проверку кода.
- Цель первого цикла — **работающая заготовка с очень открытой дверью для доработки**, а не заявление о готовом профессиональном агенте для любых конфигураций.
- Пользователь обсуждает назначение и интерфейс. После разрешения реализации Codex выполняет подбор и подключение компонентов, разработку, испытания, исправления и подготовку документов для следующих разработчиков.
- [Исходная идея](LOPATA_идея_сценария_программирования_1С.md) сохраняется без переписывания. Её сведения о версиях, числе инструментов и условиях компонентов являются историческими; ниже зафиксированы уточнения исследования.

## 2. Полезный результат первого цикла

Один сценарий «1С» с двумя режимами:

1. **Сделать задачу.** Сформулировать цель обычными словами, при необходимости добавить код/файл, получить небольшой код или предложенный вариант правки, объяснение и результаты доступных проверок. Действия: скопировать результат, создать собственный файл в текущем проекте либо обновить ранее созданный сценарием файл этого же проекта.
2. **Разобраться.** Объяснить присланный код/ошибку, предложить маленький пример или упражнение, проверить попытку пользователя, дать подсказку и по запросу показать решение.

Первый запуск полезен без установленной 1С и без готовой базы: есть учебные примеры, работа с текстом BSL, локальной моделью и настоящим статическим анализатором. Выбор файла или подключение проекта не должны быть обязательными для первого вопроса.

Заготовка закончена только когда этот путь работает физически, сохраняется и восстанавливается. Одни кнопки, шаблонные ответы и неподключённый анализатор не являются результатом. Подключения к настоящей платформе допускаются позже, через описанные интерфейсы, без изменения пользовательского проекта и ядра сценария.

## 3. Границы и честные уровни проверки

| Уровень | Что можно подтвердить | Что нельзя обещать |
|---|---|---|
| Ответ модели | Получен код/пояснение по указанной задаче | Корректность исполнения |
| BSL Language Server | Фактические диагностики выбранного файла/набора по закреплённому анализатору | Проверку всех платформенных API и поведения конфигурации |
| OneScript, если подключён | Выполнение совместимого отдельного алгоритма и его тестов | Выполнение платформенных объектов 1С, регистров и форм |
| Настоящая 1С/EDT, будущее подключение | Проверки, реально выполненные соответствующим адаптером на определённом стенде | Любую непроверенную конфигурацию, версию или рабочую базу |

В UI отдельно показывать: «Проверка кода», «Учебные тесты», «Проверка в 1С». Для каждой — не запускалась / выполнена / есть замечания / недоступна / ошибка инструмента. Отсутствующая 1С означает «не проверялось», а не зелёную галочку. Отсутствие замечаний линтера не означает, что задача решена. Статусы привязаны к хешу версии кода: ручная правка делает прежние проверки устаревшими.

В первом цикле не требуются установка 1С/EDT, доступ к рабочей базе, публикация HTTP-сервиса 1С, полный PRISM категории B, своя LoRA, готовая ERP/бухгалтерская конфигурация, автоматическая сборка любых CF/CFE/EPF/ERF. Бинарные форматы не изображать обычными текстовыми файлами: при их открытии объяснить, какая выгрузка или внешний адаптер нужен.

## 4. Интерфейс для минимального опыта

Размещение согласовано пользователем: **Создание → Vibe Coding → 1С**. В разделе «Создание» создаётся новая группа **Vibe Coding**; её название пишется по-английски одинаково в обоих интерфейсах RU/EN. Внутри группы расположен сценарий «1С». При реализации единый ScenarioNavigationCatalog содержит устойчивые ID группы и сценария, оба режима, RU/EN названия, теги и корректные переходы, а не отдельную несвязанную кнопку.

Первый экран со сворачиваемой панелью проектов:

```text
ЛОПАТА / Создание / Vibe Coding / 1С                        ИИ
┌ Проекты ──────────────────┬──────────────────────────────────┐
│ [+ Новый]                 │ [‹ Проекты] №1 · Текущий проект │
│                          │ [Сделать задачу] [Разобраться]   │
│ Список сохранённых        │ Что хотите сделать?              │
│ [Открыть] [Переименовать]  │ [Задача / код / ошибка          ]│
│ [Сохранить проект]        │ [Подготовить решение]            │
│                          │                                  │
│ Файлы сценария            │ Результат и пояснение             │
│   СтоимостьПозиции.bsl    │ [Копировать] [Создать файл]       │
│                          │ [Показать код и проверки]         │

│   МодульИз1С.bsl         │ Выбранный файл / его состояние   │
└──────────────────────────┴──────────────────────────────────┘
```

Слева видны текущий проект, сохранённые проекты, создание, открытие, сохранение и переименование. Панель сворачивается и возвращается одной кнопкой «Проекты» над рабочей областью; при сворачивании рабочая область занимает освободившуюся ширину. Кнопка возврата и номер/название текущего проекта остаются видимыми. Сворачивание не закрывает проект, не сбрасывает ввод, выбор файла или положение в работе; выбранное состояние панели запоминается как настройка интерфейса. Выбор названия в списке и открытие — понятные отдельные действия; при переключении несохранённый ввод сохраняется или явно предлагается решение, не исчезает. На узком окне панель переходит наверх/в доступное раскрытие, а не пропадает без кнопки. Номер, название и состояние проекта компактны; структура следует существующей механике проектов ЛОПАТЫ.

Внутри проекта разделены **«Файлы сценария»** и **«Материалы · только чтение»**. При выборе материала видна метка чтения и нет действия записи в этот файл. При выборе собственного файла доступны ручная правка, проверка и сохранение его новой версии. Код и подробные диагностики раскрываются по желанию; простой режим не требует постоянного просмотра редактора. Быстрый вопрос без проекта допустим, но создание файла требует выбрать или создать проект.

Основное действие с ответом — копирование чистого результата. «Создать файл с результатом…» позволяет выбрать имя и поддерживаемый формат в текущем проекте. После уточнения наброска 11.11.2026 используется одно действие «Сохранить весь проект»: задача, предложения и изменения собственных файлов сохраняются вместе. Перенос предложения в собственный файл — отдельное действие, не сохранение поверх исходного материала. В ответе на чужой исходник показывается отдельное предложение для копирования; сохранения поверх исходника нет даже после показа diff. Сравнение «было/стало», объяснение замечаний и возврат версии относятся к управляемым результатам сценария.

Результат объясняется коротко: что предложено, какие данные нужны, что проверено и какой следующий шаг. Показывать и объяснять замечания по одному месту; кнопка исправления не должна бесконечно перезапускать модель. Предварительно до двух автоматических исправлений после диагностики, затем явный результат с оставшимися проблемами; лимит уточняется испытаниями.

Проверка/генерация показывает занятость и отмену. Настройки модели, компонентов, коннекторов и версия платформы находятся в раскрываемых настройках/паспорте проекта. Пустые зависимости объясняются действием «Подготовить проверку», а не трассировкой Java/процесса. Светлая/тёмная тема и масштабы Windows проверяются одинаково. Полноценные RU/EN строки обязательны при реализации; не включать ключи прототипа в продукт заранее.

Горячие клавиши 1С рассматриваются по реальному действию и конфликтам, не назначаются декоративно.

### 4.3. Уточнённый набросок: исходник, задача и правка — 11.11.2026

По команде пользователя создан отдельный обновлённый интерактивный набросок; предыдущие варианты сохранены. Уточнения этого подраздела заменяют противоречащие им промежуточные подписи и компоновку первого эскиза. Продуктовая реализация по-прежнему не начата.

- На вкладке «Задача и правка» есть явное «Добавить исходник…»: имя, вставка кода или выбор текстового файла. Добавленный код становится материалом для чтения и сразу выбирается в задаче. Можно работать без исходника, создавая новый код.
- Над результатом видна связь «Исходник: имя файла → Задача №… → Предложение №…». У задачи указаны файл и область: весь файл либо выбранный фрагмент с номерами строк. Из открытого файла доступны «Использовать файл в задаче» / «Выделение в задачу», из замечания — переход к строке и «Предложить исправление».
- Во всех местах используется единый редактор кода: подсветка BSL, номера строк, выделение, прокрутка и положение курсора сохраняются при ручном вводе. Собственные файлы редактируются сразу, без отдельного переключения вида «Править». Для материалов тот же редактор работает только на чтение.
- Предложение — отдельный редактируемый результат. Слева для сравнения показывается снимок исходного кода, справа — предложение; изменённые строки имеют отметки удаления/добавления и цвет. Сравнение можно свернуть. Под ним явно написано, в какой файл и диапазон переносится результат. При изменении задачи, контекста либо исходного кода прежнее предложение помечается устаревшим и не применяется молча.
- «Копировать результат» / «Копировать фрагмент» передаёт только код справа, без номеров и знаков сравнения. «Создать файл с результатом…» создаёт собственный файл текущего проекта; для правки фрагмента он собирается с неизменёнными остальными строками. «Применить к моему файлу» появляется только для файла, созданного сценарием в этом же проекте, и меняет только связанный диапазон. В исходный материал запись недоступна.
- Одно сохранение относится ко всему проекту. Есть закрытие вкладок, подписанное переименование и отмена; новый проект начинается пустым. После переключения проектов возвращаются активная вкладка, курсор/выделение и положение кода. Область снизу называется «Замечания проекта» и явно показывает, что проверки предложения ещё не запускались и 1С не подключена.

## 5. Входы, проекты, принадлежность файлов

### 5.1. Входы для чтения и copy/paste

Первый цикл поддерживает вставленный BSL/ошибку, отдельные `.bsl`/`.os` и папку текстовых материалов BSL/XML. Известную структуру выгрузки Конфигуратора/EDT можно читать через адаптер; неизвестную структуру считать обычной папкой, не придумывая метаданные. Запросы 1С хранить как текст; выполнение запроса в базе в первый цикл не входит.

Импорт, копирование или перетаскивание исходника в проект, совпадение имени, расширения или каталога не делают его собственным файлом сценария. Материалы сохраняют статус только для чтения. Модель предлагает отдельный код/изменение для ручного переноса пользователем. Нельзя обходить это правило предложением «подтвердить запись» в чужой исходник.

### 5.2. Собственные файлы

Сценарий может создавать в собственном каталоге текущего проекта файлы поддерживаемых форматов: например, `.bsl`, `.os`, `.xml`, `.json`, `.txt`, `.md`. Список определяют реализованные генераторы/экспортёры, а не произвольное переименование расширения. Для CF/CFE/EPF/ERF нужен настоящий соответствующий сборщик и проверка; наличие такого генератора не предполагается автоматически.

Право изменения определяется одновременно **проектом, file ID, записью о создании сценарием и допустимым физическим расположением**. В проектном реестре хранить projectId, fileId, origin=createdByScenario, createdOperationId, относительный путь, формат, историю версий и контрольные суммы. Новый пустой файл, созданный через команду сценария, также регистрируется этой операцией. Импортированный файл не получает этот origin.

Проверять право в слое файловых операций перед фактической записью, а не только скрытием кнопки. Принимать file ID текущего проекта, не произвольный путь модели. Запрещены выход через `..`, абсолютные пути, junction/symlink и изменение сторонних файлов через hardlink. При создании не перезаписывать уже существующий незарегистрированный файл: выбрать новое имя/сообщить о конфликте. Файл другого проекта не становится доступным для записи из текущего, даже если оба проекта созданы ЛОПАТОЙ.

Ручная правка собственного файла не меняет его происхождение, но новая ревизия инвалидирует диагностики и незавершённое предложение модели. Внешнее изменение нельзя затирать: проверить хеш перед сохранением, показать конфликт/сравнение, сохранить пользовательский текст. При отсутствующем/повреждённом реестре не угадывать принадлежность; восстановить проект либо оставить файлы только для чтения. Модель и внешние инструменты не редактируют реестр владения.

Экспорт создаёт новую копию выбранного результата по явной команде пользователя, не перезаписывая существующий чужой файл. Экспорт за пределы проекта не разрешает затем изменять эту внешнюю копию автоматически. Портативный проект сохраняет идентичность и историю созданных файлов; восстановление проверяет схему, пути, принадлежность и хеши, а не доверяет одному полю origin в произвольном JSON.

### 5.3. Жизненный цикл проекта

Сохраняются название/номер проекта, задача, история, ссылки на материалы, реестр собственных файлов, версии кода, предложения, диагностики, модель, фактическая история инструментов и контрольные точки. Использовать принятые в ЛОПАТЕ создание, список, открытие, переименование, сохранение и продолжение. Переименование проекта не даёт новых файловых прав. Портативный пакет/расширение уточняется при реализации; обязательны schemaVersion, устойчивая идентичность, атомарная запись и резерв последнего исправного состояния.

Обновление/восстановление не применяет готовую правку повторно и не смешивает проекты. Сохранять кодировку, окончания строк и нетронутый текст. XML разбирать без внешних сущностей, с ограничениями объёма/глубины. Содержимое материалов и результат модели не являются разрешением исполнять команды.

## 7. Очень открытая дверь для доработки

Сценарий разделить на UI, проектное состояние, оркестрацию, модели, контекст проекта, проверки и исполнения. Конкретные компоненты не зашивать в MainWindow, промпт или один большой сервис. Имена ниже — предлагаемые контракты, не утверждение о существующем API:

- `IOneCProjectAdapter`: определить вид входа, перечислить модули/метаданные, прочитать объект и построить проверяемые ссылки на файл/диапазон. Подключённые исходники доступны для чтения. Предложения правок возвращаются как данные для copy/paste, а не как право записи в источник.
- `IOneCGeneratedFileStore`: создать файл, прочитать/предложить изменение и сохранить новую версию только зарегистрированного файла текущего проекта. Это единая точка проверки принадлежности; адаптеры источников и модель не выдают себе такие права.
- `IOneCCodeChecker`: возможности, версия, проверка кода/проекта, структурированные диагностики. BSL LS и настоящая платформа не подменяют друг друга.
- `IOneCExerciseRunner`: профиль исполнения, входы/ожидания, лимиты, stdout/stderr, результаты тестов. OneScript — одна из реализаций.
- `IOneCKnowledgeProvider`: разрешённые локальные источники, поиск с привязкой к документу/версии; отдельно от языковой модели и контекста пользователя.
- Адаптер модели использует общий runtime ЛОПАТЫ и паспорт реальных возможностей: не каждая модель поддерживает tools или одинаковые шаблоны диалога.

Дать версионируемые JSON-схемы запросов/ответов, manifest возможностей и ошибок: unsupported, unavailable, permission-required, cancelled, failed. Возможности discover/list/read/check/run/createOwnedFile/editOwnedFile разделены; отсутствие run не отключает чтение и пояснения. Запись ограничена собственными файлами текущего проекта для всех расширений. Очень открытая доработка не означает обхода этого ограничения; любое расширение внешних прав требует отдельного решения пользователя и изменения ТЗ. Для внешних подключений предусмотреть отдельный процесс и структурированный протокол stdio с лимитами, requestId, отменой и версией; MCP — возможный транспортный адаптер, не обязательный формат всего ядра.

**Обязательные выходы для следующего разработчика:** архитектурный README, карта каталогов и точек регистрации, примеры JSON, пошаговый документ «добавить свой проверяющий инструмент/источник проекта», настоящий образец файлового адаптера и автоматические контрактные тесты. Контрольный пример расширения должен подключаться без правок основного UI и оркестратора. Тестовый fake-адаптер допустим для тестов, но не выдаётся за работающую 1С и не входит в список настоящих подключений.

Эти материалы доступны из справочной кнопки по подразделу 4.4. Руководство по расширению содержит назначение каталогов/контрактов, подготовку среды, минимальный пример подключения с точкой регистрации, форматы входов/выходов, запуск проверок и ожидаемый результат. Отдельно описываются ограничения доступа к данным и честное обозначение недоступных платформенных проверок. Публичные примеры используют безопасные учебные материалы без секретов, персональных путей и закрытых конфигураций.

Не вводить обязательную чужую IDE, платную подписку, API-ключ облака или регистрацию в стороннем сервисе для основной заготовки. Не создавать ради этого универсальную плагинную систему для всех сценариев ЛОПАТЫ: расширяемость сначала ограничена конкретными контрактами 1С.

## 9. Исполнение и данные

Произвольный BSL/OneScript может читать файлы, обращаться к сети и запускать действия. Отдельный процесс, Job Object и timeout сами по себе не являются защитной песочницей. До включения запуска пользовательского/модельного кода определить настоящий профиль изоляции и доступов; если он не реализован, оставлять ручной запуск доверенных учебных примеров либо только статический анализ с честным статусом.

Сценарий не пишет в информационные базы и пользовательские исходники. Будущий коннектор в рамках этого ТЗ предоставляет ограниченные чтения/проверки, а не установку расширения или изменение базы. Даже подтверждение diff не открывает запись в чужие файлы. Изменение этой границы возможно только отдельным решением пользователя, а не настройкой адаптера. Не вызывать upstream `--install` автоматически при выборе модели. Секреты подключения не передавать модели и не экспортировать в проектные архивы. Результаты инструментов и документация считаются данными, а не инструкциями для расширения полномочий.

В экспортируемые новые кодовые/проектные результаты включать предусмотренное правилами происхождение без ломки BSL/XML и без персональных путей; известные модель/ревизия/операция — из фактической истории. Точные исходные копии ради меток не менять.

## 10. Порядок будущей реализации

1. Утвердить простой экран, границы рабочего первого цикла и открытую архитектуру. Сейчас выполняется только этот подготовительный шаг.
2. Практически проверить совместимый модельный профиль и реальный BSL LS на маленьких файлах; зафиксировать runtime/JDK, формат диагностик, кодировки, ограничения и лицензии. Большие веса не скачивать заранее «на всякий случай».
3. Сделать видимое управление проектами, copy/paste, реестр создаваемых файлов, редактор только собственных результатов, запрос к модели и настоящий цикл диагностики. Интегрировать существующие аудит, фоновые операции, языки, темы, навигацию и аппаратный выбор.
4. Подключить учебные примеры/объяснения. OneScript включать только с определённым профилем исполнения; при его отсутствии первый результат честно ограничен статическим анализом.
5. Прогнать таблицу проверок, исправить найденные сбои, подготовить примеры для доработки и инструкции. Изолировать новое от стабильных сценариев, сохранить откат.
6. После приёмки этого цикла — отдельное решение о настоящей 1С/EDT, новых форматах/адаптерах и расширенных испытаниях. Не держать базовую заготовку бесконечно незавершённой из-за отсутствия корпоративной базы.

Набор задач ограничить представительными случаями: арифметика, строки, дата, массив/структура, синтаксическая ошибка, неизвестный платформенный объект, правка собственного модуля и предложение по чужому исходнику без записи в него. Для исполнения требуются проверяемые ожидаемые результаты; PRISM mock и fake-адаптер не доказывают работу модели/платформы. В отчёте отдельно указать автоматические тесты, настоящий локальный запуск, непроверенные аппаратные варианты и недоступную 1С.

Первый цикл может быть принят без платформенного исполнения, если базовый сценарий действительно работает и расширение продемонстрировано. Заявлять полную поддержку 1С или пройденную категорию B без соответствующего стенда нельзя. Публикация и повышение версии рассматриваются по правилам только после реализации/приёмки, не из-за архивирования идеи.

## 12. Обязательные сопровождение и откат

Перед изменениями — path-safe backup и отдельная рабочая копия при грязном дереве. Дополнить реестр фоновых операций, каталог навигации/тегов, REESTR и документацию API/примеров. При подключении озвучки читать [слепок голосовых уведомлений](../../Документы_проекта/Голосовые_уведомления/README.md) и соблюдать подраздел 4.5: использовать существующие подходящие реплики, сохранять их идентификаторы/дубли; только важные уведомления без аналога допускают точечную подготовку новых RU/EN ассетов с прежними настройками и отдельным русским SynthesisText.

Rollback возвращает код, компонентные профили и проектную схему без удаления пользовательских проектов/исходников. Проектные миграции не выполняются молча. Новый сценарий держать в собственных каталогах Controls/Services/Models, в существующих больших orchestration-файлах оставлять только подключение.

## 13. Что ещё обсуждается

- Основной экран уточнён: пошаговый copy/paste со сворачиваемой панелью проектов и разделением собственных файлов/материалов. Кнопка возврата панели всегда видна; детальное расположение остальных элементов обсуждается.
- После исследования и самопроверки уточнён набросок: единый редактор, явная связь исходника/диапазона с задачей и предложением, сравнение и перенос результата по подразделу 4.3. Детали остаются предметом обсуждения; реализация программы не начата.
- Размещение согласовано: «Создание → Vibe Coding → 1С»; название новой группы Vibe Coding по-английски в обоих языках интерфейса.
