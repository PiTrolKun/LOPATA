# ЛОПАТА — выходной формат музыки и метаданные

Дата фиксации: 2026-10-07

## Цель

Зафиксировать концепцию рабочего аудиоформата и метаданных для музыкального сценария ЛОПАТЫ.

Проблема возникла во время массовых тестов YuE2:

- одна серия легко создаёт десятки неудачных генераций;
- текущий WAV занимает слишком много места;
- по одному имени файла трудно понять, что именно проверялось;
- номера генераций автоматически растут, а пользовательская пометка в имени файла легко остаётся старой;
- через несколько десятков или сотен файлов смысл отдельных дублей без логов или Codex уже трудно восстановить.

Главный принцип:

> Модель может генерировать в любом удобном ей внутреннем формате. ЛОПАТА сама приводит результат к стандартному рабочему формату и автоматически записывает в него полезные метаданные.

---

## 1. Рабочий формат

### Предпочтительный кандидат — Ogg Opus

Для внутренней музыкальной библиотеки ЛОПАТЫ разумно использовать:

```text
Ogg Opus
```

Почему:

- значительно компактнее WAV;
- стандартный распространённый формат;
- хорошее качество при умеренном битрейте;
- поддерживает обычные текстовые метаданные;
- подходит для хранения больших серий генераций;
- не привязывает библиотеку к нативному формату конкретной модели;
- удобен как рабочий формат, а не как финальный мастер.

Это особенно важно для ИИ-музыки, где большая доля генераций может быть отбракована.

---

## 2. Нативный формат модели не должен определять формат ЛОПАТЫ

Модель может возвращать WAV, FLAC, PCM, MP3 или другой поддерживаемый формат.

Для ЛОПАТЫ это внутреннее дело backend-а:

```text
выход модели
↓
нормализация / транскодирование
↓
рабочий формат библиотеки ЛОПАТЫ
```

Пользовательский музыкальный проект не должен зависеть от того, какой формат конкретный backend умеет отдавать напрямую.

---

## 3. Экспорт отдельно от рабочего хранения

Рабочий формат и экспорт — разные задачи.

Внутри ЛОПАТЫ:

```text
Ogg Opus
```

При экспорте пользователь может выбрать, например:

```text
FLAC
WAV
MP3
Opus
```

Логика:

- Opus — компактная рабочая библиотека;
- FLAC — lossless для хранения/публикации;
- WAV — совместимость и дальнейшая обработка;
- MP3 — максимальная бытовая совместимость.

---

## 4. Не нужен собственный контейнер

От идеи собственного контейнера для музыки лучше отказаться.

Также нет необходимости использовать MKA только ради метаданных.

Причины:

- появляется лишняя сложность;
- хуже совместимость;
- сторонние программы не увидят данные без нашей поддержки;
- публикация и перенос файлов становятся менее удобными.

Предпочтительно использовать стандартный музыкальный формат и стандартные поля тегов.

---

## 5. Какие метаданные должны автоматически записываться

В каждый созданный ЛОПАТОЙ музыкальный файл нужно автоматически писать максимум уже известных программе полезных данных.

Базовый набор:

```text
Title
Artist / Author
Album / Project
Genre
Date
Lyrics
Comment / Description
```

Дополнительные поля ЛОПАТЫ:

```text
LOPATA version
Model
Model variant
Model precision / quantization
Backend
Seed
Generation date/time
Project name / project ID
Track / variant number
```

Если формат позволяет custom tags, можно использовать собственные ключи, например:

```text
LOPATA_MODEL
LOPATA_MODEL_VARIANT
LOPATA_PRECISION
LOPATA_BACKEND
LOPATA_VERSION
LOPATA_SEED
LOPATA_PROJECT
```

---

## 6. Самое важное пользовательское поле — заметка

Нужно отдельное поле:

```text
User note
```

или:

```text
Test note
```

Это должна быть человеческая пометка о смысле конкретной генерации.

Примеры:

```text
без mood
только blues
проверка женского вокала
плохой порядок строк
лучший русский из серии
тест Keep/Words
BF16, контроль
тот же ABC, другой sound seed
```

Это решает реальную проблему, которая уже проявилась в тестах: номер генерации меняется автоматически, а пользователь может забыть изменить смысловую часть имени файла.

С заметкой смысл дубля хранится внутри самого файла и не зависит от имени.

---

## 7. Имя файла не должно быть базой данных

Имя файла можно оставить коротким:

```text
Лопата - Будильник_17.opus
```

Всё важное хранится внутри metadata.

Это лучше, чем превращать filename в строку вида:

```text
Будильник_Q8_seed123_blues_nomood_test5_good-russian_v2.wav
```

Имя файла остаётся читаемым, а информация не теряется.

---

## 8. Lyrics должны храниться внутри файла

Текст песни желательно записывать в стандартное поле lyrics, если контейнер/формат это поддерживает.

Плюсы:

- текст travels with audio;
- сторонние плееры и редакторы могут его показать;
- не нужно искать отдельный TXT;
- при переносе или публикации информация не теряется;
- проще будущая индексация библиотеки.

При наличии секций желательно сохранять текст в том виде, в котором он был передан модели:

```text
[Verse 1]
...

[Chorus]
...
```

---

## 9. Обложка

Если в музыкальном сценарии появится обложка трека/альбома, стандартный контейнер должен по возможности хранить её внутри файла.

Это не обязательный минимум первой версии, но архитектура должна не мешать этому.

---

## 10. Что НЕ надо писать в обычные пользовательские метаданные

Не следует превращать обычный музыкальный файл в дамп лабораторной диагностики.

В стандартный пользовательский трек НЕ нужно запихивать:

```text
полный ABC
semantic tokens
checkpoint tensors
KV cache
полные runtime logs
внутренние JSON request
сырые diagnostic traces
```

Для этого должен существовать отдельный исследовательский/стендовый артефакт.

Обычный музыкальный файл:

> музыка + человечески полезная информация.

Экспериментальный стенд:

> request + ABC + semantic tokens + logs + hashes + audio + metrics.

Эти два режима не надо смешивать.

---

## 11. Что можно сохранять дополнительно при повторяемости

Небольшие технические поля допустимы, если они реально полезны пользователю:

```text
LM seed
Sound seed
Model
Precision
Backend version
```

Для YuE2 особенно полезно хранить оба seed, если backend их разделяет.

---

## 12. Метаданные должны записываться автоматически

Пользователь не должен вручную заполнять то, что ЛОПАТА и так знает.

Автоматически:

```text
модель
вариант модели
precision
backend
версия ЛОПАТЫ
дата
seed
проект
номер дубля
lyrics
жанр / стиль — если известны из проекта
```

Вручную пользователь добавляет только то, что программа не может знать:

```text
название
автор
альбом
заметка
оценка
личный комментарий
```

Часть этих полей можно наследовать от проекта/альбома.

---

## 13. Зачем стандартные метаданные

Преимущество стандартных тегов:

- Windows и сторонние программы могут индексировать их;
- музыкальные плееры могут показывать их;
- многие сайты и сервисы подхватывают стандартные metadata при загрузке;
- файлы остаются понятными вне ЛОПАТЫ;
- библиотека не привязана навсегда к одному приложению;
- проще поиск среди тысяч генераций.

Это особенно важно для ЛОПАТЫ как локального автономного инструмента.

---

## 14. Альбомная структура

Так как музыкальный сценарий планируется тестировать на конкретной структуре альбома, полезно предусмотреть:

```text
Album
Track number
Disc number
Project
Title
Artist
Year / Date
Genre
Comment
Lyrics
Cover
```

Даже если часть полей сначала не используется, схема должна позволять их добавить без смены формата.

---

## 15. Возможный рабочий пайплайн

```text
Backend генерирует аудио
↓
LOPATA получает исходник
↓
при необходимости сохраняет исходник временно
↓
перекодирует в Ogg Opus
↓
записывает метаданные
↓
добавляет файл в библиотеку проекта
↓
исходный временный WAV удаляется, если он больше не нужен
```

При экспорте:

```text
рабочий Opus / исходный lossless при наличии
↓
Export
↓
FLAC / WAV / MP3 / Opus
↓
метаданные переносятся
```

---

## 16. Важная оговорка по качеству

Если появится сценарий, где требуется lossless master для дальнейшего монтажа, можно предусмотреть настройку проекта:

```text
Working storage:
- Compact — Opus
- Lossless — FLAC
```

Но для обычных ИИ-генераций и массового перебора кандидатов приоритет — компактность.

---

## 17. Связь с исследовательским стендом

Обычная музыкальная библиотека и benchmark-стенд должны использовать разные уровни хранения.

### Обычная библиотека

```text
audio
lyrics
title
genre
model
precision
seed
LOPATA version
user note
```

### Экспериментальный стенд

```text
request JSON
style
lyrics
LM seed
sound seed
ABC
semantic tokens
WAV / reference audio
timings
logs
hashes
ASR transcript
line coverage
omissions
repeats
reorders
language drift
good-case score
```

Главное:

> лабораторные данные хранятся рядом с тестом, а не забиваются в обычный пользовательский аудиофайл.

---

## 18. Итоговое направление

Предпочтительная концепция:

```text
Рабочая музыка:
Ogg Opus + стандартные metadata

Экспорт:
FLAC / WAV / MP3 / Opus

Обычные metadata:
название
автор
альбом/проект
жанр
дата
lyrics
обложка
LOPATA version
model
variant/precision
backend
seed
user note

Не помещать в обычный файл:
ABC
semantic tokens
KV/cache
полные логи
огромные JSON
```

Ключевой пользовательский принцип:

> Каждый музыкальный файл должен сам объяснять, что это за генерация, даже если его вынесли из папки проекта и забыли, как назывался тест.
