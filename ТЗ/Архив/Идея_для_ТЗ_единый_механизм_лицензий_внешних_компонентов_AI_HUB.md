# ТЗ: единый механизм принятия лицензий внешних компонентов AI_HUB

## 1. Цель

Добавить в AI_HUB единый механизм отображения и принятия лицензий внешних компонентов, которые программа использует или самостоятельно загружает.

Механизм должен разделять внешние компоненты на две группы:

1. **Обязательные компоненты AI_HUB** — без них базовая программа не может полноценно работать.
2. **Профильные компоненты** — нужны только отдельным сценариям и загружаются по желанию пользователя.

Главная цель: до загрузки и/или использования стороннего компонента пользователь должен видеть, кому он принадлежит и на каких условиях распространяется.

---

## 2. Группа 1 — обязательные компоненты

К этой группе относятся:

- ядро AI_HUB;
- обязательные backend/runtime;
- обязательные вспомогательные утилиты;
- другие внешние компоненты, без которых базовая установка AI_HUB неработоспособна.

### Поведение

Лицензии этой группы принимаются **одновременно с установкой AI_HUB**.

В установщике должен появиться отдельный этап:

**«Лицензии внешних компонентов»**

На нём пользователь видит список:

- название компонента;
- разработчика/правообладателя;
- тип лицензии;
- ссылку или кнопку просмотра полного текста лицензии;
- краткое пояснение при наличии существенных ограничений.

Пример:

```text
AI_HUB использует следующие внешние компоненты:

• Component A — MIT
• Component B — Apache 2.0
• Component C — GPL-3.0
...

[Просмотреть лицензии]

☐ Я ознакомился и принимаю условия лицензий
   обязательных внешних компонентов.

[Продолжить установку]
```

Без подтверждения установка не продолжается.

Не требуется отдельное подтверждение каждой обязательной лицензии, если все они представлены пользователю в этом общем этапе.

---

## 3. Группа 2 — профильные компоненты

К этой группе относятся:

- специализированные AI-модели;
- модели генерации изображений;
- модели генерации видео;
- специализированные vision/audio/OCR модели;
- дополнительные runtime;
- профильные инструменты конкретных сценариев;
- другие необязательные компоненты.

Они **не должны включаться в лицензионное соглашение установщика заранее**, поскольку пользователь может никогда ими не воспользоваться.

### Поведение

Перед первой загрузкой такого компонента AI_HUB показывает его собственную лицензионную карточку.

Пример:

```text
FLUX.2 [dev]

Разработчик:
Black Forest Labs

Источник:
Hugging Face / официальный репозиторий

Лицензия:
FLUX Non-Commercial License

Основное ограничение:
Только некоммерческое использование.

[Открыть полный текст лицензии]

☐ Я ознакомился и принимаю условия лицензии
   правообладателя.

[Скачать]
[Отмена]
```

Пока пользователь не подтвердил условия, загрузка не начинается.

---

## 4. Разные типы лицензий

Механизм должен поддерживать разные уровни отображения.

### 4.1. Свободные лицензии

Примеры:

- MIT;
- Apache 2.0;
- BSD.

Можно использовать облегчённую карточку:

```text
Лицензия: Apache 2.0
Источник: ...
[Подробнее]
[Скачать]
```

Явный checkbox необязателен, если это не требуется условиями конкретной лицензии.

### 4.2. Лицензии с существенными ограничениями

Например:

- Non-commercial;
- research-only;
- custom license;
- gated model;
- другие специальные условия.

Для них обязательно:

- явное описание основного ограничения;
- доступ к полному тексту;
- отдельное подтверждение пользователя;
- только после этого разрешается загрузка.

---

## 5. Хранение информации о согласии

Для профильных компонентов, требующих явного согласия, локально сохранять минимум:

```text
component_id
component_version
license_id / license_name
license_version или hash текста лицензии
official_license_url
accepted_at
```

Пароли, токены и иные лишние пользовательские данные для этого механизма не нужны.

---

## 6. Изменение лицензии

Если лицензия компонента изменилась относительно той версии, которую пользователь ранее принимал:

```text
старая license hash/version != новая
```

старое согласие больше не считается достаточным.

Перед следующей загрузкой или обновлением компонента показать новую лицензию и запросить повторное подтверждение.

Если лицензия не изменилась, повторно спрашивать пользователя не нужно.

---

## 7. Источник компонента

Для каждого управляемого внешнего компонента желательно иметь единый набор метаданных:

```text
ID
название
разработчик / правообладатель
официальный источник
URL загрузки
версия / revision
лицензия
URL лицензии
тип лицензионного режима
SHA-256, если уже используется
```

Не дублировать эти сведения отдельно в интерфейсах разных сценариев, если в проекте уже существует общая библиотека/manifest компонентов.

---

## 8. Важная граница

AI_HUB не должен формулировать собственное разрешение на использование чужого компонента.

Не писать:

> «AI_HUB разрешает коммерческое/некоммерческое использование модели».

Корректная логика:

> «Компонент распространяется правообладателем на следующих условиях. Перед загрузкой ознакомьтесь с лицензией правообладателя».

AI_HUB только:

- сообщает происхождение компонента;
- предоставляет официальный источник;
- показывает его лицензию;
- фиксирует подтверждение пользователя;
- после этого выполняет загрузку.

---

## 9. UX

Механизм должен быть общим, а не написан отдельно для каждой модели.

Необходимо избежать:

- десятков разных самописных диалогов лицензий;
- повторных подтверждений одной неизменившейся лицензии;
- запроса согласия на компоненты, которыми пользователь никогда не пользуется;
- большого юридического полотна прямо в основном интерфейсе.

Основной экран должен быть компактным, полный текст открывается отдельно.

---

## 10. Интеграция с существующей архитектурой

Перед реализацией Codex должен:

1. проверить существующий механизм установки AI_HUB;
2. проверить общую библиотеку компонентов/моделей;
3. найти все места, где AI_HUB самостоятельно скачивает внешние файлы;
4. определить, где уже хранятся source/repository/revision/license/checksum;
5. использовать существующие структуры вместо создания параллельного каталога;
6. определить текущие обязательные и профильные компоненты.

Не создавать отдельную лицензионную систему для каждой ветки сценария.

Желательная единая цепочка:

```text
компонент выбран
      ↓
проверка лицензии
      ↓
нужно согласие?
 ┌────┴────┐
 нет       да
 │          ↓
 │     показать gate
 │          ↓
 │      согласие
 └────┬─────┘
      ↓
существующий механизм загрузки
```

---

## 11. Что не входит в задачу

Не требуется:

- менять лицензии самого AI_HUB;
- юридически интерпретировать каждую стороннюю лицензию;
- блокировать пользователя после установки модели в зависимости от того, как он её использует;
- контролировать коммерческое использование результатов;
- самостоятельно загружать новые модели, которых сейчас нет в каталоге;
- переделывать существующий менеджер компонентов без необходимости.

---

## 12. Проверки

Минимальные тестовые случаи:

1. Обязательные компоненты показываются в установщике.
2. Без принятия обязательных лицензий установка не продолжается.
3. Свободная профильная модель скачивается через облегчённую карточку.
4. Компонент с restrictive/non-commercial лицензией требует явного согласия.
5. Отмена не запускает загрузку.
6. После принятия одной и той же версии повторное согласие не спрашивается.
7. Изменение license version/hash вызывает повторный запрос.
8. Ошибка открытия страницы лицензии не должна автоматически означать согласие.
9. Существующий download/install workflow после добавления preflight не ломается.
10. Кириллица и UTF-8 в названиях/описаниях не повреждаются.

---

## 13. Runtime-проверка лицензий перед запуском сценария

Наличие установленного компонента **не означает автоматически наличие принятой лицензии**.

Перед запуском любого сценария AI_HUB должен определить полный набор внешних компонентов, которые сценарий собирается использовать:

```text
ядро + backend/runtime + модели + специализированные утилиты
```

Для каждого элемента проверить:

```text
компонент существует
+
компонент распознан
+
для его текущей версии/лицензии есть необходимое согласие
```

Если обязательное согласие отсутствует, повреждено или относится к другой версии лицензии:

1. не считать компонент готовым к запуску;
2. показать лицензионную карточку;
3. запросить согласие;
4. только после согласия разрешить использование компонента.

Это правило действует **независимо от способа появления файла на компьютере**.

Примеры:

- пользователь скачал модель через AI_HUB;
- пользователь вручную вернул ранее удалённую модель;
- модель скопирована из backup;
- пользователь заменил файлы вручную;
- компонент был установлен другой программой;
- база состояния AI_HUB была потеряна/сброшена, но сами файлы сохранились.

То есть сценарий должен проверять не:

> «модель установлена?»

а:

> **«модель установлена и для её использования выполнен требуемый license preflight?»**

Если нет — показать согласие повторно.

---

## 14. Защита от рассинхронизации состояния

License-state не должен зависеть только от штатного процесса установки.

Нужно учитывать возможное расхождение:

```text
файлы на диске ≠ состояние библиотеки AI_HUB ≠ сохранённые согласия
```

При обнаружении такого состояния AI_HUB должен восстановить безопасное состояние автоматически.

Минимальная логика:

- файл есть, согласия нет → запросить согласие;
- согласие есть, файл удалён → ничего не делать до следующей установки/использования;
- файл вернулся после удаления → проверить согласие заново по ID/version/license;
- лицензия изменилась → запросить новое согласие;
- невозможно определить лицензию компонента → не считать лицензионную проверку успешно пройденной и показать пользователю причину.

При этом **не нужно запрещать пользователю вручную управлять файлами**. Механизм должен корректно переживать такие действия.

---

## 15. Постоянное правило для Codex

После реализации механизма его требования добавить в проектные инструкции Codex (`AGENTS.md` и при необходимости расширенное описание в `CODEX.md`).

Смысл правила:

> **Любой новый внешний компонент, модель, runtime, backend или утилита, который AI_HUB умеет загружать или запускать, обязан быть зарегистрирован в общей системе лицензирования до добавления в пользовательский сценарий.**

Codex при добавлении нового внешнего компонента обязан:

- определить, обязательный он или профильный;
- указать разработчика/правообладателя;
- указать официальный источник;
- указать лицензию и официальный URL лицензии;
- определить, требуется ли явное пользовательское согласие;
- подключить компонент к общему License Preflight;
- не создавать отдельный обходной механизм скачивания;
- не считать наличие файла достаточным основанием для запуска;
- добавить соответствующую проверку в сценарий использования компонента.

**Запрещается добавлять новый автоматически загружаемый/запускаемый внешний компонент без заполненных лицензионных метаданных.**

---

## 16. Общая цепочка запуска сценария

License gate должен быть не только частью downloader'а, а обязательным условием допуска компонента к работе.

```text
СЦЕНАРИЙ
   ↓
определить требуемые компоненты
   ↓
файлы доступны?
   ↓
license preflight пройден?
   ├─ да → запуск
   │
   └─ нет
       ↓
   показать лицензию
       ↓
     согласие
       ↓
      запуск
```

Это должно защищать сценарий даже в случаях, когда:

- компонент установлен вручную;
- компонент восстановлен из резервной копии;
- компонент появился после внешнего копирования;
- часть локального состояния AI_HUB была удалена;
- компонент был заменён или обновлён нештатным способом.

---

## 17. Критерий готовности

Задача считается завершённой, когда:

- существует один общий механизм License Preflight;
- обязательные лицензии интегрированы в установку AI_HUB;
- профильные компоненты проходят проверку перед загрузкой;
- restrictive-лицензии требуют явного подтверждения;
- факт принятия версии лицензии сохраняется;
- механизм подключён к существующему менеджеру компонентов без дублирования архитектуры;
- все текущие автоматически загружаемые компоненты классифицированы по одной из двух групп;
- перед запуском сценария проверяется наличие требуемых согласий для всех внешних компонентов;
- ручное удаление/возврат/замена файлов не позволяет обойти лицензионную проверку;
- проектные правила Codex обновлены новым обязательным требованием;
- необходимые проверки пройдены без новых ошибок.

---

## 18. Обязательное действие до начала реализации

**До изменения кода Codex должен сначала показать пользователю:**

1. найденный текущий список обязательных внешних компонентов;
2. найденный текущий список профильных внешних компонентов;
3. все существующие места автоматической загрузки внешних файлов;
4. где сейчас хранятся сведения об источнике, версии, revision, checksum и лицензии;
5. предложенную точку интеграции общего License Preflight;
6. какие файлы проекта потребуется изменить;
7. какие новые структуры действительно необходимы, если существующих недостаточно.

**Не начинать реализацию до подтверждения пользователя.**
