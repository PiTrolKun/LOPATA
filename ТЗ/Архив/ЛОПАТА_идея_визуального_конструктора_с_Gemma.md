# ЛОПАТА — визуальный конструктор программ с локальной LLM

**Дата фиксации:** 4 ноября 2026 года
**Статус:** концепция для архива идей; **не техническое задание и не команда на разработку**.
**Рабочее название:** «Визуальный конструктор с Gemma» (постоянное название не выбрано).

## 1. Исходная идея

Взять подход классических визуальных конструкторов эпохи CD/DVD — прежде всего **AutoPlay Media Studio** и близких по философии инструментов — и соединить его с локальным генеративным программированием.

Главное наследие старого подхода — **ручная компоновка интерфейса из простых элементов, их свойства, события и комбинирование элементарных действий в сложное поведение**. Не требуется копировать ориентацию AutoPlay на автозапуск, диски, открытие файлов и мультимедийные меню: новый конструктор предназначен для создания разнообразных настольных Windows-приложений.

В старых конструкторах сложный проект был возможен даже из небольшого набора компонентов, если пользователь знал основы программирования, системные механизмы Windows и способы нестандартно связать события. **Локальная LLM должна снизить именно этот порог входа**, оставив человеку свободу проектировать интерфейс и логику.

Принцип: **человек собирает программу; ИИ помогает программировать отдельные действия, а не пытается автономно создать всю программу по одной фразе**.

## 2. Для чего нужен такой инструмент

- Создавать обычные настольные утилиты Windows, а не только меню дисков и файловые оболочки.
- Позволять собирать достаточно сложные системы путём сочетания простых компонентов, переменных, условий, событий и пользовательских обработчиков.
- Не требовать от пользователя знания синтаксиса языка и Windows API для большинства нестандартных действий.
- Сделать задачи для локальной LLM небольшими, проверяемыми и ограниченными по области изменения.
- Сохранять полезность конструктора даже при недоступности LLM или интернета: стандартные элементы и действия должны работать самостоятельно.

Потенциальные примеры: калькулятор, небольшой графический редактор, обработчик данных, служебная утилита, специализированное оконное приложение. Это **примеры выразительности среды**, не обещание, что все такие проекты будут простыми.

## 3. Программная модель конструктора

### 3.1. Визуальная сборка

Пользователь вручную размещает элементы на форме и управляет их свойствами: кнопки, поля ввода, списки, изображения, переключатели, панели и, по мере развития, более универсальные компоненты (например, графическое полотно).

У элементов есть типовые события: нажатие, изменение значения, загрузка формы, действия указателя и т. п. Точный каталог ещё не определён.

### 3.2. Действия в событиях

Для каждого события можно составить последовательность действий:

1. готовые стандартные команды конструктора;
2. условия, операции с переменными, вызовы других действий;
3. пользовательский код и небольшие функции, написанные или исправленные локальной моделью.

Эти способы **не конкурируют**, а комбинируются внутри одного обработчика. Конструктор не должен ограничивать пользователя только заранее предусмотренными командами.

### 3.3. Роль модели

Модель получает строго относящиеся к задаче сведения: выбранный элемент, событие, доступные свойства, типы, переменные, стабильный API конструктора, необходимые связи с другими элементами и текущий фрагмент кода.

Модель решает **локальную техническую задачу**. Например: «При перетаскивании указателя рисуй линию; толщину бери из этого ползунка». Она не должна без разрешения перерабатывать остальной проект.

Предполагаемый цикл: описание действия → код/настройки → компиляция и диагностика → исправление конкретной ошибки → проверка поведения. Сложные программы формируются из многих небольших шагов под контролем человека.

### 3.4. Универсальность простых инструментов

Желательно иметь не огромный набор одноцелевых «волшебных» компонентов, а небольшое, но достаточно выразительное ядро операций. В то же время для сложных графических задач базовые механизмы (рисование, координаты, события указателя, отображение) должны быть реализованы надёжно, а не каждый раз изобретаться моделью.

## 4. Две специализации одной Gemma

Выбрано концептуальное направление: **одна локальная модель с разными системными промптами, доступными инструментами и отдельными контекстами**, как разделение работы между программистом и исследователем в текущем процессе разработки ЛОПАТЫ.

### Режим А. Программист / конструктор

- Основная задача: создавать и изменять действия для конкретных элементов и событий.
- Работает с состоянием текущего проекта, API и диагностикой.
- Опирается прежде всего на встроенные знания, стандартные действия и локальную документацию.
- Обращается к поиску **только при реальной необходимости**: неизвестная технология, свежий API, новая версия, сложная совместимость.
- Не получает полномочий бесконтрольно менять весь проект.

### Режим Б. Исследователь / ИИ-поиск

- **Отдельный чат** с системными инструкциями преимущественно для поиска, чтения и сопоставления технических источников.
- По назначению напоминает ИИ-поиск в браузере: репозитории, библиотеки, драйверы, движки, документация, версии, ограничения и примеры.
- Допускаются короткие обсуждения и сравнения находок; не задуман как универсальный разговорный ассистент или второй программист.
- Может использоваться независимо от текущего проекта — в том числе просто из любопытства, до начала разработки.
- Не обязан самостоятельно писать код для текущего приложения, если пользователь находится именно в исследовательском режиме.

**Общее между режимами:** локальный архив результатов поиска. **Раздельное:** история сообщений и рабочие инструкции. Два параллельно загруженных экземпляра модели в VRAM для этой схемы не обязательны.

## 5. Выбор локальной LLM

Первый кандидат — **Gemma 4 26B A4B Instruct QAT**, уже применённая и практически проверенная в сценарии ЛОПАТЫ «Если накипело». Она заинтересовала качеством диалога и применением управляемых инструментов, в том числе при обращении к сохранённым беседам.

Для нового конструктора это **исходная гипотеза, а не доказанное качество программирования**. Требуется отдельная проверка написания небольших обработчиков, дисциплины инструментов и исправления ошибок компиляции.

Предпочтение пользователя при рассмотрении Qwen — не брать поколения старее **Qwen3.5**; CodeGemma 7B образца 2024 года неинтересна из-за возраста. Сравнительные современные модели могут исследоваться позже, но поиск новой LLM **не является условием начала концептуального проекта**.

## 6. Необязательный интернет и накопительный поиск

Идея внешнего поиска — **не заставлять модель искать стандартные алгоритмы, которые она и так знает**, а получать актуальную или отсутствующую в весах техническую информацию: свежие драйверы, версии движков, новый API, исправления, библиотеки и проекты.

### 6.1. Автоматическое накопление

Если сетевой поиск уже выполнен, полученные результаты **попутно сохраняются**. Это почти бесплатная дополнительная операция относительно уже совершённого сетевого запроса. Сохранять полезно и результаты, которые не использовались в текущем решении: они могут понадобиться позднее.

Накопление происходит и при обычной исследовательской беседе — пользователь может изучать GitHub без какой-либо конкретной разработки.

### 6.2. Единый поиск с локальным резервом

- **Сеть доступна:** поиск обращается к внешним источникам и пополняет локальный архив.
- **Сети нет:** тот же инструмент ищет по уже накопленным данным.
- **Сеть вернулась:** новый поиск снова доступен, старый архив не теряется.

Критично: это **обычный поисковый кэш с локальным индексом**, а не обязательная сложная агентная память, саммари или дополнительная LLM. Подходящий простой механизм для исследования — полнотекстовый индекс, например SQLite FTS5; позже при необходимости возможен более сложный поиск.

### 6.3. Сохранение репозиториев

Помимо кратких результатов можно сохранять исходники, документацию и **снимки репозиториев целиком**. Поскольку размеры репозиториев различаются, предусмотреть пользовательские ограничения:

- максимальный объём загрузки;
- допустимые типы файлов;
- исключение крупных бинарных материалов, Git LFS и подобных тяжёлых вложений;
- выбор краткого, выборочного или полного сохранения.

Для найденных материалов желательно сохранять адрес источника, дату получения, ветку/коммит или версию, структуру файлов и лицензию. Это позволяет не путать архив старой версии с актуальной документацией.

### 6.4. Индексация и повторное использование

Индексировать сохранённые репозитории и документы по именам файлов, классам, функциям, тексту и связанным метаданным. В своей базе можно проводить частый поиск, в том числе поперёк нескольких репозиториев, без сетевых задержек и ограничений API.

**Архив остаётся полезным при замене модели**: сохраняются сами первоисточники, а индекс можно перестроить без повторного скачивания.

## 7. Технологический фундамент

По предварительному обсуждению наиболее практично **не уходить от каркаса ЛОПАТЫ**:

- **C# / .NET 10** — основной язык и платформа;
- **WPF** — визуальный редактор и основной интерфейс;
- **Roslyn** — компиляция и проверка генерируемого C#;
- существующие решения ЛОПАТЫ по запуску локальных LLM и управлению процессами — вероятная база для переиспользования;
- локальное хранилище и текстовый индекс — для технического кэша.

WinForms рассматривается как возможная традиционная альтернатива для простых форм, но **предварительное предпочтение — WPF**, так как нужен не только конструктор примитивных окон, но и потенциально нестандартные интерфейсы.

Сохранять проект следует **как структуру элементов, свойств, событий и связей, отдельно от генерируемого кода**, чтобы не превращать всю программу в единственный нестабильный исходник.

## 8. Результат разработки пользователем

Созданная утилита должна иметь возможность собираться в **самостоятельную Windows-программу**, работающую без ЛОПАТЫ, конструктора, Gemma и интернета, если её собственная функциональность не требует сети или моделей.

Внешние зависимости готовой программы включаются в её комплект там, где это технически и юридически допустимо. Наличие встроенного ИИ в конечной утилите — **не обязательное свойство**, а возможная отдельная задача.

Для проверки пользовательского кода нужен изолированный тестовый запуск, а не безусловное выполнение сгенерированных действий в основном процессе конструктора. Поиск кода и чтение документации не должны автоматически разрешать установку драйверов, запуск непроверенного ПО или изменение системы.

## 9. Чего эта концепция не предполагает

- Не обычный чат «сделай всё приложение одной командой».
- Не учебная среда с игрушечными ограничениями.
- Не узловой вычислительный граф по образцу ComfyUI.
- Не повторение CD/DVD-ориентации AutoPlay Media Studio.
- Не обязательное облачное API, подписка или сетевой бэкенд для генерации.
- Не два разных набора весов LLM для двух ролей.
- Не необходимость загружать всю огромную историю GitHub или все репозитории целиком.
- Не старт разработки сейчас: идея сохранена на будущее.

## 10. Основные нерешённые вопросы для будущего обсуждения

1. Минимальный, но выразительный каталог визуальных элементов и стандартных событий.
2. Контракт доступа к объектам и состоянию приложения: переменные, методы, события, межэлементные связи.
3. Безопасная компиляция, тестирование и применение кода без повреждения проекта.
4. Формат проекта и экспорт самостоятельных EXE, включая управление зависимостями.
5. Политика загрузки, индексирования, объёма и обновления локального архива репозиториев.
6. Практический стенд Gemma на коротких обработчиках и обращениях к инструментам поиска.
7. Границы между «готовым стандартным действием» и произвольным кодом.

## 11. Суть одной фразой

**Универсальный событийный визуальный конструктор Windows-приложений в духе старых AutoPlay / Visual Basic, где локальная Gemma помогает писать и проверять небольшие обработчики, а отдельный ИИ-поиск накапливает технические материалы для онлайн- и офлайн-работы.**
