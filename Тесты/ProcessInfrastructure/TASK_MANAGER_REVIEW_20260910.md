# Task Manager: пользовательская проверка 0.1.86-dev

2026-09-10. Windows 11 Pro, 10.0.26200. Результат: визуальная группировка не выполнена; исправление пока не подтверждено.

## Наблюдение

На пользовательском снимке `codex-clipboard-84372127-8e19-41b1-9850-91e2776dd9cc.png` Python (2) и llama-server.exe отображаются отдельно. В раскрытой группе AIHub только окно ЛОПАТЫ. Снимок не содержит PID, поэтому нельзя достоверно приписать каждый Python-процесс из него конкретному worker.

## Локальные свидетельства

Журнал `%LOCALAPPDATA%/AI_HUB/Diagnostics/Processes/processes.jsonl`, владелец 10988 (время UTC):

| Время | Компонент | PID | Событие |
|---|---|---:|---|
| 05:22:13.739 | KokoroSpeechRuntimeService | 27888 | started |
| 05:22:28.202 | OmniLlamaRuntimeService | 31652 | started |
| 05:22:57.618 | OmniLlamaRuntimeService | 31652 | exited, -1 |
| 05:22:57.633 | KokoroSpeechRuntimeService | 27888 | exited, -1 |

Две короткие диагностические команды ImageAnalysisHeavyResourcePlanningService завершились с кодом 0. На момент проверки через Win32_Process процессов AIHub, llama-server, python, pythonw и qdrant уже не было. Журнал подтверждает запуск двух workers через реестр и их завершение, но сам по себе не устанавливает причину закрытия или родство всех строк скриншота.

OwnedProcessRegistry.Start устанавливает CreateNoWindow=true и сразу после Process.Start назначает отдельный Windows Job Object. После успешной регистрации пишет started. Job обеспечивает владение и уборку; общей визуальной идентичности для EXE код не задаёт. Строка AIHub с вложенным главным окном не является свидетельством объединения workers.

## Проверка технологии

- Microsoft описывает [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) как управление группой процессов, наследование принадлежности потомками и завершение. Это не контракт отображения Task Manager.
- [AppUserModelID](https://learn.microsoft.com/en-us/windows/win32/shell/appids) документирован для группировки окон на панели задач и Jump Lists. Нельзя считать его готовым исправлением диспетчера задач без отдельного опыта.
- В трекере Microsoft есть открытый [отчёт WebView2 #5628](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5628) о похожем расхождении на Windows 11, включая замечание автора об отсутствии эффекта от AppUserModelID. Это пользовательский отчёт о другом runtime, не доказательство общей причины ЛОПАТЫ и не официальная гарантия решения.
- Чтение существующего Task Manager через UI Automation вернуло только контейнеры Pane, без строк процессов. Автоматическая проверка визуального результата этим способом не получена. Настройки и процессы Task Manager не менялись.

## Решение по текущему проходу

Отменена формулировка готовности к приёмке: ТЗ на доработке. Код, системный реестр, EXE сторонних компонентов и установщик не менялись. Подмена имён файлов, внедрение кода в сторонние процессы и смена упаковки приложения не применялись. Дополнительные модели не запускались. Следующая проверка должна установить рабочий способ именно визуального объединения разных EXE на этой Windows, сохранив скрытый запуск, stdout/stderr, остановку и защиту от бесхозных потомков. До такого подтверждения обещать результат как у Teams нельзя.
